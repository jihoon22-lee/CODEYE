# 12. 보고서·웹 화면·진행 표시

## 1. 화면 구성

프로젝트 목록, 등록/연결 진단, 프로젝트 개요, 실행 상세, 보고서 요약, 영역별 분석, 발견 사항 상세, 결과 비교, 예약, 운영자 노드/풀/모델/도구 설정으로 나눈다. 현재 실행과 마지막 완료 보고서를 함께 제공한다. 새 분석을 시작했다고 기존 보고서를 감추지 않는다.

등록 필수 입력은 Git URL+브랜치 또는 노드/root+경로다. 이름은 자동 제안하고 설명·첨부·관심 영역·테스트·예약은 접힌 선택 항목이다. 자동 탐색 결과를 수정할 수 있지만 매 실행 승인 폼을 강제하지 않는다.

## 2. 보고서 3단 구조

### 요약

분석 입력/SHA·시각·프로필·실행 상태, 우선 확인할 3~5개 사항, 신규/지속 항목, 필수 검사 실패, 분석 공백, 테스트 실행 여부를 배치한다. 한 개의 100점 품질 점수를 초기 핵심 지표로 만들지 않는다. 읽는 사람이 '그래서 지금 무엇을 해야 하나'를 알 수 있어야 한다.

### 영역별

정확성, 오류·취소, 동시성, 자원 수명, 데이터/인터페이스 계약, 소스 보안, 구조·유지보수성, 성능 구조, 테스트 공백을 기본 축으로 둔다. 각 영역은 발견 사항뿐 아니라 수행한 검사·검토와 제한을 표시한다. 수행하지 않은 영역을 녹색으로 칠하지 않는다.

### 개별 발견

| 항목 | 요구 |
|---|---|
| 제목 | 구체적인 결과와 조건. '코드를 개선하세요' 금지 |
| 요약 | 어떤 조건에서 무엇이 잘못되는지 2~4문장 |
| 영향 | 사용자·데이터·서비스·운영에 미치는 영향, 범위 |
| 심각도 | critical/high/medium/low/info와 판단 이유 |
| 검증 상태 | unreviewed/supported/reproduced/refuted/inconclusive |
| 근거 | snapshot 코드, related locations, flow, tool observation, 실행 결과 |
| 반증 | 확인한 방어 코드, 배제한 가능성, 남은 전제 |
| 개선 | 변경 방향과 호환성·부작용 고려 |
| 확인 | 회귀 테스트 입력/조건 또는 검토 절차 |
| 이력 | 최초 발견·현재 비교·사람 disposition |

## 3. 심각도와 확신

critical은 현실적인 조건에서 광범위한 중대한 영향이 있는 경우, high는 중요한 경로의 심각한 실패, medium은 제한된 조건의 실질적 결함, low는 영향이 낮은 개선, info는 설명·관찰이다. 영향이 크다는 가정만으로 critical로 올리지 않는다.

validation과 review priority는 별개다. 영향이 클 수 있지만 미확정인 후보는 '우선 확인'으로 보일 수 있다. 모델의 숫자 confidence를 측정된 정확도처럼 표시하지 않는다. 초기에는 정성적 근거 수준을 사용한다. tool-reported도 실제 결함 확정과 같지 않다.

## 4. 통계의 원천

모든 숫자는 finding/observation/task/coverage 데이터에서 계산한다. LLM 서술이 숫자를 만들어내면 검증 실패다. 요약은 action 항목(supported/reproduced)과 미확정 후보(unreviewed/inconclusive), 기각(refuted), 숨긴 disposition을 구분한다. 규칙 진단 수와 원인별 finding 수를 나란히 표시해 중복 제거를 설명한다.

데이터 기반 fallback 보고서는 모델 서술 생성 실패에도 열람 가능하다. HTML과 Markdown과 JSON은 같은 report revision을 사용한다. schema validation과 증거 resolve가 실패한 주장은 본문에서 확정적으로 표시하지 않는다.

## 5. 진행 상태

표시할 정보는 현재 stage, 활성 task/tool, completed/total, succeeded/failed/skipped, 경과 시간, 마지막 heartbeat, 대기 사유다. completed task 수에는 terminal이 포함될 수 있지만 성공 수를 따로 표시한다.

추정 진행률은 plan revision의 작업량 가중치다. 예: 종료 task의 weight 합/계획 weight 합. 이를 시간의 경과 비율이나 코드 검증 비율이라고 표현하지 않는다. 동적으로 추가 작업이 생기면 revision과 추가 이유를 표시하고 새 분모를 사용한다. 백분율이 내려갈 수 있음을 UI로 설명하며 거짓 단조 진행률을 유지하지 않는다.

도구가 실제 파일 처리량을 제공할 때만 N/M 파일을 표시한다. LLM은 검토 단위 완료 수와 현재 활동을 표시한다. 토큰 스트림·heartbeat를 실제 분석 완료율로 환산하지 않는다. 상세 내부 사고 과정 대신 '오류 종료 경로 확인 중' 같은 작업 상태를 표시한다.

첫 실행은 ETA 없음이 기본이다. 유사 snapshot 규모·도구·모델·node·캐시 조건의 이력이 충분할 때 범위 추정을 제공한다. 잔여 시간을 정확한 약속으로 쓰지 않는다. 네트워크 단절 시 '마지막 확인 12초 전'을 표시하고 실행이 멈췄다고 단정하지 않는다.

## 6. 근거와 코드 뷰

기본 코드 뷰는 분석한 snapshot이다. 현재 브랜치의 최신 파일로 자동 연결하지 않는다. 파일·행·심볼·related flow를 연결하고 원시 진단과 해석을 펼쳐 볼 수 있게 한다. snapshot 만료 시 source unavailable을 표시하며 다른 버전 소스로 대체하지 않는다.

흐름이 도구가 생성한 경로인지 모델이 추정한 경로인지 표시한다. 코드 내 HTML/script와 모델 Markdown은 escape/sanitize한다. 외부 이미지·자동 링크 fetch는 기본 금지한다. secret 발견은 마스킹된 위치와 조치만 보여준다.

## 7. 비교와 사용자 검토

new/persisting/changed/absent_unverified/resolved_observed를 구분한다. 도구 실패 때문에 사라진 항목은 해결이 아니다. 비교 대상의 환경·규칙·범위 차이를 상단에 표시한다. 사람의 acknowledged/accepted_risk/false_positive/fixed_by_user/suppressed는 이유와 만료 범위를 기록한다.

## 8. 접근성과 내보내기

색상 외 텍스트/아이콘, 키보드 이동, 적절한 대비, 긴 코드 가로 스크롤, 표 페이지, 오류의 재시도 경로를 제공한다. 그래프는 표 대안을 갖는다. 첫 화면에 과도한 차트 대신 실행 상태와 행동 우선순위를 둔다.

초기 export는 JSON·Markdown·자체 포함 HTML이다. PDF는 후속 옵션이다. 코드 미포함 export는 snippets·raw logs·비밀값·내부 절대 경로뿐 아니라 서술에 섞인 코드 인용도 제거/검사한다. 다운로드 역시 프로젝트 권한을 검사한다. 외부 CDN·폰트가 필요한 HTML을 만들지 않는다.

## 9. 사용자 수용 기준

예시 보고서를 처음 보는 개발자가 짧은 읽기 후 핵심 위험, 근거, 미확인 범위, 수정·검증 방법을 찾을 수 있는지 평가한다. 읽기 시간을 실측하기 전 보장치로 쓰지 않는다. 보고서 장식의 수를 전달 품질로 평가하지 않는다. [예시 보고서](../examples/report.md)를 출력 계약의 기준으로 삼는다.
