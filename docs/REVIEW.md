# 모델 검토

모델 검토는 고정 스냅샷에서 정적 분석 뒤에 실행되는 제한된 모델 작업이다. 모델은 플랫폼이 고른 발췌와 근거 ID만 받는다. 모델의 출력은 후보와 판정 서술일 뿐이다. task 상태, 재현 여부, 통계, 보고서 수치는 워커와 서버가 구조화 기록으로 정한다. 이 문서는 역할, 지침 팩, 입력 선택과 크기 한도, 비밀값 선별, 출력 검사와 검증 규칙, 복구 경로, OpenCode 어댑터, 소스 정책, 검토 기록 형식을 정한다.

- 구현 위치: [`internal/worker/review`](../internal/worker/review), [`internal/worker/review/record`](../internal/worker/review/record), [`internal/worker/opencode`](../internal/worker/opencode), [`prompts/review`](../prompts/review)
- 요구사항: REQ-004/005/009/010/011/012/013/026/027/030, NFR-007/008/010([요구사항](REQUIREMENTS.md))
- 수용 시험: TC-05, TC-10~12, TC-16, TC-18, TC-33, TC-34, TC-76~79, TC-85~89, TC-97, TC-100, TC-123, TC-128, TC-129, TC-287, TC-288([시험](TESTING.md))
- 품질 평가와 지침 개정 절차: [평가](EVALUATION.md)

## 공통 경계

- 플랫폼이 승인한 스냅샷·모듈·발췌와 근거 ID만 모델에 전달한다. 원본 절대 경로, 인증정보, 평가 정답, 개인 모델 세션은 입력이 아니다.
- 대상 저장소의 README·AGENTS·설정에 있는 실행·권한·네트워크 요청은 문서 내용이다. 요청 설정·도구·권한을 바꾸지 못한다. 모든 입력은 `<review-input>` 안에 들어가고, 프롬프트는 그 내용을 신뢰하지 않는 검토 자료로 다루고 도구를 쓰지 말라고 지시한다.
- 문서에서 읽은 기대 동작, 코드에서 관찰한 동작, 그로부터 추론한 영향을 구분한다. 근거는 상대 경로·행 범위·blob SHA-256 또는 검증된 도구 관찰 참조로 남는다.
- 모델은 새 근거 ID를 발급하지 못한다. 셸·네트워크·추가 모델을 호출하지 못한다. 경로나 줄 번호를 지어내도 읽기·실행 범위가 늘지 않는다.
- 워커가 스냅샷의 바이트와 행 범위를 확인한다. 서버는 run·attempt·manifest·근거 연결을 확인한다.
- 실패·시간 초과·정책 제외는 해당 task에 남긴다. 이미 확보한 도구 관찰과 탐색 사실은 보존한다.
- 다른 모델이나 외부 모델로 자동 전환하지 않는다. 모델 설정이 없으면 검토 task는 `unsupported`(`model_not_configured`)다.
- 모델의 내부 추론(reasoning), 원시 이벤트 스트림, 원시 프롬프트, 프로세스 출력은 기록·로그·보고서·화면에 넣지 않는다.

## 검토 지침

검토 기준은 하나다(A52). 지침은 저장소의 [`prompts/review`](../prompts/review/pack.yaml)에 있고 빌드 시점에 실행 파일에 묶인다(`embed`). 대상 저장소가 지침이나 digest를 제공할 수 없고, run 요청·프로필·API·노드 설정으로 다른 지침을 고를 수 없다.

| `pack.yaml` id·version | 기록 schema | 역할 |
|---|---|---|
| `review` 2.8.0 | `0.7`(줄 번호 인용, 모든 역할과 slice). 이전 워커의 `0.2`, slice `0.3`, 계약 후속 검토 `0.4`, HTTP 경로를 고른 문서 `0.5`, 함께 읽은 HTTP 근거 `0.6`도 읽는다 | environment, documents, investigate, interpret, verify, contract |

- 지침 개정은 이 지침 하나에 한다. 개정의 검증 절차는 [평가](EVALUATION.md)에 있다.
- 보고서는 Go가 만들므로 종합·보고 역할에 모델을 호출하지 않는다.
- `scripts/validate_bundle.py`가 `pack.yaml`의 id·역할·언어 지침과 예시 기록의 역할별 digest를 확인한다.

### 팩 구성과 digest

- 지침은 공통 지침 `00-core.md`, 역할 지침 여섯, 영역 지침 `domains.md`, 언어 지침 여섯(`languages/cpp.md`·`go.md`·`java.md`·`javascript.md`·`python.md`·`rust.md`)으로 구성한다.
- 한 역할의 지침 텍스트는 공통, 역할, 영역, 고른 언어 지침 순으로 이어 붙인다.
- 언어 지침은 스냅샷 scope 안에 소스가 있는 생태계만 생태계 이름 순서로 붙는다. 판별은 분석기 팩의 공백 계획과 같은 `pack.InScope`다([분석기](ANALYZERS.md)). 소스 확장자로 세고, data·vendor 디렉터리는 빼며, build 파일만으로는 생태계가 들어오지 않는다. 지원 생태계가 없으면 언어 지침을 붙이지 않는다.
- 역할별 digest는 SHA-256이다. 입력은 `pack.yaml`과 실제로 고른 파일이고, UTF-8 상대 경로 오름차순으로 `경로 NUL 내용 NUL`을 이어 해시한다. 따라서 같은 역할도 생태계 조합마다 digest가 다르고, `pack.yaml`의 version·status가 바뀌면 모든 역할 digest가 바뀐다.
- 호출 기록마다 팩 id·version·역할 digest(`pack_sha256`)·고른 파일 목록(`pack_files`)이 남는다. 보고서는 실제 사용한 팩을 표시한다.
- digest는 run 생성 시 계산한다. 저장소가 제공한 digest를 믿지 않는다.
- 저장소 `.gitattributes`(`* text=auto eol=lf`)가 모든 checkout을 LF로 고정한다. CRLF로 바뀐 checkout은 지침 바이트가 달라져 digest와 요청 크기가 OS마다 달라진다.

### 지침 작성 규칙

- 지침 파일에는 평가·시험 사례의 내용을 쓰지 않는다. 사례 ID, 작업 ID, fixture 경로와 식별자, 특정 문서·재시도 횟수·버전 조합이 여기에 해당한다. 예시가 필요하면 사례 없는 규칙으로 쓴다.
- [`prompts/review/bundle_test.go`](../prompts/review/bundle_test.go)가 사례 ID·fixture 이름을 검사한다. 같은 뜻을 다른 말로 쓴 문장은 이 검사로 잡지 못하므로 지침 검토에서 확인한다.
- 언어 생태계마다 언어 지침이 있어야 한다(시험으로 고정). 의존성·타입·헤더가 없어 생긴 진단은 결함이 아니라 분석 공백으로 다룬다. 지침에 도구 규칙 ID를 쓰지 않는다.
- 지침 작성자는 보류 평가 결과와 보류 사례를 읽지 않는다. 범위는 [평가](EVALUATION.md)에 있다.

## 역할과 산출물

워커는 탐색과 정적 분석 뒤에 기본 역할 다섯을 실행한다. 선택한 문서 계약 후속 검토는 모듈별 검토 뒤에 온다. 모델에 전달하는 테스트 발췌는 스냅샷에 보존된 테스트 코드다. `with-tests`에서는 독립 조사와 정적 진단 해석 뒤에 테스트를 실행한다. 검증 입력의 테스트 발췌에 실제 케이스 위치가 포함되면 해당 줄과 통과·실패·건너뜀을 최대 16건 전달한다. 케이스 이름과 원시 로그는 모델에 전달하지 않는다. - 도구 진단 해석은 독립 조사와 별도 입력으로 수행하고 원시 메시지·규칙·위치를 보존한다. 도구의 실행 상태, finding 수, 심각도를 다시 말하지 않고, 진단이 없다는 사실을 깨끗한 코드로 서술하지 않는다.
- 출력 개수 한도: documents는 계약 6, 충돌 3, 질문 4, 지침성 문구 메모 3개까지. interpret는 가설 2, 한계 3개까지이고 합해서 하나 이상. investigate 후보는 줄 번호를 붙여 보낸 코드·테스트 원문이 32 KiB 이하이면 4개, 32 KiB마다 하나씩 늘어 출력 한도가 정한 상한(4~12개, [요청 크기](#요청-크기))까지이고 요청에 그 수를 적는다. 강점은 3개까지다. 문서 검토는 명확성·완전성·실행 가능성·일관성에 관한 근거 있는 판단을 4개까지, 전체 조사 역할은 고른 문서 계약과 코드의 대조를 6개까지 기록한다. 대조는 계약 순번과 그 문서 근거에 묶인다. 일치·부분 일치·불일치에는 해당 경로의 구현 코드 근거가 필요하고, 미확인은 근거 부족을 설명한다. 보고서에서 대조가 없는 수락 계약은 미확인으로 표시한다([문서 계약 대조](#문서-계약-대조)). 후보와 interpret 가설은 근거 ID를 6개까지, verify의 근거 목록은 8개, 조건·가정 목록은 4개까지 인용한다. 이 한도는 역할 계약 문자열에도 적는다.
- 문서 응답의 계약·질문·문서 품질 항목은 각각 서로 다른 근거 ID를 1~4개 인용한다. 지침성 문구 메모와 충돌의 각 편은 각각 1~3개다. 요청은 가장 직접적인 한 근거를 우선하도록 안내하고, 형식 복구 오류 코드에는 문제가 있는 근거 ID 필드 이름을 함께 표시한다.
- 문서 검토는 README·사용 안내·공개 인터페이스에서 사용자가 확인할 수 있는 동작을 우선 고른다. 하나의 계약이 한 조건과 관찰 가능한 결과를 설명하며, 지원 범위와 예외는 별도로 판정할 수 있을 때 각각 기록한다. 설계에서 읽은 기대에는 구현을 확인할 질문을 연결한다.
- 조사 역할은 사용자 진입점에서 결정적인 분기를 거쳐 결과가 전달되는 근거를 대조한다. 계약이 함수 자체의 동작으로 한정되면 그 함수의 구현을 대조한다. 확인하지 못한 호출 경로나 결과는 미확인으로 남긴다. 검토에서 읽은 테스트 단언은 해당 조건의 보조 근거다.
- 하위 역할은 수락된 결과만 받는다. 앞 역할이 생략·실패·사용 불가면 `upstream_<역할>_<상태>` 한계를 남긴다(예: `upstream_documents_skipped`).
- 모델 전송이 승인되지 않으면 모든 역할이 `skipped_policy`(`model_source_not_approved`)다.

### 검토 대상이 없는 역할

새 task 상태를 만들지 않는다. `skipped_policy`와 통제된 사유 코드를 함께 쓴다. 사유 코드는 task의 `reason`에 저장하고 화면은 코드별 문구로 표시한다.

| 사유 코드 | 의미 | 모델 검토 성공으로 셈 |
|---|---|---|
| `model_source_not_approved` | 소스의 모델 전송 미승인(정책 제외) | 아니오 |

필수 여부는 계획 시 정한다. 문서가 없어 생략한 문서 역할을 모델 검토 성공으로 세지 않는다. 필수 모델 작업이 실패했으면 도구 결과가 남아도 검토 전체를 완료로 올리지 않는다. 진행 단계 판정에서 이 생략을 어떻게 셈하는지는 [구조](ARCHITECTURE.md)에 있다.

## 검토 입력 선택

모든 발췌는 고정 스냅샷의 manifest 항목(크기·SHA-256)과 대조해 읽는다. 512 KiB를 넘는 파일, UTF-8이 아니거나 NUL을 포함한 파일, 민감값 패턴에 걸린 파일, 비밀값 선별이 보류한 파일은 발췌하지 않는다. 발췌는 원문의 줄 단위다. 근거 ID는 manifest digest, 스냅샷 상대 경로, blob SHA-256, 행 범위에서 결정된다(`record.ExcerptID`).

한도는 발췌 텍스트를 JSON으로 인코딩한 바이트로 센다(`encoding/json`은 `<`·`>`·`&`를 6바이트로 바꾼다). 상수는 [`inputs.go`](../internal/worker/review/inputs.go)에 있다.

### 종류 판별과 제외 디렉터리

- 일반 발췌에서 code·test·config·document 종류는 경로로 정한다. worker와 보고서 decoder가 같은 규칙([`record/source.go`](../internal/worker/review/record/source.go))을 쓴다. code는 분석기 팩의 `pack.SourceFiles`와 같은 소스 확장자다. test는 언어별 이름·디렉터리 관례, config는 고정 manifest 목록이다. 공개 API 페이지가 참조하는 Python docstring은 `document` 종류를 받고 별도 출처 경로를 기록한다.
- 테스트 경로: Go `*_test.go`. Python `test_*`·`*_test`·`conftest.py`. JS/TS `*.test.*`·`*.spec.*`. Rust `tests.rs`. C/C++ `test_*`·`*_test`·`*_tests`·`*_unittest`·`*-test`. Go가 아닌 언어는 `test`·`tests` 디렉터리 아래 파일도 테스트다(JS/TS는 `__tests__`도, Rust는 `tests`만).
- manifest(config): go.mod, pyproject.toml·setup.cfg, package.json·tsconfig.json, Cargo.toml, CMakeLists.txt, Maven·Gradle 빌드 선언. `compile_commands.json`은 생성 산출물이고 보통 생성한 머신의 절대 경로를 담으므로 config 후보가 아니다.
- Go가 아닌 파일은 분석기 팩의 data 디렉터리(숨김·testdata·vendor·node_modules, `anypack.DataDir`) 아래에 있으면 후보가 아니다. 어느 깊이든 `build`·`dist`·`target`·`coverage`·`htmlcov`·`site-packages`·`venv`·`__pycache__`·`third_party` 아래 파일도 뺀다. 같은 이름의 소스 디렉터리도 빠진다. 범위 안 소스가 이렇게 빠지면 `source_in_excluded_directories`를 남긴다.
- Go 파일은 이 제외 규칙을 받지 않는다(internal/build 같은 Go 패키지가 흔하다). Go 발췌는 vendor·testdata·`.`·`_`로 시작하는 디렉터리를 건너뛴다.
- 다른 생태계의 파일과 manifest는 그 생태계의 소스가 범위 안에 있을 때만 넣는다(`pack.InScope`). Go 저장소의 package.json·Cargo.toml처럼 build 파일만 있으면 config 발췌가 되지 않는다.
- 확장자 없는 스크립트와 생성 파일 이름(예: `.min.js`)은 판별하지 않는다.

### 코드 발췌(investigate)

- Go 파일은 가장 깊은 go.mod 디렉터리(모듈)로 묶는다. 다른 언어 파일은 같은 생태계 manifest가 있는 가장 깊은 디렉터리로 묶고, 없으면 `.`다.
- 묶음 안의 순서는 진입점, 소스, 테스트이고 같은 순위는 깊이와 경로 순이다.
- 진입점: Go `main.go`. Python `__main__`·`main`·`app`·`cli`·`manage`(`.py`). JS/TS `main`·`app`·`server`·`cli`(소스 확장자)와 `index`. `index`는 모듈 루트(가장 깊은 package.json·tsconfig.json 디렉터리)나 그 `src`에 있을 때만 진입점이다. Rust `main.rs`·`lib.rs`. C/C++ `main`(`.c`·`.cc`·`.cpp`·`.cxx`·`.c++`). 테스트 경로는 진입점이 아니다.
- 순회(round-robin): 각 순회에서 묶음마다 다음 파일 하나를 고른다. 묶음은 생태계 이름 순으로 돈다. 첫 순회가 범위 안의 모든 모듈과 언어를 지난 뒤에 어느 모듈도 두 번째 파일을 얻는다.
- 전체 조사에서는 수락된 문서 계약의 문장과 인용 원문의 관련 구절로 구현·테스트 위치를 찾는다. 명시된 파일 이름, 함수·명령·옵션처럼 코드에 등장하는 식별자, 사용자 오류 메시지에 쓰인 한국어 어휘를 함께 비교한다. 여러 계약에 반복되는 일반 어휘의 가중치는 낮춘다. 코드 경로는 계약의 적용 범위 안에서만 연결한다.
- 두 계약 이상에 범위가 맞는 구현 단서를 찾으면 기존 전체 조사 요청 안에서 계약마다 발췌 묶음 하나를 우선 배정한다. 문서 원문과 계약 양쪽의 이름을 구현에서 확인하거나 구조적으로 연결된 소스 위치를 쓴다. 서로 다른 계약이 같은 발췌를 사용하면 원문은 한 번만 보내고 `scope.contract_anchors`의 계약 번호별로 같은 근거 ID를 연결한다. 같은 파일의 떨어진 구현 창도 파일별 줄·바이트 한도 안에서 사용할 수 있다. 묶음과 일반 발췌는 기존 요청 크기와 발췌 상한을 공유한다. 묶음이 둘 미만이거나 요청에 들어가지 않으면 기존 선별 순서를 사용한다. 이 단서는 조사 입력에만 있으며, 보고서에는 검증된 모델 대조와 그 인용 근거를 저장한다. 모델 호출 상한과 검토 기록 형식은 유지한다.
- 인용 원문이 인라인 코드로 표시한 필드 이름이나 점 경로가 수락한 계약에도 대소문자까지 같은 온전한 이름으로 나오면 Go 구조체의 명시적인 `json` 태그를 따라 값을 만드는 구현을 찾는다. 계약의 백틱 생략, 이름에 붙은 한국어 조사나 구두점을 허용한다. 동일한 패키지와 검토 범위에서 확인한 구조체 리터럴 또는 반환할 값의 필드 대입을 발췌한다. 필드 값을 만드는 직접 호출의 전체 함수가 한 창 또는 두 창에 들어가거나 같은 패키지의 리터럴 상수가 확인되면 정의도 보낸다. 반환과 바깥쪽 태그는 남은 발췌 한도 안에서 함께 보일 수 있다. 값을 만드는 위치를 찾지 못한 단일 필드에는 그 필드를 읽고 오류를 반환하는 검사 분기를 보낼 수 있다. 검토 범위 안의 파일을 빠짐없이 읽을 수 없는 패키지, 여러 구조체나 빌드 조건의 정의가 겹치는 경우, 사용자 정의 직렬화는 일반 선별을 따른다. 경로 탐색은 기존 읽기 예산과 비밀값 선별을 공유한다. 발췌는 값이 생성·변경되는 위치이며, 저장과 전송의 전체 동작을 확인하려면 그 경로의 구현 근거가 필요하다.
- Python docstring에서 채택한 계약은 인용된 선언의 docstring 뒤에서 결과를 반환하거나 오류를 내는 구현 줄을 우선 찾는다. 이름이 대응하는 pytest 파일의 단순한 숫자 입력 행에서 동일한 입력과 옵션에 따라 다른 기대값이 나오고 한 창에 담기면 그 행을 함께 검토한다. 테스트 매개변수는 정적 기대값이다. 문서 일치·부분 일치·불일치 판정에는 인용한 docstring과 겹치지 않는 구현 근거가 하나 이상 필요하다.
- Java의 `src/main/java`에서 공개 최상위 타입의 공개 메서드에 직접 붙은 Javadoc을 문서로 읽는다. 이 Javadoc만 있는 프로젝트에도 문서 검토를 계획한다. 일반 문서와 같은 읽기·입력 예산에서 원문 주석을 최대 네 건 보내고 경로·줄·blob 해시를 기록한다. 선언의 서명은 입력에 따로 표시해 오버로드를 구분한다. 테스트·생성 경로, 일반 주석, 문자열 안의 주석 모양, private 메서드, 메서드와 결합 여부가 불분명한 주석은 제외한다. PR은 변경된 파일에서만 골라 읽는다. 조사에서 인용된 주석과 같은 선언의 구현을 확인할 수 있으면 별도 코드 발췌를 보낸다. 인용한 주석과 겹치는 발췌는 그 계약의 구현 근거로 쓸 수 없다. 인용된 메서드 안에서 같은 클래스의 구현을 직접 호출하고 결합을 확인할 수 있으면 그 본문도 별도 근거로 제공한다. 긴 본문은 진입·종료 부근에서 읽은 범위를 남긴다.
- 수락된 계약과 인용 문단에 합산과 곱셈 또는 나눗셈이 함께 나오면 Python 계산을 찾는다. 같은 적용 범위의 함수 설명에서 계산 대상을 확인하거나 문서가 함수명을 명시해야 한다. 고유하게 확인한 함수가 해당 산술이 들어간 `sum()` 결과를 반환하면, 반환식과 함께 발췌에 들어가는 앞쪽 준비문과 포함 조건을 우선 보낸다. 함수나 합산 이름의 바인딩이 모호하면 일반 발췌를 사용한다. 기존 읽기 한도 안에서 Python 주요 구현 파일을 먼저 확인하며, 전체 조사에서 이 계산 발췌는 최대 하나다.
- 계약 범위에 `app`·`src`·`lib` 등 프로젝트 소스가 함께 있으면 릴리스·배포 등에 쓰는 보조 스크립트와 같은 이름의 테스트는 계약 어휘 점수를 낮춘다. 계약에서 해당 파일이나 운영 작업을 직접 지칭하면 일반 점수를 적용한다. 보조 스크립트도 일반 순회의 대상이다.
- 구현과 벤치마크가 공존하면 기본 동작 계약에서 벤치마크 경로의 어휘 점수를 낮추고, 성능 계약과 명시된 경로에는 일반 점수를 적용한다. JavaScript·TypeScript 구현이 있는 범위에서는 런타임 계약에 대한 타입 선언 파일의 점수도 낮춘다. 타입 계약·명시된 경로·타입 선언만 있는 범위에는 일반 점수를 적용한다. `test.js`·`test.ts`·`*.test-d.ts`는 테스트로 분류한다.
- 경로를 먼저 대조하고 고정 스냅샷의 적격 소스·테스트를 최대 192개·4 MiB까지 읽는다. 일반 우선 탐색에서 생성 헤더·부차 경로·minified JavaScript 파일을 제외한다. PR은 변경 파일 안에서만 이 우선 탐색을 한다. 일반 계약의 구현·호출부·테스트는 합쳐서 최대 4개, 각 24줄·1,500바이트 발췌로 보낸다. 발췌를 함수·분기·실행문 등 관련 줄에서 시작하고, 바로 앞에 검증 조건이 있으면 함께 보낸다. 보고서는 모델이 인용한 경우 같은 스냅샷 위치에 코드 발췌를 붙인다.
- PR 이외의 전체 조사에서 인용한 예제의 Go 공개 함수 이름이 수락한 계약에도 정확히 있으면 문서 적용 디렉터리의 Go 패키지를 확인한다. 같은 디렉터리의 비테스트 Go 파일을 모두 검사할 수 있을 때 AST로 생성 래퍼의 인자 전달, 반환값 또는 일부 결과를 버린 뒤의 반환, 한 곳에서 선언한 같은 패키지 함수를 확인한다. 중간 수기 함수의 직접 전달 호출을 한 번 더 따라갈 수 있다. 예제의 리터럴을 전달받은 매개변수로 분기하는 `switch`나 반환 조건을 포함한 구현 창을 먼저 고른다. 탐색은 기존 읽기 한도를 공유하며 한 패키지에 최대 32개·512 KiB를 쓴다. 범위와 비밀값 검사를 적용하고 부차 디렉터리를 건너뛴다. 빌드 조건이 있는 정의, 모호한 정의, 메서드, 다른 패키지는 이 경로에서 제외한다.
- 위 Go 경로는 전체 조사에서 최대 두 개, 발췌는 합계 다섯 개까지다. 생성 파일은 확인한 래퍼의 줄만 발췌하며 장부에는 `generated_file`로 분류하고 고유 파일을 한 번 센다. 발췌 하나를 우선 배정할 관련 테스트가 있으면 함께 보낸다. 같은 파일의 여러 창은 50줄·2,400바이트 한도를 공유하고 전체 조사 요청 한도를 적용한다. 실제 남은 창 사이의 직접 호출을 `scope.direct_calls`로 전달한다. 우선 발췌로 밀린 적격 파일은 범위 계획의 기존 배정 규칙을 따른다.
- 수락한 계약과 인용 원문에 같은 Go CLI 명령과 첫 인자가 나오면, 범위 안에서 유일한 `cmd/<명령>/`의 `package main`을 찾는다. `os.Args[1]` 또는 `os.Args[1:]`를 전달한 인자의 첫 값과 같은 문자열을 비교하는 분기와 그 구현을 우선 발췌한다. 최대 두 번의 직접 인자 전달을 따라가며 같은 패키지의 정의와 스냅샷 줄을 사용한다. 이렇게 찾은 경로에는 기본 발췌 한도를 적용하고 명시하지 않은 QA·벤치마크 스크립트 대신 제품 구현과 관련 테스트를 우선한다. 모호한 분기나 정의, 생성 소스의 경유, 범위 밖 파일, PR에는 이 연결을 만들지 않으며 일반 발췌를 사용한다. 이 연결은 문서 동작을 대조할 위치를 제공한다.
- `cmd/<명령>/README`에서 해당 명령의 단독 실행이나 옵션 실행을 인용한 계약에는 같은 디렉터리의 `main`을 우선 발췌할 수 있다. `main`이 직접 호출하는 같은 패키지의 구현이 하나이고 두 함수의 전체 줄이 발췌 한도에 맞으면 두 함수를 함께 보낸다. 여러 곳에서 같은 구현을 부르면 한 구현으로 센다. 후보가 여럿이거나 구현 창이 한도를 넘으면 발췌 가능한 `main`만 보낸다.
- C/C++의 `#if`·`#ifdef`·`#ifndef`·`#elif`가 계약의 옵션과 어휘로 연결되고 같은 분기 실행문을 발췌에 넣을 수 있으면 전처리 조건부터 보낸다. 조건과 실행문을 함께 검토해 해당 설정이 코드에 적용되는 경로를 확인한다.
- 수락한 계약과 인용 원문에 같은 C 함수 이름이 있고 읽기 한도 내 해당 범위의 `.c` 파일에서 함수의 정의가 하나 확인되면 정의와 본문을 먼저 발췌한다. 가시성 매크로를 붙인 일반 C 선언을 읽고 주석·전처리 지시문·함수 원형·`static` 정의·호출문을 건너뛴다. 각 창은 24줄·1,500바이트로 최대 두 개이며 전체 조사 발췌 한도를 공유한다. 같은 파일에 계약과 연결된 전처리 조건을 먼저 골랐으면 그 창을 보존한다. 모호하거나 본문이 한도에 들어가지 않는 정의는 일반 탐색을 따르고 빌드 변형 및 호출 관계는 별도 근거로 판단한다.
- JavaScript·TypeScript 계약이 멤버 접근이나 호출을 이름으로 지칭하면 메서드 본문이나 `Object.defineProperties`의 해당 속성 정의를 찾는다. 테스트가 상대 경로로 같은 모듈의 팩터리나 생성자를 가져오고 그 객체로 같은 동작을 검사할 때, 본문과 단언 한 쌍을 앞의 네 발췌 안에 우선 배정한다. 독립된 호출 직후의 상태 단언을 접근자 읽기나 단언 내부 호출보다 먼저 고른다. 모호한 구현 경로는 일반 탐색으로 넘긴다.
- 이 쌍의 정확한 두 발췌가 요청에 남으면 `scope.member_test`에 멤버 이름과 구현·테스트 근거 ID를 넣는다. 모델은 연결을 읽을 위치로 사용하며 문서 대조의 판정은 모델이 인용한 발췌의 구현 조건과 테스트 단언을 검증해 기록한다. 테스트 실행 여부는 실행 근거로 판단한다.
- JS/TS 계약과 인용 원문에 명시된 옵션이나 공개 API가 있으면, 같은 범위에서 ESM으로 공개한 함수와 리터럴 기본값, 옵션이 가르는 반환·오류 경로를 우선 발췌한다. 상대 import로 같은 함수를 부르고 나머지 리터럴 입력이 같은 테스트를 찾아 기본값과 반대 조건을 검사하는 단언을 함께 보낸다. 비동기 함수는 기다린 결과나 명시적인 Promise 결과를 확인한다. 바인딩이 여러 개이거나 콜백 전달만 보이면 이 연결을 만들지 않는다. 테스트는 스냅샷의 코드 근거다.
- 계약에 관련된 출발 위치에서 [파일 사이의 호출 근거](#파일-사이의-호출-근거)를 찾아 호출문과 실제 정의를 함께 고른다. 읽기는 기존 탐색 한도를 공유한다. 같은 시도에서 스냅샷 경로 목록과 검증한 blob의 자격증명 양식 검사 결과를 다시 쓴다. 각 역할은 읽는 바이트의 해시와 현재 비밀값 선별 결과를 확인하고 해당 역할의 탐색 한도를 적용한다.
- 일반 발췌에서 이미 두 위치를 볼 수 있으면 일반 순회를 따른다. 우선 선택한 두 발췌가 실제 요청에 남으면 `scope.direct_calls`에 발췌 ID 두 개와 함수 이름을 넣는다. 모델은 이 연결을 위치 탐색에 쓰며, 문서 계약 판단과 보고서 인용은 각 발췌의 입력 조건·구현 결과·테스트 단언에 근거한다.
- 남은 자리는 일반 순회 순서의 파일을 [검토 단위](#검토-단위)로 채운다. 발췌 수와 줄 번호를 붙인 코드·테스트 원문 바이트의 합계는 요청 크기에서 정한다(기본 64개·213,952바이트, 최소 예산에서 8개·12,000바이트). 남은 예산이 128바이트 미만이면 멈춘다. 파일 일부만 발췌하면 `excerpt_only`, 고르지 못한 후보 파일이 있으면 `files_outside_review_context`를 남긴다. 위 선택기들의 창별 줄·바이트 한도는 그대로다. 토큰 일치는 검토할 위치를 고르는 기준이다. 계약과 구현의 대조는 모델이 제공된 근거를 인용해 판정한다.
- 전체 조사에서 이름이나 경로가 인용 문서와 연결된 짧은 구현의 일부를 먼저 골랐으면 이미 검증한 원문으로 앞쪽의 관련 분기와 반환도 함께 보낼 수 있다. 원문 전체는 50줄·2,400바이트 이내이며 기존 발췌를 모두 둔 상태로 전체 코드와 요청 한도에 들어가야 한다. 이 파일을 참조하는 직접 호출·테스트 연결이나 다른 발췌가 있으면 기존 줄 범위를 유지한다. 원문 전체를 보낼 때는 그 줄 범위로 근거 ID와 실제 노출량을 기록한다.
- 수락한 계약과 같은 적용 범위의 인용 원문에 Python 공개 함수 호출이 있고 선택한 구현 창이 그 함수의 본문에 속하면, 같은 파일의 선언 한 곳을 별도 근거로 보낼 수 있다. 이름과 스코프를 확인하고 여러 줄 매개변수·기본값·반환 형식을 원문 그대로 보낸다. 중복 선언·가려진 이름·동적 바인딩·데코레이터 때문에 함수 관계를 확인할 수 없으면 추가하지 않는다. 기존 구현과 테스트를 먼저 유지하고 같은 파일·전체 발췌 한도를 공유한다. 두 위치는 코드 근거이며 대조 판정은 별도로 기록한다.
- Go 설정의 기본값을 명시한 계약과 인용 원문에 같은 설정 이름이 있으면, 그 이름이 쓰인 구조체 초기화나 생략 시 적용되는 반환·대입 분기의 원문을 먼저 선택한다. 스냅샷 읽기와 적용 범위는 기존 문서 근거 검색 한도를 쓴다. 구조체 필드 선언, 주석, 유효성 검사 반환을 기본 동작 근거로 고르지 않는다. 선택한 발췌는 대조에 쓰이며 문서 약속의 충족 여부는 모델이 검토한다.
- 계약과 인용 원문에 같은 Go HTTP 쿼리 옵션 이름이 있으면, `url.Values.Get` 결과를 나누는 `switch`의 불리언 초기값·변경, 같은 지역 값을 넘기는 직접 호출과 그 매개변수에 따른 반환을 함께 찾는다. 긴 결과 변환은 선택에 따른 반환과 같은 결과 변수에 대입한 JSON 필드, 마지막 반환과 해당 필드의 태그를 각각 발췌한다. 호출 결과를 변수로 받으면 그 값을 반환하거나, 옵션의 분기에서 직렬화한 바이트를 응답에 쓰는 실행문까지 확인한다. 값을 바꾸거나 버리는 경로가 있으면 이 연결을 생략한다. 전체 조사에서 이 연결은 최대 한 건이며 기존 탐색·발췌 한도를 공유한다. 응답에 쓰는 줄까지 연결한 경우 앞쪽 처리기 요약보다 그 줄을 먼저 보존한다. 범위 안의 `go.mod`와 고유한 함수 정의를 확인하고, 가려지거나 다시 대입된 값, 모호한 등록, 제외·보류 파일 또는 한도를 벗어나면 일반 발췌를 사용한다. 선택한 줄은 모델이 문서와 대조할 소스 근거다.
- 위 연결은 지역 변수와 확인한 직접 함수 호출을 따르는 정적 탐색이다. 함수값이나 실행 시 정하는 전달 경로에는 일반 발췌를 쓴다. 여러 조건이나 저장·게시처럼 다른 경로를 포함한 약속은 각 부분의 근거가 필요하다. 확인한 부분 밖에 판단에 필요한 구현이 남으면 모델은 미확인 상태와 그 이유를 기록한다.
- C 문서가 함수군의 접미사를 코드로 표시한 경우 같은 안내의 C 코드 블록에서 실제 호출 이름을 찾는다. 최대 두 문서, 문서당 64 KiB를 다시 읽는다. 같은 소스에 나란히 정의된 기본 함수와 변형 함수가 동일한 형태의 인자를 같은 내부 함수로 넘기고 한 위치의 리터럴만 바꿀 때, 두 래퍼와 해당 인자의 `if/else` 분기를 두 발췌로 함께 보낼 수 있다. 선언 중복, 조건부 정의, 인자를 먼저 바꾸는 코드, 범위·발췌 한도는 일반 코드 선택으로 돌린다. 두 발췌는 대조에 사용할 소스 단서다.
- 모든 적격 파일에 발췌가 있고 예산이 남으면 다른 계약과 직접 어휘가 맞는 구현 창을 최대 두 개 더 붙인다. 창마다 최대 13줄을 쓰며 기존 창과 겹치지 않는 줄 범위를 인용한다. 한 파일의 합계는 50줄·2,400바이트 이내다. 범위 장부에서 파일은 한 번 세고 실제 전달한 창들의 줄과 바이트를 합산한다.
- 발췌가 있는 모듈 디렉터리는 `modules`(최대 32개)에 들어간다.
- Python docstring 또는 rustdoc을 인용한 계약에는 같은 선언에서 실행문을 고른다. Python import·별칭 또는 Rust의 동일 소스 `super::` 호출·통합 시험의 crate import가 해당 선언으로 이어지고, 테스트 단언 안에서 실제 호출을 확인하면 단언 줄을 함께 선택한다. 파일 안 Rust 단위 시험은 기존 코드 파일 분류를 유지하며 별도 위치에 있는 정적 단언을 발췌한다. Rust 계약은 원본 rustdoc ID와 같은 선언의 구현 ID를 함께 전달한다. 여러 함수를 인용하면 함수마다 구현을 먼저 배정한 뒤 단언을 보낸다. 해당 함수의 구현이 범위나 요청 예산에 들지 않으면 `rust_api_implementation_outside_review_input`을 남긴다. 실제 테스트 실행은 `with-tests` 실행 기록으로 확인한다.
- 전체 investigate는 수락한 문서 계약·질문과 함께 관련 코드·테스트의 위치 후보를 최대 12개 보낼 수 있다. 확정한 조사 입력과 대조해 미제공 실행문이 포함된 코드 창을 고른다. 계약과 인용 원문 양쪽에 있는 정확한 식별자와 관련 분기를 우선하고, 겹치지 않는 구현 위치를 추가할 수 있다. 확인할 수 있는 구현 단서가 여러 파일의 일반 함수 위치에 그치면 후보에서 뺀다. 적격 코드가 있는 계약에는 관련 테스트 위치도 보낸다. JavaScript·TypeScript 테스트에서 확인한 단언을 구조 후보로 사용하며, 확인할 수 없는 구문은 일반 함수·호출 위치를 사용한다.
- 위치 선별은 앞서 읽은 계약 관련 소스 발췌용 파일을 재사용한다. 별도 읽기 한도는 코드와 테스트 각각 16개·256 KiB이며, 같은 디렉터리의 다른 파일보다 아직 방문하지 않은 곳을 먼저 읽는다. 범위와 비밀값 선별을 따르며 PR은 변경 파일만 대상으로 삼는다. 메시지 상한에 걸리면 기존 발췌를 유지하고 위치부터 줄인다. 위치는 경로·줄 범위·실제 이름을 제공하며 코드 원문 전달·근거 인용으로 집계하지 않는다.
- 위치 후보를 보낸 요청은 `L1`부터 번호를 붙인다. 모델은 같은 응답의 `contract_probe`에 `unknown`으로 대조한 계약 하나와 해당 범위의 제공된 위치 ID 1~3개를 고르거나 `null`을 낸다. 워커는 코드 위치를 하나 이상 고른 선택을 수락한다. 추가 검색은 입력에서 확인된 대소문자 구분 식별자 최대 3개를 정확히 찾는다. 검증한 위치는 스냅샷에 묶인 원래 ID·해시·줄 범위로 저장한다. 적격 위치가 있는 미확인 대조의 응답이 수락되면 선택 누락·`null`과 검증 실패를 검토 원시 기록에서만 구분하고 일반 후보와 대조를 유지한다. [위치 선택 기록 예시](../examples/review/investigate-probe.json)
- 범위 안 소스가 모두 제외 디렉터리 아래 있거나 발췌가 하나도 없으면 investigate는 `failed`(`review_input_unavailable`)다.

- 수락된 미확인 대조의 이유가 선택한 위치를 후속 확인 지점으로 명시하면 요청 별칭을 검증한 파일과 줄 범위로 바꿔 기록한다. 보고서는 그 위치를 앞으로 확인할 곳으로 읽는다.

### 검토 단위

코드·테스트 발췌의 기본 단위는 파일 전체다([`units.go`](../internal/worker/review/units.go), [`corpus_units.go`](../internal/worker/review/corpus_units.go)). 모델은 한 모듈의 파일과 선언을 함께 읽고 파일 사이의 호출을 따라간다.

- 단위 크기는 줄 번호를 붙인 원문의 JSON 바이트로 잰다. 상한은 [요청 크기](#요청-크기)에서 정한다(기본 42,790바이트, 최소 예산 2,400바이트).
- 한 단위에 들어가는 파일은 통째로 보낸다. 더 큰 파일은 최상위 선언의 시작(바로 위 주석·데코레이터·attribute 포함)에서 연속한 단위로 나누고, 단위마다 선언을 들어가는 만큼 담는다. Go는 `go/parser`로 경계를 찾고 파싱하지 못하면 중괄호 판별로 돌아간다. C/C++·Java·Kotlin·Scala·C#·Rust·Swift·JavaScript·TypeScript는 문자열·문자·주석을 건너뛰는 중괄호 깊이, Python은 들여쓰기 없는 문장과 그 위의 주석·데코레이터로 판별한다. JavaScript·TypeScript는 피연산자 자리의 `/`를 정규식 리터럴로 보고 건너뛴다. JSX의 닫는 태그(`</b>`)와 스스로 닫는 태그(`/>`)는 정규식이 아니다. C/C++는 전처리 줄의 중괄호를 세지 않고, `#if`/`#else`로 갈린 대안 분기는 첫 분기를 지난 깊이로 이어 간다. CRLF 파일은 줄 끝의 `\r`을 무시해 LF 파일과 같은 경계에서 나뉜다. Python의 CRLF 빈 줄도 문장이 아니다. 한 선언이 단위보다 크면 그 안의 멤버 경계에서 자르고, 경계가 없으면 줄에서 자른다. 외부 파서·cgo는 쓰지 않는다. 판별기는 구문 분석기가 아니므로 비정형 코드에서는 경계가 덜 정확할 수 있다. 그래도 단위는 항상 연속한 줄이고 근거 ID는 실제 줄 범위로 계산한다.
- 파일 첫 줄에서 시작하지 않는 단위는 그 파일의 머리(package 절·import·include·use 등, 최대 80줄)와 함께 간다. 여러 줄에 걸친 import는 괄호가 닫힐 때까지, `#define`은 줄 끝 `\`가 이어지는 동안 머리에 든다. overview는 파일의 단위를 순서대로 보내므로 첫 단위가 머리를 담는다. slice는 머리 줄을 `origin: header` 발췌로 붙이고 그 바이트를 slot 계획에 포함한다. 같은 slot이 그 파일의 첫 단위도 보내면 머리를 따로 붙이지 않는다. 첫 단위가 머리를 담고, 머리와 정확히 같은 단위이면 같은 근거 ID가 두 번 갈 것이기 때문이다.
- overview 순서: 문서 계약·호출 근거·진단 등 선택기 발췌를 먼저 두고, 남은 예산을 모듈 순회 순서의 파일 단위로 채운다. 선택기가 보여 주지 않은 파일이 먼저다. 모든 파일의 첫 단위가 어느 파일의 두 번째 단위보다 먼저 들어간다. 파일의 단위는 순서대로 들어가고 들어가지 않는 첫 단위에서 그 파일을 멈춘다. 요청 안에서는 선택기 발췌 뒤에 모듈·디렉터리·경로·시작 줄 순으로 나열해 관련 코드가 함께 간다.
- 선택기 발췌가 같은 요청의 다른 발췌 안에 있으면 원문을 다시 보내지 않는다. 요청에서 그 발췌는 원문 없이 `within`에 감싸는 발췌의 근거 ID를 가진 참조다. 근거 ID, 출처 표시, 검토 기록은 바뀌지 않고 인용도 그대로 받는다.
- slice도 같은 단위를 쓴다. `review.scope`는 overview가 보내지 않은 줄을 단위로 나눠 slot에 배정한다. 배정은 overview처럼 너비 우선이다. 모든 파일이 앞 단위를 받기 전에는 어느 파일도 다음 단위를 받지 않는다. 한 파일의 단위는 순서대로 가고 각 단위는 파일 머리와 함께 간다. 범위 산출물의 `limits`는 그 노드의 요청 크기에서 정한 값이고 `max_file_lines`는 `max_file_bytes`와 같다(단위는 바이트로만 제한한다). slot 수와 작업 키는 요청 크기와 무관하게 manifest와 범위로 정한다(A37).

### 문서 발췌(documents)

- 대상은 탐색 산출물에서 `selected` 상태인 안내 문서다. 문서 수나 발췌 크기 상한 때문에 모두 넣기 어려우면 [문서 탐색](ARCHITECTURE.md#문서-탐색)과 같은 순위로 대표 README, 제품 안내와 지역 문서를 고른다. Markdown 링크는 비밀값 검사에 통과한 대표 README 원문과 이번 검토에 쓸 수 있는 후보만 대상으로 삼는다. 모두 넣을 수 있는 경우 에이전트 지침, README, CONTRIBUTING, 설계 문서 순이고 같은 분류는 얕은 경로가 먼저다.
- 제목과 한 개의 리터럴 `::: package.module` 또는 `::: package.module.object`만 있는 Markdown API 페이지는 최대 두 개까지 원래 발췌 자리에서 Python docstring을 전달한다. 페이지 적용 디렉터리와 그 아래 `src/`의 `.py`·`__init__.py`를 고정 스냅샷에서 찾는다. 한 경로로 정해지고 범위·비밀값 검사를 통과할 때만 모듈 또는 공개 선언의 첫 문자열에서 옵션·예제·반환 설명을 우선 고른다. 파이썬과 문서 생성기를 실행하지 않는다. 문서 생성 옵션·가져오기로 다시 공개한 이름·동적 객체 해석은 처리 범위 밖이다. 발췌 한도는 다른 문서와 같다.
- 선택된 reStructuredText 안내의 최상위 `autofunction`·`automethod` 지시문에서 완전한 이름이나 `currentmodule`이 한정한 이름을 읽는다. Markdown 코드 블록은 한 리터럴 Python `from … import …` 바인딩이 실제 호출된 경우를 읽는다. 모듈에 선언이 직접 있거나 단순 재공개를 따라 같은 스냅샷의 공개 선언 한 곳으로 이어지면 원본 안내와 함께 docstring을 보낸다. 해당 문서의 첫 발췌 뒤에 있는 지시문도 64 KiB 이내에서 찾는다. 와일드카드 가져오기, 이름 재정의, 런타임 문서 생성과 import hook은 해석하지 않는다.
- Rust Markdown의 `rust`·`rs` 코드 블록에서 호출에 쓰인 crate 한정 이름이나 `use` 바인딩을 읽는다. 문서 적용 디렉터리의 `Cargo.toml`과 기본 `src/lib.rs`에서 공개 함수까지 `mod`와 명시적 `pub use`를 따라가며, 바로 붙은 rustdoc을 원본 안내와 함께 보낸다. 경로가 겹치는 모듈, 조건부 선언, 대체 소스 루트, build script, 매크로를 거친 선언은 연결에서 빠진다. crate README에 이름이 있는 호출 예제가 없으면 같은 crate의 기본 라이브러리 진입점에서 명시적 `pub use`를 최대 24개까지 따라가 공개 함수에 붙은 rustdoc을 고른다. 재공개나 발췌가 예산을 넘으면 `rust_public_api_partially_sampled`를 기록하고 실제로 읽은 줄만 근거로 남긴다.
- Python docstring과 rustdoc의 `path`·해시·줄 범위는 실제 소스 파일을, `directive_path`는 문서 적용 범위를 정하는 원래 안내를 가리킨다. 기존 문서 수·줄·바이트 예산 안에서 소스 문서를 최대 두 건 고르고, 별도 소스 탐색은 32개 파일과 512 KiB를 공유한다. 범위 밖·제외·보류·생성 파일은 새 연결에 사용하지 않는다. PR에서 새로 연결하는 소스 근거는 변경 파일에 한정한다.
- `docs/units.md`의 `::: counters.units`가 `src/counters/units.py`로 연결되면 문서 근거의 `path`는 `src/counters/units.py`, `directive_path`는 `docs/units.md`다.
- Markdown·MDX 안내에 리터럴 npm 패키지 이름을 쓰는 `import` 또는 `require`와 그 바인딩을 호출하는 예제가 함께 있으면 워커가 호출의 패키지 범위를 찾는다. 실제 JS/TS 코드 블록의 짧은 호출이나 인접한 인라인 코드의 호출을 읽는다. 고정 스냅샷의 검증된 `package.json`에 해당 이름이 하나이고, 이번 분석 범위 안에 한 런타임 진입점이 있을 때만 참조를 만든다. 외부 패키지는 참조하지 않는다. 바인딩을 가리거나 변경할 가능성, 여러 로컬 패키지, 모호한 진입점, 생성 파일 또는 비밀값 보류 파일이 있으면 연결을 생략한다. 패키지나 예제를 실행하지 않는다.
- `input.documents[]`의 `package_reference`는 해당 발췌의 `applies_to`와 별도로 그 호출의 범위를 담는다. 호출 이름을 명시한 계약이나 질문이 예제를 인용하면 같은 파일·blob에서 예제 바로 앞이나 뒤에 이어진 설명도 함께 인용할 수 있다. 충돌·지역 지침은 기존 디렉터리 범위를 따른다. 앞 발췌의 끝에서 검증 가능한 짧은 코드 블록이 끊기면 기존 상한과 여유 슬롯 안에서 전체 예제를 별도로 보낸다. 요청 예산은 검색 문서 목록보다 해당 예제를 우선 보존한다. 조사 역할은 진입점과 호출 이름을 범위 안 코드 탐색에 활용하며 실제로 보낸 구현 발췌만 대조 근거가 된다.

`site/docs/usage.md`에서 `import { format } from '@sample/price'`와 `format(1250)`을 읽은 요청의 참조 예시다. 이 문서의 `applies_to`는 `site`이고, 이 호출에 관한 계약은 `packages/price`에 적용할 수 있다.

```json
{
  "package_reference": {
    "name": "@sample/price",
    "callable": "format",
    "scope": "packages/price",
    "entry_path": "packages/price/src/index.ts"
  }
}
```

- 발췌는 각 40줄·2,000바이트, 총 8개·10,000바이트까지다. 여러 문서가 자리를 두고 경쟁하면 대표 README와 제품 요구사항, 주제별 안내를 고른다. 긴 제품 안내에서는 사용자 흐름·역할·기능 요구처럼 제목과 본문이 함께 있는 뒤쪽 절을 대표 발췌로 고를 수 있다. 대표 README의 도입부와 가져오기·호출 예제를 담은 발췌는 보존한다. 제품 본문이 더 있으면 부차 경로의 미연결 문서나 일반 안내보다 한 구간을 먼저 보낸다. 대표 README가 연결한 예제와 부차 경로에만 있는 안내도 검토 대상이다. 여유가 생기면 README 또는 사용 안내의 뒤쪽 절에서 API·사용법·옵션·예제 등 제목과 조건·반환·오류 설명을 추가한다. 설치·목차·후원·변경 이력 등은 추가 위치 탐색에서 제외한다. 두 발췌는 같은 스냅샷 파일의 독립적인 줄 범위를 인용한다.
- PR 이외의 전체 실행에서 발췌 상한과 경쟁하는 대표 README는 도입부 다음에 제품 동작의 조건·계산·제약이 담긴 절이나 문단을 두 곳까지 보낸다. 이미 보낸 줄을 건너뛰고, 창의 끝에서 본문이 빠진 제목은 제외한다. 빌드·기술 스택·문서 목록은 이 두 자리를 고르는 기준에서만 낮게 보고 일반 발췌의 후보로 남긴다. 경로 지정 실행과 PR은 기존 문서 선택과 범위를 따른다.
- 긴 대표 README와 연결되지 않은 하위 테스트 자료가 경쟁하면 제품 안내·링크된 문서·테스트 디렉터리의 대표 안내를 먼저 보존한다. 기존 발췌에서 떨어진 제목의 완결된 문단이나 짧은 예제를 최대 두 구간 추가한다. 각 구간은 16줄·800바이트로 제한하고 전체 문서 발췌 한도를 공유한다. 앞서 보낸 절에서 떨어진 위치를 먼저 고르며 제목이나 끝나지 않은 코드 블록만 있는 구간은 건너뛴다.
- 뒤쪽 절에 여러 API 멤버 제목이 들어 있고 발췌 개수에 여유가 있으면 같은 줄 범위를 제목 경계에서 나눈다. 나눈 발췌의 합계는 원래 선택한 절과 같으며 각 발췌에 별도의 근거 ID를 부여한다. 모델이 해당 멤버의 발췌를 인용하면 보고서가 그 제목 주변을 보여준다.
- 기존 발췌를 모두 둔 뒤에도 예산이 남으면 대표 README부터 각 사용 안내의 빠진 본문을 한 구간씩 돌아가며 추가한다. 제목이 없거나 인식되지 않은 절도 본문을 담으며, 이미 선택한 범위와 운영 섹션을 피하고 원래 줄 경계에서 자른다. 발췌 개수와 바이트 합계는 같은 요청 상한을 따른다. 보고서는 요청에 실린 줄을 근거로 연결한다.
- Markdown 목록은 같은 파일의 인접 발췌를 합쳐서 확인한다. 요청 한도에 맞춘 뒤 목록 일부가 빠진 발췌에는 `incomplete_list`를 붙인다. 모델은 보이는 항목을 근거로 쓰고 전체 목록의 구성이나 실행 순서를 단정하지 않는다.
- 탐색의 로컬 읽기 범위는 [문서 탐색](ARCHITECTURE.md#문서-탐색)에 기록한다. 모델 검토의 근거는 요청에 실제로 포함된 발췌다. 예산 때문에 문서가 빠지면 `documents_outside_review_input`, 문서 일부만 보내면 `document_excerpt_only`를 남긴다.
- 읽지 않은 안내 문서(최대 16개), 모듈별 문서 연결과 겹침 묶음(각 최대 32·16개, 목록당 8개)을 함께 준다. 줄이면 `document_lists_shortened`다.
- 발췌와 부가 목록을 함께 보낼 수 있는지 먼저 확인한다. 요청 상한에 닿으면 읽지 않은 문서·모듈 연결·겹침 묶음을 먼저 줄여 문서 원문을 보존한다. 목록을 모두 덜어 내도 상한에 닿으면 뒤쪽 발췌부터 줄인다. 요청과 검토 기록에 `document_lists_shortened`를 남기고 탐색 산출물은 유지한다.
- 문서 요청의 `evidence_id`는 전달한 발췌 순서에 따른 `D1`, `D2` 같은 짧은 참조다. 형식 복구에서도 같은 참조를 보낸다. 워커는 응답의 모든 문서 인용을 스냅샷 근거 ID로 바꾼 뒤 범위와 중복을 검사한다. 정확히 제공된 참조와 그 발췌의 근거 ID만 받으며 저장 기록과 후속 검토에는 스냅샷 근거 ID를 사용한다.
- 범위 복구 요청의 `repair.document_scopes`에는 문제가 된 목록 이름, 1부터 세는 항목 번호와 실제 인용, 모든 인용이 적용되는 물리 범위 및 확인된 패키지 범위를 담는다. 패키지 범위에는 인용이 가리키는 호출 이름을 붙인다. 패키지 참조가 있는 문서 요청에서 복구 뒤에도 범위가 너무 넓으면 명시된 호출의 근거가 뒷받침하는 하위 패키지가 하나일 때만 그 경로로 좁힌다(`document_package_scope_narrowed`). 범위 오류만 남고 유효한 항목이 있으면 해당 오류 항목을 제외하고 `document_scope_items_omitted`를 보고한다. 유효한 항목이 없거나 근거 ID·서술 등 다른 검증이 실패하면 응답을 거부한다.
- 문서 규칙의 적용 경로(`applies_to`)는 탐색에서 정한 문서의 적용 디렉터리와 같거나 그 아래여야 한다.

### 환경 입력(environment)

- gap 모듈(판정이 `satisfied`가 아닌 모듈) 최대 4개, 그 모듈들의 요구 최대 16개다. 넘으면 `environment_gaps_outside_input`·`requirements_outside_input`를 남긴다.
- 요구마다 원문 줄(600바이트 이하)과 근거 ID를 준다. 원문을 쓸 수 없으면 `requirement_source_omitted`다.
- 출력 메모는 자기 모듈의 요구·근거 ID만 인용한다. 한 모듈·호스트에서 본 버전을 다른 모듈로 옮기지 않는다.

### 도구 관찰과 해석 창(interpret)

- 계획된 분석기 task의 관찰 산출물을 다시 검증해 읽는다. 소스에서 억제된 진단과 구조 지표는 넣지 않는다([분석기](ANALYZERS.md)).
- 도구 상태는 최대 8개(`tools_outside_interpret_input`), 관찰은 경로·줄·ID 순으로 최대 8개다(`observations_outside_interpret_input`).
- 관찰 메시지가 UTF-8이 아니거나, 민감값 패턴에 걸리거나, 600바이트를 넘으면 `(omitted by the platform)`으로 바꾸고 `observation_message_omitted`를 남긴다. 비밀값 선별이 보류한 기본 위치나 관련 위치의 메시지도 생략하고 `secret_files_withheld`를 남긴다. [도구 진단 분류](#도구-진단-분류)도 같은 함수(`shownMessage`)로 메시지를 정한다.
- 진단 위치가 지원 언어의 소스 파일이면 위치 10줄 앞부터 21줄, 1,600바이트 이하의 줄 창을 만든다. 창은 최대 4개다(`observation_context_outside_input`). manifest·설정·문서처럼 소스가 아닌 파일에는 창이 없고 관찰만 간다.
- Cppcheck·clang-tidy·Opengrep의 관찰에 실행 원문의 위치와 스냅샷 위치를 확인한 관련 기록(메모, taint 흐름 단계)이 있으면, 기본 진단 창과 연결한 관련 소스 근거를 요청당 최대 두 곳 더 고른다. 기존 네 창을 공유하고 남는 창이 없으면 뒤쪽 기본 창 하나를 관련 창으로 바꿀 수 있다. 기존 창 밖의 원문을 최대 네 번 다시 읽고, 관련 메모의 종류와 원래 줄, 실제 발췌 ID를 관찰에 연결한다. 메모 원문은 보내지 않으며 범위 밖·선별 보류·위치 미확인·작업 사본 변경 경로는 건너뛴다. 가정과 분기 표시는 분석기가 보고한 정적 단서다.

### 검증 입력과 호출자 확장(verify)

- 후보가 인용한 발췌를 스냅샷에서 다시 읽어 ID 연결을 확인한다. 확인하지 못하면 `review_input_unavailable`이다.
- 인용된 코드·테스트 범위마다 그 범위를 감싸는 선언(첫 줄을 담은 선언부터 끝 줄을 담은 선언까지, 앞 주석 포함)을 다시 읽는다. 인용보다 넓고 한 단위에 들어가면 `origin: declaration` 발췌로 인용 바로 뒤에 보낸다. 검증자는 조사자가 고른 줄만이 아니라 그 줄이 속한 함수·메서드·타입 전체를 읽는다([`verify_declarations.go`](../internal/worker/review/verify_declarations.go)).
- 기존 Go 확장은 후보가 인용한 줄과 겹치는 패키지 함수와 구체 수신자 메서드를 합쳐 최대 8개 고른다. 여기에 [파일 사이의 호출 근거](#파일-사이의-호출-근거)로 확인한 직접 호출이나 구현 원문을 추가할 수 있다. 후보가 인용한 위치에서 시작하며 연결된 발췌는 인용하지 않은 일반 문맥보다 먼저 보낸다.
- 추가 발췌는 두 경로를 합쳐 요청 크기에서 정한 수와 바이트까지다(최소 예산 6개·8,000바이트, 기본 24개·136,000바이트). 한 발췌는 최대 60줄·2,400바이트다. 확장은 인용된 발췌만 기준으로 찾으므로, 앞 역할의 긴 단위 안에 있는 호출자도 별도 창으로 간다. 그 창이 요청에 다시 보내는 단위 안에 있으면 참조로 간다. 파일 사이의 호출 탐색은 최대 80개 파일·8 MiB를 읽는다. manifest 크기와 SHA-256을 확인하고 승인한 범위와 PR 변경 경계를 적용한다. 비밀값 선별에서 보류된 파일은 읽지 않으며 `secret_files_withheld`를 남긴다.
- 기존 Go 확장 기록에는 `caller_expansion_go_only`나 `caller_expansion_package_functions_only`가 남을 수 있다. 적격 선언을 찾지 못하면 `no_symbol_for_expansion`, 호출을 찾지 못하면 `no_callers_found`, 읽기 또는 발췌 예산을 넘기면 `callers_outside_review_context`를 남긴다. 파일 사이의 호출 근거를 얻으면 이전 Go 확장 실패 사유를 적용하지 않는다.

- 검증 지침은 코드로 확인한 프로그램 상태, 근거로 확인한 런타임 동작, 실제 호출 경로에서 선택 가능한 지원 입력·설정을 유효 조건으로 쓸 수 있게 한다. 후보의 발동이나 영향에 필요한 외부 동작이 아직 확인되지 않았으면 `inconclusive`를 반환하고 미확인 전제를 적는다.
- verify 요청의 발췌는 인용 발췌, 감싸는 선언, 확장(호출자·테스트·직접 호출), 인용한 파일의 긴 단위, 그 밖의 80줄 이하 문맥 순이다. 개수는 요청 크기에서 정한다(최소 예산 40개, 기본·최대 128개). 인용 발췌는 항상 남는다. 요청이 한도를 넘으면 확장·비인용 문맥·문서 계약을 먼저 줄인다(`review_input_trimmed`, `callers_outside_review_context`, `contracts_outside_verify_input`). 후보 하나가 진단 8개보다 많은 관찰에 기대면(분류 문제 묶음은 64개까지) 요청은 그 후보의 앞 진단 8개와 그 참조만 싣는다(`verification_observations_trimmed`). 검토 기록과 발견은 진단을 모두 가진다. 이어서 발췌의 SHA-256을 요청에서만 생략할 수 있다(`verification_excerpt_hashes_omitted`). 근거 ID와 경로·줄·코드 원문은 유지하고 검토 기록에는 스냅샷과 대조한 해시를 저장한다. 그래도 넘으면 후보를 앞에서부터(investigate 다음 interpret) 보낼 수 있는 만큼만 보낸다. 보내지 못한 후보는 `unreviewed`(`verification_budget_exceeded`)로 남고 task는 `failed`(`review_input_incomplete`)다.

- Go 입력의 요청 바이트는 `TestGoReviewInputsUnchanged`가 역할마다 지침 해시와 입력 해시로 고정한다.

#### 구체 수신자 메서드의 호출자와 테스트

- 같은 패키지의 검증된 원문을 Go 구문·타입 분석으로 연결한다. 메서드 이름이 같아도 실제로 가리키는 선언이 다르면 제외한다. 한 인용이 여러 메서드와 겹치면 후보에 적힌 정확한 이름을 원문 선언과 대조하며, 같은 이름이 여럿이면 수신자까지 일치해야 한다. 인터페이스 선택, 동적 호출, 외부 패키지, 생성 코드와 빌드 조건에 따라 달라지는 모호한 선언은 연결하지 않는다. 의존성을 불러오거나 프로젝트를 빌드·실행하지 않는다. PR에서 새 메서드 발췌는 변경 파일 안에서만 고르며 기존 패키지 함수의 조회 범위는 run scope를 따른다.
- 호출부에는 호출과 함께 보일 수 있는 반환·조건·정리 경로를 포함한다. 같은 패키지의 표준 Go 단위 테스트는 해당 메서드의 반환값이 조건에 쓰이고 그 조건에서 테스트 실패를 기록하는 경우에 그 호출과 단언을 담는다. 테스트와 호출자를 번갈아 배정하고, 후보가 인용하지 않은 문맥보다 먼저 요청에 넣는다. 추가로 찾은 발췌가 앞선 역할과 같은 ID이면 앞서 기록한 출처와 속성을 유지하고 요청 순서만 앞당긴다. 테스트는 저장된 원문에 적힌 기대 동작으로 읽는다.

### 요청 크기

한 요청의 크기는 노드 운영자의 요청 예산 하나에서 정한다([`budget.go`](../internal/worker/review/budget.go)). `codeye agent --review-request-bytes N --review-output-tokens N`, 서비스 설정 `agent.model.review_request_bytes`·`review_output_tokens`가 값을 정하고 Hello의 같은 이름 필드로 워커에 간다. 모든 역할과 slice가 같은 규칙으로 상한을 계산하므로 작은 예산은 같은 모양의 작은 요청을 만든다. 계획은 예산과 무관하다.

| 설정 | 기본 | 범위 | 뜻 |
|---|---|---|---|
| 요청 바이트 | 262,144(256 KiB) | 40,000~1,048,576 | 한 요청의 전체 메시지 텍스트(`opencode.Prompt`: 지침, 계약, 복구 규칙, 입력, 감싸는 문장) |
| 출력 토큰 | 16,384 | 1,536~65,536 | 호출당 모델이 쓸 수 있는 출력. 서술 길이와 후보 수를 정하고 relay 프로필의 출력 한도가 된다 |

요청 바이트 `R`과 출력 토큰 `O`에서 상한을 이렇게 계산한다. 40,000은 지침·계약·문서·환경 메모·도구 관찰처럼 자체 상한을 가진 고정 부분의 몫이다.

| 상한 | 규칙 | 최소 예산 | 기본 | 최대 |
|---|---|---|---|---|
| 복구 여유 | max(3,072, R/32) | 3,072 | 8,192 | 32,768 |
| 조사 코드 원문(줄 번호 포함) | max(0.3R, R−40,000−복구 여유) | 12,000 | 213,952 | 975,808 |
| 검토 단위 | max(2,400, 코드 원문/5) | 2,400 | 42,790 | 195,161 |
| 조사 발췌 수 | 코드 원문/1,500, 8~64 | 8 | 64 | 64 |
| verify 발췌 수 | 코드 원문/300, 40~128 | 40 | 128 | 128 |
| verify 확장 | 6×배수(최대 24)개, 8,000×배수 바이트. 배수 = 코드 원문/12,000 | 6·8,000 | 24·136,000 | 24·648,000 |
| 서술 필드 | O×1,200/16,384, 400~1,200바이트(지침에는 그 3/10 글자) | 400(120자) | 1,200(360자) | 1,200 |
| 후보의 실패 과정(`mechanism`) | 서술 필드의 두 배, 최대 2,400 | 800 | 2,400 | 2,400 |
| 조사 후보 | (O−4,096)/1,536, 4~12. 보낸 코드 32 KiB까지 4개, 이후 32 KiB마다 하나 | 4 | 8 | 12 |

| 한도 | 값 | 적용 |
|---|---|---|
| OpenCode 어댑터 입력 한도 | 1,048,576바이트 | 지침 + 입력. 넘으면 `invalid_review_input` |
| OpenCode 응답 보관 한도 | 524,288바이트 | 출력 토큰 최대치의 8배. 넘으면 `model_output_incomplete` |
| relay 프로필 | 출력 = 출력 토큰, 문맥 = 요청 바이트 + 16,384 + 출력 토큰 | 관리형 OpenCode 설정이 relay 모델에 선언하는 한도. 토큰은 요청의 1바이트 이상이므로 요청 바이트가 입력 토큰의 상한이다 |
| QA 예산 relay | 입력 기본 278,528바이트(최대 1,064,960), 출력 기본 16,384 토큰(`--max-output-tokens`, 최대 65,536) | relay가 받는 요청당 메시지 텍스트와 출력. 운영은 [평가](EVALUATION.md)에 있다 |
| 호출 제한시간 | 600초(1초~30분) | `--model-timeout`. 기본 요청을 읽고 출력 한도까지 쓰는 호출이 멈췄을 때의 상한이며 측정한 지연 시간이 아니다. CODEYE가 쓰는 OpenCode provider 설정(relay, 키 파일 provider, 운영자 OpenCode 설정을 옮긴 native provider)은 응답 헤더와 다음 스트림 조각을 이 시간만큼 기다린다(`headerTimeout`·`chunkTimeout`, 밀리초). 설정하지 않으면 OpenCode 1.19.5는 각각 300초에 요청을 끊는다. native provider에 운영자가 정한 값은 그대로 둔다 |

- 요청은 메시지 하나이고 도구 정의를 쓰지 않는다.
- 보내기 전에 메시지 바이트를 재고, 넘으면 발췌를 뒤에서부터 줄이고 `review_input_trimmed`를 남긴다. 최소 발췌로도 넘으면 task는 `failed`(`review_input_too_large`)다.
- 예산이 모자라면 목록 뒤쪽이 먼저 빠진다. 첫 순회에서 생태계 이름 순으로 뒤인 언어의 발췌가 여기에 해당한다. 여섯 생태계가 모두 범위에 있으면 언어 지침이 커져 코드 발췌가 줄고, 최대 길이 후보가 많은 verify는 일부 후보를 보내지 못할 수 있다. 합성 최악 입력(모든 서술 필드를 최대 길이로 쓴 후보)에서 최소 예산의 verify는 후보 6개 중 4개를 보내고, 기본과 최대 예산은 모두 보낸다(`TestReviewRequestSizeWorstCase`). 보내지 못한 후보는 `unreviewed`(`verification_budget_exceeded`)다.
- 서술 필드 한도와 조사 후보 상한은 출력 토큰에서만 정한다. 후보 수는 그 상한 안에서 보낸 코드에 따라 는다. 작은 요청 바이트에 큰 출력 토큰을 짝지으면 후보 서술이 verify 요청의 자리를 차지해, 최대 길이로 쓴 후보는 일부만 검증되고 나머지는 `unreviewed`(`verification_budget_exceeded`, task `review_input_incomplete`)로 남는다. 합성 최악 입력에서 최소 요청 바이트(40,000)에 기본 출력 토큰(16,384)을 짝지으면 verify는 후보 6개 중 2개만 보낸다. 최소 출력 토큰과 짝지으면 4개다(`TestReviewRequestSizeWorstCase`). 요청 바이트를 줄일 때는 출력 토큰도 함께 줄인다.
- 비용은 요청과 출력 크기에 비례한다. 요청 바이트를 줄이면 한 번에 읽는 코드가 줄고 남은 줄은 slice로 넘어간다. 출력 토큰을 줄이면 서술과 후보 수가 준다. 호출 수는 `review_max_calls`가 정한다. 실제 비용과 지연 시간은 측정하지 않았다.

## 모듈 단위 검토 분할

overview 조사(`review.investigate`)가 보내지 못한 코드와 테스트 줄을 후속 검토에 넣는다. `review.scope`가 스냅샷을 다시 읽고 수락된 overview의 실제 발췌 범위를 뺀다. 파일 앞부분이나 문서 계약 주변만 보냈으면 같은 파일의 나머지 줄도 대상이 된다. 남은 줄은 [검토 단위](#검토-단위)로 나눈다. 한 번의 요청에 담는 단위 수, 단위 크기, 원문 합계는 overview와 같은 [요청 크기](#요청-크기) 규칙을 따른다(최소 예산에서 8개, 단위 2,400바이트, 합계 12,000바이트). 전체 메시지는 지침과 복구 여유를 포함해 요청 바이트 이하다. [계획과 범위 계산](../internal/worker/review/slice_coverage.go) · [실행](../internal/worker/review/slice_run.go)

| task | 단계 | 판정 필수 | 모델 호출 | 내용 |
|---|---|---|---|---|
| 전체 역할 다섯 개 | 위 표 | 위 표 | 위 표 | 저장소 구조와 문서 계약, 도구 관찰을 바탕으로 조사하며 overview verify는 interpret 후보도 검증한다 |
| `review.scope` | `code_review` | 아니오 | 없음 | 검토 대상 소스가 있을 때 범위를 기록하고, 아직 조사하지 않은 줄을 계획된 slot에 배정한다 |
| `review.investigate.sNNN` | `code_review` | 아니오 | 1~3 | slot의 줄 범위로 조사하고 근거와 후보를 남긴다 |
| `review.verify.sNNN` | `code_review` | 아니오 | 0~3 | 해당 slot investigate의 후보를 검증한다. 후보가 없으면 모델을 부르지 않는다 |

채워지지 않은 slot은 `no_review_scope`로 끝난다. 호출 상한에 막히거나 실패한 slot은 상태를 유지하고 해당 줄의 공백을 보고한다. 실행 결과의 종합 판정은 필수 역할과 분석 도구의 상태를 따른다. 코드 검토 단계에는 실제 후속 검토의 상태가 표시된다. [단계와 task](ARCHITECTURE.md#표시-단계와-task-단계)

### 검토 우선순위

- 모듈 ID는 `<ecosystem>:<dir>`이다. 소스는 해당 생태계의 가장 깊은 선언 디렉터리에 속하고, 선언이 없으면 루트(`.`)에 속한다. `discovered`는 모듈 탐색에서도 같은 ID를 찾았는지 나타낸다. 각 모듈의 적격 파일 수와 실제 검토 범위를 각각 기록한다.
- 일반 검토는 manifest에서 필요한 작업 수를 추정하며 최대 96개의 후속 조사·확인 쌍을 계획한다. 실패하거나 취소된 실행을 고정 스냅샷에서 재시도할 때 이전 작업 키가 모두 필요하므로 기존 추정 규칙을 유지한다. 확장 코드 검토는 스냅샷의 검증된 원문에서 필요한 발췌 수를 산정해 최대 999개의 작업 쌍을 계획한다. 같은 스냅샷·범위에서 노드 호출 상한을 바꾸거나 재시도해도 작업 키가 같다. `review.scope`는 실제 JSON 바이트 크기를 기준으로 발췌를 배정한다.
- 일반 실행은 아직 수락된 발췌가 없는 모듈에 가장 앞선 파일의 첫 단위를 먼저 배정한다. 주요 소스의 모듈을 먼저 배정하고, 부차 소스만 남은 모듈에도 첫 단위를 배정한 뒤, overview가 보여 주지 않은 파일의 첫 단위, 그다음 모든 파일의 남은 단위를 차례로 돌며 배정한다. 단위는 파일 전체이거나 선언 경계로 나눈 부분이다([검토 단위](#검토-단위)). PR은 변경 파일, 변경 파일과 같은 디렉터리의 파일, 그 밖의 파일 순을 유지하며 각 단계 안에서 같은 배정 순서를 쓴다. 한 slot에 여러 모듈의 짧은 발췌를 담을 수 있다.
- 같은 순서에서 비지표 도구 진단의 심각도와 수, 필수 분석기 실패, 진입점, 소스, 테스트, 경로를 사용한다. 파일 안에서는 해당 진단 위치, 그다음 실행문이 있는 발췌를 우선한다. 억제된 진단과 지표는 진단 우선순위에 포함하지 않는다. `priority.secondary`에는 예제·시험 입력·의존성·생성물 경로를 식별하는 규칙이 남는다. 첫 10줄에 생성 표지가 있는 파일도 부차 파일이다. [분류 규칙](../internal/worker/review/record/priority.go)
- 원문 길이 한도에 걸린 줄은 `review_line_input_limit`을 남기고 다음 줄을 검토한다. 공백으로만 이루어진 발췌는 `source_blank_range`로 기록한다. slot 한도 뒤의 파일과 줄은 `review_slice_limit`로 남는다. 원문 입력 크기 상한, 읽을 수 없는 텍스트와 빈 파일, 비밀값 선별에 걸린 파일에도 실제 이유가 남는다.

### 호출 상한과 승인

- `codeye agent --review-max-calls N`과 서비스 설정 `agent.model.review_max_calls`는 attempt당 호출 수를 제한한다(기본 99, 15~2,013). 일반 검토에는 최대 207회가 적용된다. `scope.review_coverage: "extended"`를 선택하고 노드 상한이 207회를 넘을 때 96개 이후의 후속 조사도 실행할 수 있다. 전체 역할 다섯 개의 최대 호출은 15회이며 후속 조사보다 먼저 실행된다. [도구 진단 분류](#도구-진단-분류) slot은 전체 역할 뒤, 후속 조사 앞에서 같은 상한의 나머지를 쓴다.
- slice는 조사와 확인을 위해 두 호출이 남아 있을 때 시작한다. 조사 재시도는 확인에 쓸 한 호출을 보존한다. 후보가 없는 slot은 검증 호출 없이 완료된다. 형식 복구도 같은 상한을 쓰며, 호출을 남김없이 써야 하는 검토는 기존 복구 횟수보다 일찍 종료할 수 있다. 승인되지 않은 slot은 `budget_exhausted`(`review_budget_exhausted`)로 기록한다. 선택적 `review.contract`도 같은 계수의 잔여 호출을 사용한다.
- 계수 파일은 attempt의 scratch에 둔다. 순서대로 실행하는 모든 모델 요청은 호출 전에 계수를 확인하고 한 줄을 기록한다. 계수를 읽거나 쓰지 못하면 해당 호출은 `review_call_count_failed`로 끝난다.

### 범위 산출물과 모델 기록

- 범위 산출물의 media type은 `application/vnd.codeye.review-scope+json`이고 현재 스키마는 0.3이다. `overview`에는 수락된 조사에 들어간 파일, `slices[].files`에는 시작 줄·줄 수·실제 JSON 바이트 수를 가진 예정 범위, `excluded`에는 보류 및 읽기 불가 파일, `unplanned`와 `omitted`에는 배정하지 못한 파일과 줄을 기록한다. 같은 파일의 이어지는 줄은 여러 slot에 들어갈 수 있다. 0.1과 0.2 범위 산출물도 읽는다. [범위 스키마](../schemas/review-scope.schema.json) · [범위 예시](../examples/review/slices/scope.json)
- 스냅샷 manifest의 경로와 내용 digest, 파일과 모듈 수, 범위의 상한과 중복을 검증한다. 각 slice 요청은 줄을 스냅샷에서 다시 읽어 계획된 범위와 인코딩 크기를 대조한다. 모든 입력은 같은 비밀값 선별과 읽기 필터를 거친다. 비밀정보 탐지가 미설정이거나 결과를 검증할 수 없으면 `model_input_not_secret_screened`를 기록하고 기본 선별을 적용한다.
- slice는 overview와 같은 역할 지침을 쓴다. 문서·환경 맥락 때문에 코드 줄이 빠질 경우 먼저 덜 중요한 환경 메모와 문서 전달 항목을 줄인다. 전체 요청 한도 때문에 계획한 범위를 담지 못하면 `review_input_trimmed`로 남긴다. [조사 예시](../examples/review/slices/investigate.s001.json) · [검증 예시](../examples/review/slices/verify.s001.json)
- 코드 강점은 요청에서 실행문을 찾을 수 있는 구현 발췌를 인용해야 한다. 근거가 부족한 강점을 제외해도 같은 응답의 유효한 후보와 계약 대조는 유지한다.
- 보고서는 기록된 조사 요청의 발췌와 응답이 수락된 발췌의 줄을 각각 합친다. 응답을 수락하지 못했어도 요청 기록은 보존한다. 파일마다 남은 줄과 이유를 확인할 수 있다. 후보 검증은 별도이고 후보가 없어 모델을 부르지 않은 확인 작업은 후보 검증 수에 들지 않는다. 줄마다 모델이 의미를 이해했는지나 결함을 탐지했는지는 측정하지 않는다. [보고서](REPORT.md#모듈별-검토-장부)

## 도구 진단 분류

해석 역할(`review.interpret`)이 다루는 관찰은 요청당 8개다. 나머지 도구 진단은 계획된 분류 slot이 묶음 단위로 모델에 보내 실제 문제인지 분류한다. [계획](../internal/worker/review/triage_plan.go) · [실행](../internal/worker/review/triage_run.go) · [지침](../prompts/review/triage.md)

| task | 단계 | 판정 필수 | 모델 호출 | 내용 |
|---|---|---|---|---|
| `review.triage.tNNN` | `code_review` | 아니오 | 1~3 | slot에 배정된 진단 묶음을 분류한다. 배정된 묶음이 없으면 `no_review_scope`, 해석할 관찰이 없으면 `no_tool_observations`, 호출 상한이면 `budget_exhausted` |
| `review.verify.tNNN` | `code_review` | 아니오 | 0~3 | 같은 slot에서 문제로 분류한 묶음의 후보를 검증한다. 후보가 없으면 모델을 부르지 않는다. slot이 승인되지 않았으면 같은 상태와 사유로 끝난다 |

### 계획과 묶음

- **slot 수.** manifest의 적격 소스 파일 12개마다 한 slot, 최소 2개, 최대 24개다(적격 파일이 없으면 0). 계획은 manifest·범위·상수로만 정한다(A37 2). slot 쌍은 계획의 끝, 모듈 slice와 `review.contract` 뒤에 온다. 호출 몫은 [호출 비용](#호출-비용)이 정한다.
- **대상.** 수락된 분석기 산출물의 진단 중 소스에서 억제된 진단, 구조 지표, 비밀값 탐지를 뺀 것이다. 다음은 분류하지 않고 각 slot 기록의 한계로 남긴다. 수락된 해석 후보가 이미 다룬 진단(`diagnostics_interpreted`), 위치 없는 진단(`diagnostics_without_location`), 비밀값 선별이 보류한 파일의 진단(`secret_files_withheld`), 읽을 수 있는 소스 단위가 없는 진단(`diagnostic_context_unavailable`).
- **묶음.** 같은 분석기·같은 규칙·같은 [검토 단위](#검토-단위)(단위보다 작은 파일은 파일 전체)의 진단을 한 묶음으로 한다. 서로 다른 두 도구가 같은 단위의 같은 줄에서 병합 계열([기본 심각도](ANALYZERS.md#기본-심각도))이 같은 규칙을 보고하면 두 묶음을 합치고 `cross_tool`로 표시한다. 진단은 합치지 않는다. 64개를 넘는 묶음은 64개씩 나누고, 나뉜 조각은 도구가 둘 이상일 때만 `cross_tool`이다(기록 검사가 확인한다).
- **순서.** 묶음의 도구 finding 심각도가 높은 쪽(시험·예제·벤치마크·생성물·외부 코드 경로는 [경로 규칙](ANALYZERS.md#기본-심각도)으로 낮춘 값), 같은 심각도에서는 배포 코드의 묶음이 그 밖의 경로보다 먼저, 그다음 진단이 많은 묶음, 경로, 줄, 도구, 규칙 순이다. 분류에 쓸 수 있는 몫이 작아서 배포 코드가 먼저 분류를 받게 한 것이다. 요청에 보내는 `default_severity`는 표의 값 그대로이고(모델이 보는 입력은 바뀌지 않는다) 순서에만 낮춘 값을 쓴다. 경로의 종류는 파일 경로만으로 정한다(`record.PathClass`). 담지 못한 묶음의 진단은 그대로 분류하지 않음으로 보이고 한계 코드가 남는다.
- **요청에 담기.** 순서대로 첫 번째로 맞는 slot에 넣는다. 한 요청은 묶음 수(출력 토큰에서 1,024를 빼고 1,024로 나눈 값, 2~24), 소스 원문 합계(요청 예산의 원문 한도), 진단 1,024개, 묶음 설명 바이트(요청 바이트의 1/16, 최소 8,000)를 넘지 않는다. 한 요청 안에서 같은 단위는 한 번만 보내고 비용도 한 번만 센다. slot을 다 쓰고 남은 묶음은 `diagnostics_outside_triage_slots`로 남는다.

### 요청과 출력

- 묶음마다 도구·규칙 ID·기본 심각도·진단 수·`cross_tool`·경로·줄 목록, 메시지를 붙인 진단 예시 최대 8개, 문맥 발췌 ID(묶음의 단위, 단위가 파일 처음이 아니면 그 파일의 머리 한 번)를 보낸다. 메시지 규칙은 해석 창과 하나다([도구 관찰과 해석 창](#도구-관찰과-해석-창interpret)).
- 관련 위치를 모델 입력에 싣는 분석기(cppcheck·clang-tidy의 메모, Opengrep의 taint 흐름 단계)의 진단 예시는 관련 위치를 함께 보낸다. 관련 위치마다 종류, 줄, 그 줄을 담은 묶음 자신의 문맥 발췌 ID를 보낸다. 예시당 최대 8개이고, 넘치면 앞 7개와 마지막(흐름의 위험 호출)을 남긴다. 묶음 문맥 밖(다른 단위·다른 파일)의 관련 위치와 넘친 위치는 보내지 않고 `observation_context_outside_input`을 남긴다. 관련 위치의 문구는 보내지 않는다. 관련 위치가 비밀값 선별이 보류한 파일에 있으면 해석 창과 같이 메시지를 생략한다. 이 분석기 목록은 `relatedForModel` 하나가 정하고 해석 창도 같은 목록을 쓴다. 발췌 원문은 다른 역할과 같은 읽기 검사(비밀값 선별, 민감값 패턴, 크기)를 거친다. 요청이 예산을 넘으면 뒤쪽 묶음부터 빼고 `review_input_trimmed`를 남긴다.
- slot은 분류와 검증에 쓸 호출 두 번이 남아 있을 때 시작한다(모듈 slice 뒤이므로 남은 호출은 slice가 쓰고 남긴 것과 분류 몫이다). 분류 재시도는 검증에 쓸 호출 하나를 남긴다. 결정은 호출 계수 옆 파일에 쓰고 같은 slot의 검증이 따른다.
- 출력은 묶음마다 `problem`(조건·영향·고칠 방향과 묶음 문맥 안의 줄 인용), `harmless`(무해하게 만드는 코드 근거와 그 줄 인용), `unclear`(무엇이 더 필요한지) 중 하나다. 의존성·타입·헤더를 찾지 못해 생긴 진단은 분석 공백으로 보고 `unclear`로 둔다. 모델은 도구 상태·진단 수·원시 등급·규칙·기본 심각도를 바꾸지 못하고 심각도를 정하지 않는다.
- 출력 오류는 [출력 오류 분류](#출력-오류-분류)를 따른다. 형식 오류가 있으면 남은 묶음과 그 발췌만 담은 복구를 한 번 보낸다. 복구 뒤에도 남은 형식 오류는 그 묶음만 분류하지 않고(`triage_item_omitted`; 첫 답에 형식 오류가 있었는데 복구 답이 그 묶음을 빠뜨린 경우도 같다), 무결성 오류는 그 답을 거부한다(`triage_item_rejected`). 답이 없는 묶음은 `triage_answer_missing`이다. 한 출력에 같은 묶음의 답이 둘이면 앞 답을 받아들였어도 `triage_group_duplicate`를 남긴다. `problem`·`harmless`·`unclear` 모두 자기 묶음의 발췌만 인용한다. 다른 묶음의 발췌를 인용하면 형식 오류(`triage_evidence_not_at_group`)이고, 복구 뒤에는 자기 묶음의 인용만 남겨 검사한다. 분류하지 않은 묶음이 있으면 `diagnostic_groups_not_triaged`를 남긴다. 분류한 묶음이 하나도 없으면 task가 실패한다.
- **출력 한도.** 한 요청의 묶음 수는 묶음당 출력 1,024 토큰을 가정해 정한다. 실제 모델이 그보다 길게 써서 출력 토큰 한도에 답이 잘리면 출력은 JSON이 아니다(`output_not_json`). 이것은 형식 오류다. JSON이 아닌 답마다 재시도는 남은 묶음의 앞 절반(우선순위가 높은 쪽)만 묻고 나머지는 `triage_item_omitted`로 둔다(역할 호출 세 번 안에서, 7개면 7→4→2). 재시도 답에서 하나라도 받아들이면 slot은 성공하고 빠진 묶음은 `diagnostic_groups_not_triaged`로 보인다. 세 번 모두 JSON이 아니거나 묶음 하나만 남아도 JSON이 아니면 분류한 묶음이 없어 task가 실패한다(`review_output_invalid`). 그때도 호출과 묶음을 담은 실패 기록은 남는다.
- 요청을 만들 수 없었거나(`review_input_too_large`) 호출 뒤에 취소된 slot도 실패 기록을 남긴다. 기록은 한 호출과 보낸 묶음을 모두 분류하지 않은 것으로 담아, 보고서가 무엇이 모델에 갔는지 안다. 요청을 만들기 전에 실패한 기록에는 묶음이 없다.
- 문제로 분류한 묶음은 후보 `triage_N`(origin `triage`, 묶음의 관찰 ID)이 되고 `review.verify.tNNN`이 검증한다. 검증은 문서 기록과 그 slot의 분류 기록을 상류로 읽는다. 도구 진단, 모델 후보, 검증 판정은 서로 다른 기록이며 관찰 ID로 연결된다. 무해 판단은 도구 finding을 숨기지 않는다.

### 호출 비용

분류 slot은 같은 attempt 호출 상한을 쓴다. 묶음이 배정된 slot은 보통 분류 한 번과(문제가 있으면) 검증 한 번을 부르고, 형식 복구와 재시도를 포함하면 각각 세 번까지다. 배정된 묶음이 없는 slot은 부르지 않는다.

모듈 slice가 먼저다. 분류 쌍은 계획의 끝에 있고, 분류 몫은 실행 때 한 번 정한다.

- 전체 역할이 남긴 호출을 L, 아직 보낼 줄이 있는 slice 수 × slice 입장 예비(호출 2)를 필요량으로 한다.
- 필요량이 L 이하이면 몫은 0이다. slice는 전처럼 모든 줄을 보내고 분류는 slice가 쓰고 남긴 호출을 쓴다. 남은 호출이 둘 미만이면 분류는 실행되지 않고 모든 진단이 분류하지 않음으로 남는다.
- 필요량이 L을 넘으면 L 16회마다 분류 쌍 하나(호출 2)를 몫으로 둔다. 최소 한 쌍이고 묶음이 배정된 slot 수를 넘지 않는다. slice와 `review.contract`는 이 몫을 쓰지 않는다. 첫 slot이 심각도가 가장 높은 묶음(같은 심각도에서는 배포 코드의 묶음)을 담으므로 몫이 한 쌍이어도 가장 심각한 진단부터, 배포 코드부터 분류된다.
- 16은 평가 실행의 상한 20에서 한 쌍, 기본 상한 99에서 다섯 쌍이 되는 값이다. 지금까지 측정한 품질 향상은 slice가 상한 20 안에서 모든 줄을 보낸 데서 나왔으므로 slice가 양보하는 양을 작게 정했다. slice가 다 쓰지 않은 호출은 분류가 쓴다.

몫은 attempt마다 처음 slice 입장 때 정해 scratch의 `review.triage.hold`에 둔다. 범위 산출물이 없거나 모델·진단이 없으면 몫은 0이다. 범위 산출물의 `calls_before_slices`는 전체 역할의 호출만 세고, 보고서 장부는 분류 slot 기록의 호출을 slice처럼 더한다.

이 저장소를 가짜 upstream으로 검토한 결과(실제 분석기, 진단 853개)는 다음과 같다. 실제 모델의 비용·품질은 측정하지 않았다.

| 상한 | 규칙 | 들어간 slice | 새로 보낸 줄 | 분류한 slot | 분류한 진단 |
|---|---|---|---|---|---|
| 20 | 분류 먼저(이전) | 0 | 0 | 6 | 523 |
| 20 | slice 먼저, 몫 한 쌍 | 5 | 441 | 1 | 238 |
| 99 | 분류 먼저(이전) | 30 | 102,410 | 16 | 851 |
| 99 | slice 먼저, 몫 다섯 쌍 | 41 | 155,009 | 5 | 493 |

## 문서 계약 후속 검토

모델 검토가 승인되고 안내 문서와 지원 언어 구현 경로가 계획 범위에 있으면 마지막에 `review.contract`를 한 건 둔다. 앞선 독립 조사에서 수락된 `contract_probe`와 명시적인 `unknown` 대조가 있어야 보낸다. 같은 문서 근거와 범위의 계약이 충돌할 때는 기존 판정을 보존한다.

요청은 같은 스냅샷에서 다시 읽은 문서 약속과 앞선 이유, 위치 선택으로 얻은 구현·호출·테스트 발췌를 담는다. 수락된 계약과 그 원문에 모두 이름이 나오는 함수는 최대 두 개까지 적용 범위 안에서 정확히 찾아 진입점의 본문을 함께 보낼 수 있다. 선언만 있거나 같은 이름의 정의가 여러 개면 그 검색 결과는 쓰지 않는다. 관련 모듈 검토가 실제로 제공한 코드·테스트 줄도 사용할 수 있다. 해당 기록과 `review.scope`의 digest를 묶는다. 실제 발췌만 근거 목록과 코드 노출에 포함하며 `loc_` 위치 ID는 그 자체로 인용할 수 없다.

선택한 경로와 검증된 리터럴 검색에서 찾은 경로에 배정된 모듈 검토를 먼저 확인한다. 다른 적격 발췌를 다시 읽어 리터럴을 확인할 때 적용하는 80개 상한보다 뒤에 있는 선택 경로도 같은 원문·산출물 검증을 거쳐 읽는다. 같은 근거 ID를 여러 모듈 기록에서 반복해서 읽지 않는다.

선택한 구현 창에서 독립 조사에 없던 Go 패키지 함수 본문을 찾으면, 같은 패키지에서 그 함수를 이름으로 직접 호출하고 결과를 분기 또는 반환에 쓰는 창을 최대 두 개 보낸다. 함수 선언이 창 밖에 있으면 같은 파일의 구문 트리로 본문이 속한 함수를 확인한다. 선택한 줄의 조건이나 반환에서 직접 호출한 짧은 구현도 두 개 중 하나의 창으로 보낼 수 있다. 호출이나 결과의 줄도 새로 읽은 줄이어야 한다. 적용 범위와 PR 변경 경로의 Go 파일을 최대 32개·512 KiB까지 읽으며, 테스트·생성물·보류 파일은 호출자 후보에서 빠진다. 모든 분석 대상 파일을 읽은 디렉터리에서만 다른 파일의 빌드 조건 없는 정의를 연결한다. 지역 이름이 가리는 호출과 같은 이름의 선언이 여럿인 경우는 제외한다. Go 파서가 연결한 직접 호출을 발췌하므로 해당 프로젝트의 빌드나 실행은 필요하지 않다.

선택한 계약과 원문에서 공통으로 찾은 코드 식별자나 마침표를 포함한 이름·버전을 수락된 모듈 검토의 강점과 대조한다. 같은 단서가 그 강점이 인용한 구현의 새 실행문 줄에도 있으면 발췌를 최대 두 개 우선 넣는다. 해당 모듈 검토와 범위 산출물의 digest를 연결하고 원문을 다시 검증한다. 강점의 제목과 설명은 검색에만 쓰며 대조 판정은 후속 응답이 인용한 구현 근거로 검증한다.

선택한 위치, 검증된 리터럴 검색, 또는 문서에 명시된 이름으로 찾은 새 실행문과 앞선 발췌가 같은 구현 파일에 있으면, 전체가 50줄·1,600바이트 이하이고 요청 한도에 들어갈 때 함수 선언과 나머지 분기를 함께 보낸다. 원본 스냅샷에서 다시 읽어 새 근거 ID를 부여하고, 기존 인용과 모듈 기록에 연결된 발췌, 서로 다른 분기를 보여 주는 발췌를 유지한다. 같은 내용을 포함하는 발췌가 있으면 그 안에 포함되는 선택 발췌는 생략할 수 있다.

응답은 기존 계약 인덱스·적용 범위·문서 근거 ID를 그대로 반환한 대조 한 건이다. 일치·부분 일치·불일치를 저장하려면 독립 조사 입력 전체의 구현 발췌에 없던 실행문이 대상 범위 안에 한 줄 이상 인용돼야 한다. Rust의 테스트 전용 항목과 JS·TS 템플릿 문자열 본문은 실행문 근거에서 제외한다. 호출 경로와 결과가 실제 계약과 이어지는지는 모델의 정적 판단이다. 테스트 원문에서 해당 입력과 단언을 확인할 수 있고 테스트 실행 결과는 없다. 위반 조건과 준수 조건을 각각 확인했을 때 부분 일치를 사용한다. 일부만 확인했으면 `unknown`과 `contract_comparison_inconclusive`를 기록하고 보고서에서 원래 판단을 유지한다. 새로 확인한 구현은 추가 관찰로 남길 수 있다. 불일치한 참조, 잘못된 출력, 선별 제한, 예산 부족에도 원래 결과를 유지한다.

### 파일 사이의 호출 근거

호출부와 구현의 연결은 스냅샷의 소스와 import·모듈 선언으로 확인한다. 전체 조사는 계약 원문과 관련된 호출을 고른 때 두 발췌의 실제 줄 범위를 확인해 `scope.direct_calls`에 넣는다. 후보 검증과 문서 계약 후속 검토는 인용한 파일과 줄에서 한쪽을 확인하고 다른 쪽 발췌를 추가할 수 있다. 후속 검토에서는 기존 전체 조사에 없는 소스만 추가한다. 적용 범위, PR 변경 경계, 생성물 제외, 비밀값 선별 및 각 요청 한도를 따른다.

| 언어 | 확인하는 경로 |
|---|---|
| Go | `go.mod`의 모듈 경로와 import 이름으로 같은 모듈의 다른 패키지에 있는 공개 함수를 찾는다. 패키지의 비테스트 소스를 확인해 정의가 하나여야 한다. 짧은 함수는 몸체를, 긴 함수는 끝의 확인된 반환 창을 우선 사용할 수 있다. |
| Java | 명시적인 클래스 또는 정적 멤버 import를 따라 공개 정적 메서드를 찾는다. 같은 클래스의 직접 호출도 이름·인자 수와 리터럴 또는 호출자 매개변수의 타입으로 구현을 좁힌다. 상속으로 더 적합한 오버로드가 있을 수 있거나 구현이 동적으로 달라질 수 있으면 연결하지 않는다. |
| Python·JS/TS | 최상위 Python `from … import …`와 JS/TS 상대 경로 named import를 따라 간다. 명시적 이름 변경이나 재내보내기를 최대 네 모듈까지 따라 실제 반환·오류·단언이 있는 함수를 찾는다. Python의 일반 모듈·`src` 배치와 JS/TS의 상대 파일·`index` 배치를 확인한다. |
| C/C++ | 소스가 직접 지정한 로컬 헤더 하나에서 고유한 `static inline` 정의를 찾고 본문의 직접 반환 호출에 연결한다. 전처리 조건, 매크로, 다른 include가 섞인 소스의 빌드 대상은 선택하지 않는다. |
| Rust | 표준 Cargo 소스 경로와 명시적 `mod` 선언부터 `use crate::…` 이름이 가리키는 공개 함수까지 따라 간다. 대체 모듈 파일, 조건부 속성이나 매크로가 있는 경로는 선택하지 않는다. |

경로 중복, 이름 섀도잉, 실행 시 선택하는 import·빌드 구성, 읽을 수 없는 중간 모듈은 일반 발췌와 미확인 상태를 유지한다. 직접 호출 연결은 소스로 확인할 위치다. 실행 성공, 선택한 빌드에서의 도달, 테스트 통과의 판단에는 별도의 실행 기록이 필요하다. 소스 토큰을 읽는 경로는 파일당 토큰 16,384개와 중첩 깊이 128을 넘기면 생략한다.

### Go HTTP 사용자 동작

문서의 기본·보충 요청은 목록 안에서 여유가 있을 때 `handler`에 확인된 Go 처리기의 파일명과 함수명을 읽기 쉬운 짧은 표현으로 표시한다. 긴 이름과 안전한 형식으로 줄일 수 없는 이름은 생략한다. 이름을 보내기 전에 등록과 처리기에 범위·스냅샷·비밀값 선별 규칙을 적용한다. 같은 메서드·패턴이 여러 곳에 있거나 패턴에 리터럴 경로 조각이 없을 때 이름을 먼저 담는다. 이름을 생략해도 앞서 들어간 경로 선택지와 문서 발췌는 유지한다.

워커는 Go 소스에서 리터럴 패턴과 처리기 본문을 모두 확인할 수 있는 등록을 찾는다. 표준 라이브러리의 HTTP 등록, 지원하는 `gorilla/mux` 등록과 접두 경로, 메서드·경로·처리기 필드를 전달하는 제한된 형태의 경로 테이블을 읽는다. 조건부·모호한 등록과 실행 시 계산되는 값은 목록에서 빠질 수 있다. 경로는 해당 등록의 패턴으로, 상위 라우터에 붙는 상대 경로일 수 있다. 워커는 서비스를 구동하거나 실제 도달 여부를 판정하지 않는다.

검색은 범위 내 주요 Go 파일 최대 512개, 파일당 96 KiB, 전체 4 MiB 안에서 수행한다. pull request에서는 변경 파일 경계를 적용한다. 선별에서 보류된 파일, 생성 소스, 테스트와 부차 경로는 후보에서 제외한다. 확인한 경로의 패턴은 128바이트 이하다. 파악한 등록을 최대 64개까지 서로 다른 경로 묶음에 걸쳐 모아 요청에 최대 5,000바이트의 목록으로 넣는다. 같은 파일에서 같은 메서드와 처리기 본문을 등록하면 한 경로를 먼저 싣고 나머지 패턴은 다른 동작 뒤에 싣는다. 여유가 있으면 `same_handler_as`로 앞선 등록을 가리킨다. 처리기 공유 여부는 미들웨어·입력 조건과 별개다. 여유 공간이 부족하면 먼저 문서 부가 목록을 줄이고 문서 원문은 보존한다.

문서 검토는 같은 호출에서 `workflow_routes`의 짧은 ID를 수락된 사용자 동작 계약에 선택적으로 연결한다. 상태 변경과 이후 조회처럼 한 계약에 여러 경로가 필요할 수 있으며 전체 응답에서 최대 네 건을 선택한다. 검토 기록에는 최종 수락된 계약 번호와 run·attempt·스냅샷·등록·실제 코드 위치에 묶인 digest만 남는다. 누락하거나 잘못된 선택은 일반 문서 계약·질문을 유지한다. 잘못된 선택은 원시 기록에 `workflow_selection_invalid`로 남는다. 경로 ID와 digest 자체는 인용할 근거가 아니다.

기본 요청과 보충 요청은 문서의 동작을 직접 수행하는 경로를 고르고, 같은 계약의 결과를 확인하는 데 필요할 때 선행 동작과 이후 조회도 함께 고르도록 지시한다. 출력 형식에는 실제 후보 번호나 경로 ID 예시를 넣지 않는다.

전체 조사는 같은 범위와 선별 규칙으로 경로를 다시 확인한 뒤 여섯 줄 창 이내로 처리기와 등록부를 우선 보낸다. 요청에 들어간 실제 발췌의 ID는 해당 계약과 함께 전달한다. 처리기와 이어지는 구현에 아직 읽지 않은 줄이 있으면 기존 위치 선택 후보에 포함할 수 있다. 후속 검토에는 같은 계약과 적용 범위에 해당하는 실제 호출부와 구현 발췌를 사용할 수 있다. 소스에서 확인한 한 가지 호출 구성은 배포 전체의 동작을 입증하지 않는다. 다시 확인하지 못한 근거는 상세의 `workflow_evidence_unavailable`로 남기며, 기존 모델 호출 상한과 새 구현 근거 조건을 적용한다.

처리기가 호출하는 함수가 16줄·1,600바이트 안에 들어가면 선언과 본문 전체를 유지한다. 긴 함수에서는 바깥 블록에 확인된 HTTP 응답이 하나 있고 앞 발췌에 그 응답이 없을 때, 인용할 응답 호출과 앞쪽의 읽기·오류 처리 등 한도 안에 들어오는 문장을 함께 고른다. 표준 HTTP 함수나 실제 `http.ResponseWriter` 매개변수의 쓰기 및 그 매개변수로 만든 JSON·XML 인코더의 호출을 찾는다. 응답 후보가 모호하거나 발췌에 들어가지 않으면 앞 발췌를 유지한다.

호출이 이어지는 구현에서 요청이 읽거나 바꾸는 상태의 소스가 확인되면, 경로가 선택된 뒤에만 결과 발췌를 찾는다. 같은 패키지의 직접 반환 호출과 실제 같은 수신자의 호출, 인자를 직접 호출하는 것으로 확인한 콜백을 최대 두 호출까지 추적한다. 수신자 타입을 확인한 `database/sql`·pgx의 리터럴 SQL 연산과 선언을 확인한 구조체 필드 연산을 읽는다. 호출과 결과 발췌는 각각 최대 16줄·1,600바이트다. 이름에 특정 기능 용어가 나오는지보다 확인한 호출 관계와 실제 연산을 사용한다.

전체 조사에서는 처리기와 등록부를 먼저 배정한다. 전체 여섯 발췌 한도의 남은 자리에서 연결된 호출부와 결과 구현을 함께 담을 수 있을 때 결과 근거를 추가하고, 이어서 적격한 테스트 발췌를 붙일 수 있다. 후속 검토는 같은 계약의 원문 뒤에 연결된 구현을 우선 둔다. 요청에서 필요한 발췌가 모두 연결되면 해당 경로에 `conditional_source_unexecuted`를 표시한다. 실제 실행이 없으므로, 이 표시는 그 조건에서 코드가 시도하는 동작을 읽었다는 뜻이다.

선택된 경로에는 적용 범위와 PR 변경 경계를 지키는 등록부·처리기 디렉터리의 Go 테스트를 최대 32개·512 KiB까지 확인해 테스트 발췌 하나를 붙일 수 있다. 같은 테스트 함수에서 `httptest.NewRequest`나 `http.NewRequest`, 또는 `httptest`에 메서드·경로 인자를 그대로 넘기는 짧은 함수를 찾고, `ServeHTTP`에 전달한 recorder에서 상태·응답 본문·헤더의 구체적 기대값을 확인한다. 확인한 리터럴 경로와 단순 경로 변수에 맞는 등록이 하나일 때 사용한다. 같은 서버를 이용한 변경 요청, 관련 GET과 두 단언을 한 창에 담을 수 있으면 우선한다. 테스트 원문은 최대 28줄·1,600바이트다. 테스트의 통과 여부는 시험 실행 결과가 있을 때 확인한다.

테스트가 성공 상태를 단언한 변경 요청 바로 뒤에 같은 경로 변수 값으로 저장소를 읽고 오류 타입을 단언할 수 있다. 두 처리기가 같은 생성자 인자로 초기화한 필드에서 같은 타입의 경로 키를 사용하고, GET 처리기가 그 조회 메서드와 오류 타입으로 HTTP 응답을 결정할 때 관련 변경으로 연결한다. 조건부 빌드 파일에 있는 단순 필드 반환 접근자도 해당 소스 경로의 단서로 사용할 수 있다. 선택된 GET 처리기와 테스트 원문이 함께 전송됐을 때 `related_mutation`에 테스트가 호출한 변경 경로와 전송된 구현 발췌 ID를 표시한다. 전체 조사에서는 기존 여섯 발췌 한도 안에서 조회 등록·조회 처리기·변경 처리기·테스트를 한 건 먼저 배정한다. 나머지 자리는 다른 처리기와 등록부에 쓴다.

## 모델 입력의 비밀값 선별

검토 역할은 정적 분석 계획의 비밀값 분석 task가 끝난 뒤 실행된다. 각 역할은 시작할 때 그 결과를 읽는다([`screen.go`](../internal/worker/review/screen.go)). 비밀값 분석기 자체는 [분석기](ANALYZERS.md), 비밀정보 정책은 [보안](SECURITY.md)에 있다.

| 비밀값 task 결과 | 처리 |
|---|---|
| 계획되지 않았거나 미실행(`unsupported`/`not_run`) | 선별 없이 보낸다. 기록과 보고서에 `model_input_not_secret_screened`를 남긴다. 조용히 넘어가지 않는다 |
| 실행됐지만 쓸 수 없음(실패, 시간 초과, 취소, 부분 파싱, 산출물 누락·무효) | 검토를 건너뛰지 않는다. 지금까지 읽은 결과와 해석되는 실패·부분 envelope의 관찰 경로가 가리키는 파일은 계속 뺀다(`secret_files_withheld`). 나머지는 기본 읽기 필터만 거쳐 보내고 `model_input_not_secret_screened`를 남긴다. 아무것도 읽을 수 없을 때만 빼는 파일이 없다. 보고서는 미선별과 쓸 수 없던 작업·사유를 적는다 |
| 완전한 파싱으로 성공 | 보고된 파일을 모든 발췌(코드 문맥, 문서, 관찰 창, 검증 확장)에서 뺀다. `secret_files_withheld`를 남긴다 |

- 모든 발췌는 같은 읽기 경로(`readLines`)를 지나므로 새 입력 종류도 같은 선별을 받는다.
- 이와 별도로 민감값 패턴(`record.Sensitive`: 개인 키 블록, `sk-`·`gh?_` 형식 토큰, Authorization 헤더 값, 따옴표로 감싼 api_key·password·client_secret 값)에 걸린 파일은 발췌하지 않는다. 이 패턴은 완전한 비밀 탐지를 보장하지 않는다.
- 모델이 쓴 서술도 같은 패턴에 걸리면 기록에 남지 않는다(`record.SafeText`).

## 인용

코드·테스트 원문은 줄 번호를 붙여 보낸다. 요청에서 각 줄은 `<줄 번호>| <원문>`이다. 줄 번호는 요청을 인코딩할 때만 붙고, 워커가 들고 있는 원문과 검토 기록에는 없다([`record/request.go`](../internal/worker/review/record/request.go), [`citations.go`](../internal/worker/review/citations.go)).

- 모델은 코드·테스트 발췌를 `<근거 ID>:<시작>-<끝>`(한 줄이면 `<근거 ID>:<줄>`)으로 인용한다. 범위는 그 발췌 안이고 80줄 이하다. 80줄보다 긴 발췌(대개 파일 전체 단위)는 범위 없이 인용할 수 없다(`citation_range_missing`). 문서·manifest 근거와 80줄 이하 발췌는 ID만으로 인용할 수 있다.
- 워커는 범위가 보낸 발췌 안에 있는지 확인하고 인용을 그 범위의 근거 ID로 바꾼다. 같은 경로·blob·종류에 (snapshot digest, 경로, blob SHA-256, 행 범위)로 계산한 ID이고 출처 표시는 `cited`다. 후보, 판정, 해석 가설, 강점의 근거와 보고서 발췌는 이 좁힌 범위를 가리킨다. 좁힌 범위도 다른 근거처럼 decoder가 ID와 blob을 다시 계산해 확인한다.
- 범위 형식이 틀리거나, 80줄을 넘거나, 문서 근거에 범위를 붙이면 `citation_range_invalid`다. 범위가 보낸 발췌에 없는 줄을 가리키면 `citation_range_outside`다. 보내지 않은 ID는 기존처럼 `evidence_id_unknown`이다. 모두 형식 복구 요청에 오류 코드로 가고, 그 항목(목록과 번호, verify는 후보 ID)·필드·인용한 발췌 ID도 함께 간다. 보내지 않은 ID는 되돌려 보내지 않는다.
- `citation_range_missing`·`citation_range_invalid`는 실제로 보낸 발췌를 가리키므로 형식 오류다. 복구 뒤에도 남으면 플랫폼이 그 인용을 정리하거나 그 항목을 뺀다. `citation_range_outside`·`evidence_id_unknown`은 무결성 오류다([출력 오류 분류](#출력-오류-분류)).
- 역할 계약 문자열과 복구 규칙은 긴 발췌의 유효한 인용(ID와 범위, 80줄 이하, 요청의 ID 형식을 따른 예시)을 함께 적는다. 이 문구는 지침 팩 밖의 Go 고정 문자열(`citationRule`, `repairRules`)이다.
- 전체 조사의 문서 계약 대조도 후보처럼 인용한 범위를 저장한다([문서 계약 대조](#문서-계약-대조)). 계약 후속 검토의 코드 근거만 범위를 확인한 뒤 발췌의 원래 ID를 저장한다. 후속 검토는 새로 읽은 창 단위로 새 구현 여부를 정하기 때문이다.
- verify는 앞 역할이 좁힌 범위를 인용 발췌로 받고, 그 범위를 다시 좁혀 인용할 수 있다.
- 근거 ID는 위치(경로·blob·행 범위)에 묶이므로 verify가 만든 범위가 앞 역할의 발췌와 정확히 같을 수 있다. 감싸는 선언이 앞 역할이 보낸 단위 전체이거나, 확장 창이 앞 역할의 창이거나, 검증자가 다시 보내지 않은 앞 역할의 창과 같은 줄을 좁혀 인용하는 경우다. 그때 verify는 그 발췌를 앞 역할의 항목 그대로(출처 표시·심볼 포함) 보내고 기록한다. 워커는 기록을 쓰기 전에 이를 확인하고, 어긋나면 그 task를 `failed`(`review_lineage_mismatch`)로 끝낸다. 보고서도 같은 규칙으로 다시 확인한다([`record/lineage.go`](../internal/worker/review/record/lineage.go)).
- 기록에 남는 좁힌 범위(`cited`)는 그것을 담은 발췌가 같은 기록에 있어야 한다. verify는 후보가 인용하지 않은 앞 역할의 좁힌 범위(강점·계약 대조의 범위 등)를 그 범위를 담은 발췌가 요청에 함께 남을 때만 보낸다. 담은 단위를 다시 보내지 않는 파일(후보가 인용하지 않은 긴 파일)이나 예산에서 잘린 단위의 범위는 보내지 않는다. 계약 후속 검토도 앞선 대조가 인용한 범위를 같은 규칙으로 보낸다.

## 문서 계약 대조

전체 조사(`whole_run`)는 수락된 문서 계약을 최대 6건 구현과 대조한다(`contract_comparisons`, [`comparisons.go`](../internal/worker/review/comparisons.go)). 대조는 선택 항목이다. 후보와 강점이 유효하면 대조 하나가 틀렸다고 필수 검토를 잃지 않는다.

- 코드 근거(`code_evidence_ids`)는 후보와 같은 규칙으로 인용하고 좁힌 범위를 저장한다. 80줄보다 긴 발췌는 범위를 붙여야 한다. 범위 없는 긴 단위는 어느 줄이 계약을 구현하는지 말하지 않으므로 형식 복구를 요청한다. 복구 뒤에도 범위가 없거나 틀리면 보낸 발췌 전체를 근거로 다시 검사하고(`citation_range_unspecified`), 통과하지 못하면 그 대조만 뺀다. 같은 단위의 두 범위는 서로 다른 근거다.
- 구현이 인용한 문서 자체이면 안 된다는 규칙과, 문서화된 API의 본문 안이어야 한다는 규칙은 좁힌 범위로 판단한다. 같은 소스 파일에 문서가 있는 API(Java Javadoc, 안내 문서가 가리키는 Python docstring·rustdoc)는 파일 전체 단위가 문서 줄도 담는다. 그래서 단위 전체를 근거로 쓰면 이 규칙을 만족할 수 없고, 본문 줄을 범위로 인용해야 한다.
- 문서 근거(`document_evidence_ids`)는 계약의 `evidence_ids`를 범위 없이 그대로 쓴다.
- 대조 한 건의 거부는 조건마다 고정 코드다. 형식 복구 요청의 `output_errors`에 코드가 가고, `repair.items`에는 목록 `contract_comparisons`와 1부터 세는 대조 번호, 필드 이름, 인용 오류이면 그 발췌 ID, 코드가 간다. 요청 크기를 넘으면 들어가는 만큼만 싣는다. 모델 서술은 어느 쪽에도 넣지 않는다.

## 출력 검사

- 출력은 `workspace_proof`와 `result`를 가진 JSON 객체 하나여야 한다. `result`는 역할 계약의 엄격한 JSON이다. 계약의 목록 key는 모두 배열로 있어야 하고 알 수 없는 필드는 거부한다(`output_schema_invalid`).
- 그 호출에 준 근거·관찰 ID만 인용할 수 있다. 오류 코드: `evidence_id_unknown`, `evidence_id_duplicate`, `evidence_kind_invalid`, `evidence_missing`, `evidence_list_too_long`, `observation_id_unknown`, `evidence_not_at_observation`, `code_evidence_missing`.
- 탐색에서 정한 문서의 적용 경로보다 상위로 넓히면 거부한다(`scope_generalized`, `scope_unknown_path`, `scope_invalid`). 충돌의 두 쪽은 서로 다른 문서를 인용해야 한다(`conflict_same_document`).
- 실행·재현·테스트 통과를 주장하는 서술은 거부한다. 호출 오류 코드는 `execution_claim`이고, 단계 기록에는 `execution_claim_rejected` 한계가 남는다. 이 검사는 정규식 휴리스틱이다. 놓친 주장이 있어도 상태·재현·통계는 구조화 기록에서만 정하므로 모델 서술이 판정을 바꾸지 못한다.
- 서술 필드는 출력 토큰이 정한 JSON 인코딩 바이트 이하다([요청 크기](#요청-크기), 기본 1,200바이트, 최소 출력 예산 400바이트). 요청은 그 3/10 글자 이하의 간결한 한국어를 요구한다(기본 360자, 짧은 문단 하나). 후보는 무엇이 잘못되는지(`title`), 발생 조건(`condition`), 인용한 줄이 실패를 만드는 과정(`mechanism`, 서술 필드의 두 배까지), 영향, 수정이 지켜야 할 속성(`improvement`), 반박 근거나 남은 불확실성(`counterpoint`)을 쓴다. `mechanism`은 선택이다. 기록에 남는 모델 서술은 schema 0.7에서 1,200바이트(`mechanism` 2,400바이트), 이전 schema에서 400바이트 이하이고 민감값 패턴에 걸리지 않아야 한다.
- 환경 메모는 플랫폼 판정을 다시 쓰거나 올리지 못한다. 판정 필드를 붙인 출력은 거부한다.

### 출력 오류 분류

출력 오류 코드는 모두 두 분류 중 하나다([`output_codes.go`](../internal/worker/review/output_codes.go)). 등록하지 않은 코드는 무결성으로 다룬다. 아래 표와 등록이 같은지 `TestOutputCodesMatchTheReviewTable`이 확인하고, 시험이 읽는 모든 기록의 `output_errors`가 등록된 코드인지도 확인한다.

- **무결성.** 플랫폼이 받을 수 없는 내용이다. 요청에 없던 근거·관찰 ID, 보내지 않은 줄, 실행 주장, 넓힌 적용 범위, 플랫폼만 정하는 심각도, 규칙이 요구하는 근거가 없는 판정, 읽을 수 없는 결과가 여기에 든다. 처리는 이전과 같다. 응답을 거부하고 형식 복구 뒤에도 남으면 역할이 실패한다. verify는 그 후보를 격리하고, 선택 항목(강점, 문서 계약 대조)은 그 항목만 뺀다.
- **형식.** 인용한 발췌는 실제로 보낸 것이거나, 항목 하나가 자기 규칙을 어겼다. 형식 복구를 한 번 요청한다. 복구 뒤에도 남거나 복구를 보낼 수 없으면 플랫폼이 그 항목 안에서 정리하거나 그 항목만 빼고, 한계를 남기고 단계를 유지한다. 항목의 형식 오류로 단계를 잃지 않는다.

정리 규칙은 다음과 같다.

- **범위가 없거나 틀린 긴 발췌 인용**(`citation_range_missing`, `citation_range_invalid`). 80줄을 넘는 범위는 자르지 않고 범위를 정하지 않은 인용으로 본다. 자르면 모델이 가리킨 줄이 잘릴 수 있지만 보낸 발췌 전체는 그 줄을 모두 담기 때문이다.
  - verify의 근거·반대 근거: 같은 후보가 인용한 범위가 그 발췌 안에 있으면 그 범위(`citation_range_from_candidate`), 없으면 보낸 발췌 전체(`citation_range_unspecified`)다.
  - 강점, 문서 계약 대조, 계약 후속 검토: 보낸 발췌 전체(`citation_range_unspecified`)다. 정리한 대조는 대조 규칙으로 다시 검사한다.
  - 조사 후보, 해석 가설: 그 항목을 뺀다(`review_candidate_omitted`, `interpretation_items_omitted`). 후보의 근거는 결함이 있는 줄을 가리켜야 하는데 파일 전체는 그 위치를 말하지 않기 때문이다.
  - 문서·manifest 근거에 붙인 범위: 범위를 지우고 그 근거 ID로 받는다(`citation_range_unspecified`). 문서·환경 역할도 이를 요청에 없던 ID가 아니라 이 형식 오류로 본다.
- **반복·초과 인용과 목록**(`evidence_id_duplicate`, `evidence_list_too_long`, `observation_id_duplicate`, `requirement_id_duplicate`, 문서 항목의 `*_evidence_ids_invalid`, `list_too_long`). 반복을 빼고 앞에서부터 한도까지 남긴다(`citation_list_trimmed`, verify 목록은 `verification_list_trimmed`).
- **항목 규칙**(서술, 실패 과정, 근거 누락, 요구 누락, 같은 문서 충돌). 그 항목을 뺀다. 한계는 조사 후보 `review_candidate_omitted`, 해석 `interpretation_items_omitted`, 문서 `document_items_omitted`, 환경 `environment_notes_omitted`다. verify의 조건·가정·다음 확인 항목은 그 항목만 뺀다(`verification_list_trimmed`).
- 정리한 응답의 호출은 `accepted`이고 `output_errors`에 원래 코드를 유지한다. 기록에는 `review_output_degraded`와 정리 한계가 남고, verify는 판정마다 정리 한계를 남긴다. 복구를 보낼 수 없었으면(호출 상한, 요청 크기, 입력) `output_repair_not_sent`도 남는다. 항목을 빼서 역할 규칙(environment·interpret는 항목 하나 이상)을 어기면 응답은 거부된다.
- 형식 오류만 있던 응답은 그 뒤 호출이 실패해도(timeout, 거절, 모델 오류, 두 번째 형식 거부, JSON이 아닌 응답) 정리해 받는다. 취소된 단계는 정리하지 않는다.
- 보고서는 뺀 항목을 그 절의 분석 공백으로 보인다. 후보나 가설을 뺀 보고서는 `no_actionable_findings`를 게시하지 않고 판단 보류로 둔다([보고서 연결](#보고서-연결)).

## 후보 검증과 근거 규칙

- `supported`는 code 또는 test 근거 ID 하나 이상과 성립 조건 하나 이상을 요구한다.
- `refuted`는 반증 근거 ID와 주장이 성립하지 않는 조건을 요구한다. 호출자가 자원을 정리하는 등 유효한 반대 근거가 있으면 후보는 기각되고, 원래 후보와 근거는 보존된다.
- 그 밖에는 `inconclusive`이고 해소하지 못한 가정을 남긴다. 확인하지 못한 조건은 성립 조건이 아니라 남은 가정으로 적는다. 성립 조건이 모두 가정인 후보는 지지할 수 없어 판단 보류가 된다.
- 모델이 `reproduced`를 내면 플랫폼은 `inconclusive`로 내리고 `reproduction_claim_rejected`를 남긴다. 모델이 제출한 실행 결과와 실행 식별자는 증거로 등록할 수 없다. 재현은 플랫폼의 실행 산출물로만 성립한다.
- 심각도는 `high`·`medium`·`low`·`info`만 받는다. `critical`은 실행 근거나 사람의 판단이 필요하므로 모델이 줄 수 없다(`severity_not_assignable`).
- 범주는 `correctness`, `error_handling`, `concurrency`, `resource_lifecycle`, `data_integrity`, `api_contract`, `security`, `maintainability`, `performance`, `test_gap` 중 하나다.
- 후보마다 정확히 한 판정이 있어야 한다. 누락·중복 항목, 모르는 후보 ID는 거부한다. 다음 확인 사항(1~3개)은 명령이 아니라 읽기·검토 단계다.
- 끝내 검증되지 않은 후보는 플랫폼이 `unreviewed`로 표시한다(`verification_quarantined`, `verification_not_completed`, `verification_budget_exceeded`). 형식 오류만 있는 판정은 격리하지 않고 정리해 받으며, 판정의 `limitations`에 정리 내용(`citation_range_from_candidate`, `citation_range_unspecified`, `citation_list_trimmed`, `verification_list_trimmed`)을 남긴다.
- 파일·행·해시 검증은 인용의 출처를 확인할 뿐이다. 인용을 해석한 모델 문장의 의미적 정확성은 [평가](EVALUATION.md)의 판정으로만 잰다.

## 복구 경로

모든 역할에 적용한다. 단계당 호출은 최대 3회(`record.RoleMaxCalls = 3`)이고 문서 계약 후속 검토는 최대 2회다. 각 호출은 attempt의 남은 예산을 확인한다.

1. **형식 복구.** 출력이 JSON이지만 계약·근거 검사에서 거부되면, 고정 오류 코드와 거부된 항목(`repair.items`: 목록, 1부터 세는 번호, 필드, 인용 오류이면 그 발췌 ID, 코드)을 담은 복구 요청을 한 번 보낸다. 요청 크기를 넘으면 항목은 들어가는 만큼만 싣는다. verify는 거부된 후보와 그 오류(`issues`: 필드, 인용 오류이면 그 발췌 ID, 코드), 범위 없이 인용할 수 있는 근거 ID(`accepted_evidence_ids`), 범위를 붙여야만 인용할 수 있는 발췌(`range_required_evidence`)를 다시 보낸다. 모델 서술은 어느 쪽에도 넣지 않는다. 복구 뒤에도 남은 형식 오류는 [출력 오류 분류](#출력-오류-분류)대로 정리한다.
2. **JSON이 아닌 응답의 재시도.** JSON이 아닌 응답은 항목에 대해 아무 정보도 주지 않는다. 형식 복구 기회를 쓰지 않고 한 번 더 요청한다. 재시도 요청은 같은 입력에 복구 규칙과 오류 코드 `output_not_json`을 담은 `repair` 블록을 붙인다. 앞서 복구 요청이 있었으면 그 오류 코드(verify는 후보별 오류)를 유지하고 `output_not_json`을 더한다.
3. **작업공간 확인값 불일치.** 완료 이벤트까지 검사한 모델 응답이 첨부의 확인값 검사를 통과하지 못하면 응답 전체를 버린다. 정리가 확인되고 단계와 attempt에 호출이 남아 있을 때 같은 요청을 새 디렉터리와 새 확인값으로 단계당 한 번 다시 보낸다. 기존 형식 복구가 있었다면 그 요청을 그대로 보낸다. 취소되거나 디렉터리·marker 쓰기, 공급자 호출 또는 정리에 실패하면 이 재시도를 하지 않는다. 원래 호출의 `workspace_unreachable` 사유와 제공된 사용량은 기록한다.
4. **끝.** JSON이 아닌 응답이나 형식 거부가 각각 두 번 발생하거나 호출 상한에 닿으면 다시 보내지 않는다. 그때나 뒤 호출이 실패했을 때 형식 오류만 있던 마지막 응답이 있으면 정리해 받는다(취소 제외). 미수락 응답은 저장하지 않는다. 탐색 사실과 도구 관찰은 남는다.
5. **관찰 ID만 틀린 verify 항목.** 항목의 오류가 `evidence_id_unknown` 하나뿐이고 범위 밖 ID가 모두 그 요청에 플랫폼이 넣은 관찰 ID일 때만, 그 ID를 빼고 같은 검사를 다시 한다. 통과하면 받아들이고 그 호출의 `output_errors`에 `evidence_id_dropped`를 남긴다. 게시되는 판정은 범위 안의 근거만 인용한다.
   - 요청에 없던 ID(지어낸 `ev_…` 등)가 하나라도 있으면 원래 오류로 거부하고 형식 복구로 보낸다.
   - ID를 빼고 통과하지 못하면 원래 오류로 거부한다. 관찰 ID만으로 지지한 항목은 코드 근거가 없어 거부된다.
6. **후속 호출 실패(verify).** 수락한 판정이나 형식 오류만 있는 판정이 하나 이상 있고, 형식 복구나 재시도 호출이 형식 이외의 이유(timeout, 거절, 모델 오류)로 실패하면 수락한 판정을 보존하고 형식 오류만 있던 판정은 정리해 받는다. 그래도 남은 후보는 격리하고 `verification_call_failed` 한계를 남긴다. 그때 task는 `failed`(`review_output_incomplete`)이고 실패 사유는 그 호출의 `outcome`에 남는다. 받을 판정이 없거나 취소이면 단계 전체를 종료한다.
7. **verify 결과.** 일부만 유효하면 사용 가능한 판정을 보존하고 task는 `failed`(`review_output_incomplete`)다. 보고서는 그 판정을 발견에 싣고 격리한 후보만 `unreviewed`로 둔다([보고서 연결](#보고서-연결)). 사용 가능한 판정이 전혀 없으면 `failed`(`review_output_invalid`)다.

## OpenCode 어댑터 계약

모델은 관리형 로컬 OpenCode CLI로 호출한다([`client.go`](../internal/worker/opencode/client.go), [`executor/opencode.go`](../internal/worker/executor/opencode.go)). 실행 규칙(argv, 제한시간, 프로세스 트리 정리)은 [실행](EXECUTION.md)을 따른다. 원격 OpenCode attach나 별도 serve 연결은 구현하지 않았다. 추가할 때는 인증·버전·취소·workspace marker/digest를 대상 환경에서 검증한다.

- **버전.** 시험한 릴리스는 목록이다(`opencode.TestedVersions`). 릴리스마다 근거가 다르다.
  - 1.19.5: 고정 시험·예시가 쓰는 기준 릴리스(`opencode.Version`)다. 관리 설정의 권한 차단(`scripts/test_opencode_policy.py`), 시작 때의 npm 레지스트리 조회, 응답 대기 시간 기본값, 오프라인 모델 목록을 이 릴리스로 측정했다.
  - 1.19.6: 이 머신의 OpenCode가 2026-11-24 08:26(KST)에 스스로 갱신된 릴리스다. 그 뒤 소유자 예산의 실모델 실행(프로젝트 규모 5사례, 48회 호출의 회귀 실행)이 이 릴리스를 거쳤고 모든 호출이 수락됐다. 같은 머신에서 권한 차단 검사, `scripts/test_postgres.py --smokes-only --instance-model`, 가짜 upstream dry run을 통과했다.
  - 갱신을 일으킨 CODEYE 경로는 찾지 못했다. 바이너리의 바뀐 시각(ctime 2026-11-24 08:26:28 KST)에 CODEYE 실행 기록이 없고, 같은 머신에서 사용자 설정(autoupdate 기본값 켬)으로 띄운 `opencode serve`가 그때 실행 중이었다. 모델 호출과 `codeye doctor`의 버전 확인은 관리 설정의 `autoupdate: false`와 `OPENCODE_DISABLE_AUTOUPDATE=1`로 실행한다. `codeye tools`의 버전 확인은 실행별 HOME에서 `--version`만 실행했지만 이 환경변수가 없었다. 2026-11-25부터 이 확인도 같은 변수를 준다. 운영자가 같은 바이너리를 자기 설정으로 띄우면(`opencode serve` 등) OpenCode 기본값으로 갱신될 수 있다. 목록에 없는 릴리스로 바뀌면 다음 호출부터 `opencode_version_untested`가 남는다.
  - 호출마다 먼저 `--version`을 실행하며 확인에는 설정한 호출 제한시간과 30초 중 짧은 값을 적용한다. 실행 중인 버전 확인이 제한시간을 넘기면 모델 호출 전에 `opencode_version_timeout`을 기록한다. 확인과 요청은 호출당 전체 제한시간을 함께 사용한다. 다른 릴리스(`MAJOR.MINOR.PATCH[-…]`)도 실행하고 그 단계 기록에 `opencode_version_untested`를 남긴다. 릴리스 형식이 아닌 응답만 `opencode_version_unsupported`다. `codeye doctor`의 버전 확인은 모델 비용을 쓰지 않는다.
- **운영자 설정.** 실행 파일은 절대 경로다. 모델 ID는 `PROVIDER/MODEL`이다. provider는 소문자·숫자·`._-`, 모델 부분은 영숫자와 `._:@+-/`이고 `.`·`..` 경로 조각은 받지 않는다(라우터식 `vendor/model`은 받는다). 평가용 `codeye-gateway`의 Sol·Terra·Luna 모델은 relay 파일이 있을 때만 쓴다. relay 모델의 출력·문맥 한도는 요청 예산에서 정한다([요청 크기](#요청-크기)). 호출당 제한시간은 `--model-timeout`(기본 600초, 1초~30분)이다. 설정이 없거나 형식이 틀리면 요청을 보내지 않는다(`model_not_configured`). 공급자 변경은 운영자 선택이다([모델 설정](#모델-설정)).
- **작업 디렉터리와 workspace digest.** 요청마다 attempt scratch 아래 새 디렉터리를 만든다. 그 안의 `identity.txt`에 snapshot digest, 요청 digest, 무작위 32바이트 nonce에 묶인 확인값을 쓰고 첨부로 준다. 응답의 `workspace_proof`가 이 값과 다르면 `workspace_unreachable`이다. 프롬프트와 선택된 데이터는 표준 입력으로만 전달한다. 요청 digest는 정확한 메시지 텍스트의 SHA-256이다.
- **권한 차단.** `run --pure`로 실행하고, 실행별 HOME/TMP와 플랫폼이 만든 설정(`OPENCODE_CONFIG_CONTENT`)만 쓴다. 설정은 `permission: deny`, 모든 도구 `false`, share·snapshot·autoupdate·LSP·formatter·plugin 끔, 허용 provider 하나다. 프로젝트 설정, 기본 플러그인, 외부 skill, 모델 목록 조회, LSP 다운로드는 환경변수로 끈다. 사용자 설정과 대상 프로젝트 설정을 읽는 경로를 분리한다. 스냅샷 디렉터리는 보호 루트로 넘긴다.
- **응답 수집.** 한 세션·한 메시지의 완료된 응답만 받는다. `tool_use`·`permission` 이벤트는 `policy_blocked`, `error`는 `model_unavailable`, 세션 불일치·순서 위반은 `model_output_invalid`, 완료 사유가 `stop`이 아니거나 잘린 출력(512 KiB 초과)은 `model_output_incomplete`다. `reasoning` 이벤트는 버린다. 공급자 사용량 제한 메시지는 `model_rate_limited`로만 남긴다.
- **공급자와 인증.** 워커는 선택한 provider와 모델만 요청별 `OPENCODE_CONFIG_CONTENT`에 넣는다. OpenCode의 전송 방식·엔드포인트·인증은 [모델 설정](#모델-설정)을 따른다. 키 값은 argv에 넣지 않으며 실행 기록과 표준 출력·오류에서 가린다. 워커는 격리한 HOME과 환경변수로 실행한다.
- **relay 파일.** 예산 relay를 쓸 때 ready 파일은 일반 파일이고 그룹·기타 권한이 없어야 하며(Windows 제외) 4,096바이트 이하다. `base_url`은 `http://127.0.0.1:PORT/v1`, token은 32~256자다. OpenCode에는 이 임시 로컬 token만 넘기고 실행 기록에서 가린다. 상위 API 키는 relay만 가진다. relay 운영은 [평가](EVALUATION.md)에 있다.
- **취소.** 컨텍스트 취소·제한시간은 프로세스 트리 정리까지 확인한다. 정리를 확인하지 못하면 `recovery_required`로 남기고 작업 디렉터리를 지우지 않는다. 이미 전송된 공급자 추론은 취소 뒤에도 청구될 수 있다. 공급자 측 생성의 확정 중단은 보장하지 않는다.
- **실패 분류.** `opencode run`이 실패하면 JSON 오류 이벤트의 HTTP 상태와 오류 이름만 읽는다. 401·403은 `model_auth_failed`, 404는 `model_not_found`, 429는 `model_rate_limited`, 나머지는 `model_unavailable`이다. 공급자의 오류 문장은 남기지 않는다. OpenCode는 5xx를 몇 번 다시 시도하므로 실패까지 1분 넘게 걸릴 수 있다.
- **직접 확인.** `codeye model probe`는 합성 입력으로 실제 추론을 한 번 요청한다. 비용이 드는 명령이다. 인자 없이(또는 `--config PATH`) 실행하면 서비스 설정에서 `codeye start`와 같은 방법으로 모델을 정해 확인한다. `--executable ABSOLUTE_PATH --model PROVIDER/MODEL [--credential-file PATH | --relay-file PATH]`는 그 설정 그대로 확인한다. `--timeout`(기본 600초), `--json`. 출력은 provider, 모델, OpenCode 버전(시험한 버전인지), 성공 또는 실패한 단계(`configuration`·`credential`·`opencode`·`request`·`output`)와 사유 코드다. 실패하면 종료 코드 1이고, 분석은 그대로 실행된다.
- 네트워크 차단의 OS 수준 강제는 배포 환경에 의존한다([보안](SECURITY.md)).

## 모델 설정

**관리 → OpenCode 연결**에서 서비스 머신의 실행 파일, OpenCode 설정 파일, 인증 파일과 모델을 지정한다. `codeye up` 또는 `codeye start`로 띄운 서비스에서 관리자가 저장하면 다음 분석에 적용된다. **연결 확인**은 저장한 모델에 짧은 합성 요청을 한 번 보낸다. [화면에서 연결하기](GUIDE.md#관리자-화면에서-연결하기)

설정 파일은 OpenCode 1.x의 JSON·JSONC 형식이다. 모델을 비워 두면 파일의 `model`을 쓰고, 값을 입력하면 그 모델을 선택한다. 사내 OpenAI 호환 서버는 선택한 `provider`의 `npm`과 `options.baseURL`로 연결한다. 인증 파일을 함께 지정하면 그 파일의 provider 키를 사용한다. 키 파일은 서비스 계정만 읽을 수 있게 둔다. 관리자가 지정한 모델 연결 항목만 읽으며, 프로젝트의 플러그인이나 도구 권한은 실행 설정으로 가져오지 않는다.

- **에이전트.** `codeye agent --opencode ABSOLUTE_PATH --model PROVIDER/MODEL [--model-credential-file ABSOLUTE_PATH | --model-relay-file ABSOLUTE_PATH] [--model-timeout 600s] [--review-request-bytes N] [--review-output-tokens N]`. 키 파일 경로, 제한시간, 요청 예산은 Hello의 `model_credential_file`, `model_timeout_seconds`, `review_request_bytes`, `review_output_tokens`로 워커에 간다. 키 파일 없이 고른 provider는 키가 필요 없는 경우(OpenCode Zen의 무료 모델)에만 답한다.
- **키 파일 형식.** CODEYE 키 파일 `{"schema_version":"0.1","provider":"openai","api_key":"…","base_url":"…","openai_compatible":false}`(`base_url`·`openai_compatible` 선택, 알 수 없는 필드 거부) 또는 OpenCode의 `auth.json`이다. `auth.json`은 모델 provider의 항목이 `{"type":"api","key":"…"}`일 때만 쓴다(OAuth 항목은 쓰지 않는다). `base_url`은 http·https URL이다. OpenAI 호환 서버, 프록시, 시험용 가짜 upstream에 쓴다.
- **OpenCode 설정 파일을 지정하지 않았을 때의 키.** 순서대로 찾는다. (1) `agent.model.credential_file`, (2) `<state_dir>/secrets/model.json`(0600, 디렉터리 0700), (3) 사용자의 OpenCode `auth.json`(`$XDG_DATA_HOME/opencode/auth.json`, 기본 `~/.local/share/opencode/auth.json`)에서 모델 provider의 `api` 항목. `agent.model.name`이 없으면 (3)은 아래 표의 provider를 표 순서로 찾는다. 환경변수 `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `OPENCODE_API_KEY` 중 처음 있는 것을 `codeye up`이 (2)에 쓴다(`instance.WriteModelSecretFromEnv`). 같은 키면 파일을 다시 쓰지 않는다.
- **OpenCode 설정 파일을 지정하지 않았을 때의 모델.** `agent.model.name`(`PROVIDER/MODEL`, 또는 키 provider의 모델 이름), 없으면 사용자 OpenCode 설정(`~/.config/opencode/opencode.json`, 주석 없는 JSON일 때)의 `model` 중 그 provider의 것, 없으면 provider별 기본값이다. OpenCode 실행 파일은 `agent.model.opencode`, 없으면 `~/.opencode/bin/opencode`, 없으면 PATH의 `opencode`다. 제한시간은 `agent.model.timeout_seconds`(1~1800, 기본 600)다. 요청 예산은 `agent.model.review_request_bytes`(40,000~1,048,576, 기본 262,144)와 `review_output_tokens`(1,536~65,536, 기본 16,384)다.

| provider | 키 환경변수 | 기본 모델 |
|---|---|---|
| `openai` | `OPENAI_API_KEY` | `gpt-6.2-sol` |
| `anthropic` | `ANTHROPIC_API_KEY` | `claude-opus-5-5` |
| `opencode`(OpenCode Zen) | `OPENCODE_API_KEY` | `gpt-6.1-sol` |

- 키를 찾지 못하면 `agent.model`이 없을 때는 모델 없이 시작한다(검토 task `model_not_configured`). `agent.model`이 있는데 그 provider의 키가 없으면 모델 플래그는 넘기되 호출은 실패한다. 키 파일이 있으나 쓸 수 없거나(권한·형식), 기본 모델이 없는 provider에 이름이 없거나, OpenCode를 찾지 못하면 모델 없이 시작한다. 어느 경우든 정적 분석은 실행된다.
- 오프라인 모드에서는 관리자가 명시한 엔드포인트(OpenCode의 `options.baseURL`, CODEYE 키 파일의 `base_url` 또는 relay)를 사용한다. 환경변수의 키를 저장하지 않는다([오프라인 모드](OPERATIONS.md#오프라인-모드)).
- OpenCode는 플러그인을 꺼도 시작할 때 npm 레지스트리에 `@opencode-ai/plugin`을 묻는다(1.19.5 측정). CODEYE는 OpenCode 환경에 `npm_config_registry=http://127.0.0.1:9/`를 넣어 그 요청이 loopback에서 바로 실패하게 한다. `--ca-bundle`이 있으면 `NODE_EXTRA_CA_CERTS` 등 CA 변수도 넣는다.
- `codeye model probe`가 같은 해석으로 확인한다. `codeye up`은 모델 설정(모델 ID와 실행 파일 경로, 지정한 설정·인증 파일 정보)이 마지막 확인과 다를 때 한 번 확인하고 결과를 `<state_dir>/run/model-probe.json`에 둔다(키에서 나온 값은 없다).
- 이 표의 기본값 중 `gpt-6.2-sol`은 OpenCode 1.19.5의 오프라인 모델 목록에 없다. OpenCode가 요청을 OpenAI Responses API(`POST {base_url}/responses`, 스트리밍)로 보내는 것은 가짜 upstream으로 확인했고, OpenAI가 이 요청을 받는지는 실제 확인 한 번으로만 알 수 있다.

## 모델에 보낼 수 있는 소스

| 실행 방식 | 모델 검토 범위 |
|---|---|
| 웹 서비스(`codeye up`) | 플랫폼 계정이 읽을 수 있는 로컬·NFS 폴더와 GitHub·GHES 저장소 및 PR. 에이전트는 `--project-analysis-policy`로 시작하고, 프로젝트의 `send_source_to_model` 선택과 실행자에게 제공한 모델 검토 권한을 적용한다. |
| 루트별 정책으로 직접 시작한 에이전트 | 노드 운영자가 모델 전송 범위를 `--model-source-root ROOT_ID`로 지정한 로컬 루트로 제한한다. 프로젝트의 선택과 실행자에 대한 서비스 제공 범위도 적용한다. |

모델을 연결하지 않은 노드는 `model_not_configured`를 기록한다. 운영자는 서버의 OpenCode 실행 파일과 모델 설정을 지정한다. 저장소 스크립트 실행 권한은 별도로 설정한다. [모델 설정](#모델-설정) · [실행 정책](EXECUTION.md) · [플랫폼 소스 계정](GITHUB.md)

## 검토 기록

검토 task마다 산출물 하나를 role `other`, media type `application/vnd.codeye.review+json`으로 올린다. 크기는 1 MiB 이하다(파일 전체 단위의 근거와 긴 서술 때문에 256 KiB에서 넓혔다). 보고서 registry는 `schema_version`으로 decoder를 고른다. [스키마](../schemas/review-record.schema.json) · [예시](../examples/review/verify.json)(scripted caller로 만든 다섯 단계 기록 중 하나)

공통 규칙:

- 메타데이터와 모델의 판정문·근거 참조만 담는다. 발췌의 원문(`text`), 원시 프롬프트, 내부 추론, 프로세스 출력은 저장하지 않는다.
- 근거(`evidence`)는 `id`, `path`, `sha256`, `start_line`, `end_line`, `kind`, 선택 `origin`과 `symbol`을 가진다. `kind`는 code·test·document·manifest(환경 요구 원문)다. `origin`은 context·caller·test·observation(해석 창)이고, schema 0.7에서 cited(좁힌 인용)·header(나뉜 파일의 머리)·declaration(인용을 감싸는 선언)이 더해진다. document·manifest 근거에는 origin이 없다. 요청에서만 쓰는 `within`과 원문은 기록에 없다.
- decoder(`record.Decode`)는 기록을 그 attempt의 run ID·attempt ID·snapshot manifest digest·단계와 대조한다. 근거마다 ID가 (snapshot digest, 경로, blob SHA-256, 행 범위)에서 다시 계산되는지, 경로가 manifest에 있고 blob이 같은지 확인한다. 모든 참조는 그 기록의 근거 목록 안에 있어야 한다. 허위 경로·행·blob·근거 ID, 다른 run·attempt·snapshot의 기록은 거부된다.
- 사용량이 없으면 `null`이다. 요청을 만들기 전에 실패하면 요청 digest가 빈 문자열일 수 있다.
- 실패한 기록은 시도한 호출, 준 입력, 앞 단계 상태를 남기고 모델 내용은 격리한다. 수락됐다가 버려진 호출의 `outcome`은 `result_discarded`다. verify가 실패하면 후보는 모두 `unreviewed`로 남는다. 일부 후보만 판정하고 실패한 verify(`review_output_incomplete`, `review_input_incomplete`)는 수락 기록을 남기고, 보고서는 그 판정을 싣는다([보고서 연결](#보고서-연결)).
- 보고서가 검토 완료로 판단하려면 DB task 성공과 검증된 역할 기록을 함께 확인한다.

### schema 0.2

- 단계마다 하나이고 자기 호출만 담는다. 필드는 `schema_version`, `pack`(id·version), `snapshot_manifest_digest`, `run_id`, `attempt_id`, `stage`, `outcome`(`accepted`·`failed`), `failure_reason`, `upstream`, `evidence`(최대 40), `observations`(최대 16), 역할별 내용, `limitations`, `calls`다.
- 역할별 내용: environment `environment_notes`, documents `contracts`·`conflicts`·`questions`·`instruction_notes`, investigate·interpret `candidates`(`investigate_1`~`4`, `interpret_1`~`4`), interpret `interpretation_limits`, verify `candidates`(앞 단계 후보 원문)와 `verifications`.
- `upstream`은 입력 하나마다 `source`, `state`(`accepted`·`skipped`·`failed`·`unavailable`), `reason`, 읽은 산출물 바이트의 `sha256`을 가진다. 탐색·도구 산출물과 앞 단계 기록 모두 이렇게 묶는다.
- `calls[]`: `role`, `model`, `opencode_version`, `pack_id`, `pack_version`, `pack_sha256`, `pack_files`, `request_sha256`, `request_bytes`, `usage`, `attempt`(1~3), `outcome`(`accepted`, `output_rejected`, `result_discarded` 또는 실패 사유 코드), `output_errors`.
- 모듈 ID는 `<ecosystem>:<path>`, 요구 ID는 `<kind>@<선언 파일 경로>` 형식이다.

### schema 0.3(slice)

- slice 기록(`review.investigate.sNNN`, `review.verify.sNNN`)만 쓴다. 0.2에 필수 `slice`(`key` `s001`~`s096`, `modules` 1~8개)를 더한 것이다. 단계는 investigate·verify뿐이다.
- slice investigate의 upstream은 `review.scope`도 이름으로 가질 수 있고, slice verify는 `review.investigate.sNNN`과 `review.scope`를 가진다. slice verify의 후보는 investigate 후보뿐이다.
- 0.2 기록에는 `slice`가 없고 `review.scope`·slice upstream을 가질 수 없다. `slice`는 생략 가능 필드라 0.2 기록의 바이트는 그대로다(`TestReviewExampleRecords`).
- decoder는 기록의 slice key와 단계가 task key와 같은지 확인한다(`record.Expect.Slice`).

### schema 0.4(문서 계약)

- 수락된 전체 investigate에 유효한 `contract_probe`가 있으면 0.4를 쓴다. `contract_index`와 선택한 `candidates`의 위치·줄·blob SHA-256, 선택 `literals`를 담는다. 기존 전체 investigate는 0.2를 쓴다.
- 마지막 contract 기록에는 `slice`와 후보·탐색 메모가 없다. `upstream`은 수락된 documents와 전체 investigate를 반드시 참조한다. 입력을 가져온 모듈 검토가 있으면 `review.scope`와 관련 slice 역할 기록을 함께 참조한다.
- 수락 기록의 `contract_comparisons`는 한 건이고 `calls`는 최대 두 건이다. 마지막 대조가 부분 일치이면 `partial_support`의 `matching`과 `violating`에 서로 다른 조건과 각 구현 근거 ID가 필요하다. 실패 기록은 시도한 호출과 발췌 메타데이터를 남긴다. 보고서가 앞선 기록의 digest와 계약 연결을 다시 검사한다. [선행 문서](../examples/review/contract/documents.json) · [선행 조사](../examples/review/contract/investigate.json) · [후속 대조](../examples/review/contract/contract.json)

### schema 0.5(문서의 HTTP 경로 선택)

- 수락된 `documents`에 유효한 경로 선택이 있으면 0.5를 쓴다. `workflow_selections`의 행은 `contract_index`의 오름차순이고 각 행의 `route_digests`는 선택 순서다. 한 계약 안에서 같은 digest를 반복할 수 없고 전체 선택은 네 건 이하다. 0.5 기록의 `evidence`는 문서 발췌다. [기록 예시](../examples/review/documents-workflow.json)
- 문서 계약은 수락됐고 유효한 경로 선택이 없을 때, 확인 가능한 경로가 여섯 건 이상이면 계약과 경로 목록만 담아 보충 요청을 한 번 보낼 수 있다. 문서 검토의 세 호출 안에서 보내고, 전체 조사·도구 해석·검증에 최대 아홉 호출을 남긴다. 보충 요청은 재시도하지 않으며 이미 수락된 문서 원문과 계약을 유지한다. 이 호출을 보낸 기록도 0.5를 쓰며, 기존 문서 응답 뒤에 `calls[].purpose=workflow_selection`으로 실제 요청과 결과를 남긴다.

### schema 0.6(함께 읽은 HTTP 코드와 테스트)

- 수락된 전체 조사에서 선택한 경로의 조회·변경 처리기와 관련 테스트를 실제로 한 요청에 보냈을 때 `workflow_reading` 한 건을 기록한다. 최종 요청에서 조회 등록 또는 세 발췌 중 하나라도 빠지면 생략한다. 기록은 `contract_index`와 선택 경로의 `route_digest`, 서로 다른 `read_evidence_id`·`change_evidence_id`·`test_evidence_id`만 담는다. 문서 기록의 digest, 같은 run·attempt·스냅샷, 원래 계약의 적용 범위, 발췌 종류와 경로를 게시할 때 다시 확인한다.
- 함께 읽은 근거의 위치는 모델이 인용한 대조와 별도로 보존된다. 테스트 발췌는 작성된 단언이다. [선행 문서](../examples/review/documents-workflow-reading.json) · [전체 조사](../examples/review/investigate-workflow-reading.json)

### schema 0.7(줄 번호 인용)

- 줄 번호를 붙여 보내는 워커는 모든 역할과 slice에 0.7을 쓴다. 0.3~0.6의 선택 필드(`slice`, `contract_probe`·`contract_comparisons`, `workflow_selections`, `workflow_reading`)를 같은 규칙으로 가진다.
- 근거는 최대 256개다. 한 근거는 파일 전체 단위일 수 있다. origin에 cited·header·declaration이 더해진다.
- investigate 후보는 최대 16개(`investigate_1`~`16`)이고 verify의 후보와 판정은 최대 20개다. 후보에 선택 `mechanism`(2,400바이트 이하)이 있다. 서술 필드는 1,200바이트, verify의 목록 항목은 1,200바이트 이하다.
- 이전 schema 기록은 이전 한도(근거 40개, 후보 `_1`~`_4`, 서술 400바이트, 새 origin과 `mechanism` 없음)로만 읽는다. 이전 예시의 바이트가 그대로 읽히는지 `TestEarlierSchemaRecordsStayReadable`이 확인한다.
- 보고서 생성기 20부터 0.7 기록을 읽는다(`CitedReviewDecoder`). 서술 상한은 기록을 만든 생성기 버전으로 정한다. [보고서](REPORT.md)
- 형식 오류를 정리해 받은 기록은 `review_output_degraded` 한계를 가진다. 정리한 호출은 `accepted`이면서 `output_errors`에 원래 코드를 남기고, 그 뒤에 실패한 호출이 이어질 수 있다. 호출 순서 검사는 이 한계가 있는 기록에서만 이를 받는다. 필드와 형식이 바뀌지 않았고 이전 기록에는 이 한계가 없어 같은 규칙으로 읽히므로 schema는 0.7을 유지한다.

### schema 0.8(도구 진단 분류)

- 분류 slot의 기록(stage `triage`)과 그 검증 기록(stage `verify`)이다. `slice`는 `{"key":"tNNN","modules":[]}`이다. 전체 역할의 선택 필드(문서 대조, probe, 강점, 경로 선택·읽기, 환경·문서 항목, 해석 한계)는 없다.
- `triage_groups`는 보낸 묶음마다 `id`(`g1`~`g64`), `observation_ids`(최대 256), `context_evidence_ids`, 선택 `cross_tool`, 그리고 `classification`(`problem`은 `candidate_id`, `harmless`는 `reason`과 `evidence_ids`, `unclear`는 `reason`) 또는 `omitted`(`triage_item_rejected`·`triage_item_omitted`·`triage_answer_missing`)를 가진다. 관찰은 묶음 하나에만 들고 보낸 모든 관찰이 묶음에 든다.
- 후보는 `triage_1`~`triage_64`이고 origin `triage`, 묶음과 같은 관찰 ID를 가진다. 관찰 참조는 최대 1,024개다. 분류 기록의 상류는 분석기 task와 `review.interpret`, 검증 기록의 상류는 `review.documents`와 `review.triage.tNNN`이다.
- 보고서 생성기 22부터 읽는다(`TriageReviewDecoder`). [분류 예시](../examples/review/triage/triage.t001.json) · [검증 예시](../examples/review/triage/verify.t001.json)

## 보고서 연결

보고서 규칙의 전체는 [보고서](REPORT.md)에 있다. 검토 기록과 직접 맞물리는 규칙은 다음과 같다.

- 필수 검토 역할은 계획된 `review.*` task의 `required_for_verdict`로 정한다. 하나 이상이고 모두 수락됐을 때만 `ai_review: performed`, 하나도 없으면 `not_performed`다. 생성기 21부터 일부 후보만 판정하고 실패한 verify task(`review_output_incomplete`, `review_input_incomplete`, 전체와 slice)는 결과가 `accepted_incomplete`다. 계보 검사를 통과한 수락 기록의 판정을 발견에 싣고 판정하지 못한 후보만 사유와 함께 `unreviewed`로 둔다. 이 결과는 수락으로 센다. task는 실패로 남으므로 보고서는 `partial`이고 `review_verification_incomplete` 한계와 분석 공백 `role_accepted_incomplete`가 남는다(A59).
- 형식 복구 뒤 뺀 항목은 분석 공백(`review_candidate_omitted`·`interpretation_items_omitted`는 코드 분석, `document_items_omitted`는 문서 분석, `environment_notes_omitted`는 환경 분석)으로 보인다. 후보나 가설을 뺀 보고서는 `no_actionable_findings` 대신 `inconclusive`다. 필수가 아닌 역할은 `coverage.ai_review.optional_tasks`에 결과와 사유를 적고 수행으로 세지 않는다. 검토 task가 없는 계획은 필수 역할이 없다.
- `coverage.review_calls`는 호출마다 `pack_id`·`pack_version`과 호출이 든 task(`task_key`)를 싣는다. 최대 2,013개다. `llm_exposed_files`는 slice 기록이 보낸 경로도 센다.
- 앞 단계·탐색·도구 산출물의 SHA-256, 관찰 ID, verify 후보와 앞 단계 후보가 맞지 않으면 그 단계를 `review_lineage_mismatch:<task>`로 제외한다. verify 근거 중 앞 단계와 ID가 같은 발췌는 앞 단계 항목 그대로여야 한다([인용](#인용)). 같은 발췌가 앞 단계마다 다른 출처 표시(`context`·`observation`)로 올 수 있으므로 어느 한 항목과 같으면 받는다.
- 생성기 22부터 분류 slot의 문제 후보는 발견 `review_tNNN_triage_N`이 되고 그 slot의 검증 판정을 싣는다. 지지된 후보는 조치 항목에 든다. 코드 검토 절의 `diagnostic_triage`는 분류 결과와 수(대상 진단, 분류한 진단, 해석 후보가 다룬 진단)를 보고서 자신의 관찰과 발견에서 센다([보고서](REPORT.md#도구-진단-분류)).
- 모델이 서술한 숫자를 run 상태나 통계로 쓰지 않는다. 도구 관찰과 모델 후보는 서로 다른 산출물이다.

## 시험

- 회귀: `go test -race ./internal/worker/review/... ./internal/worker/run`. 실제 OpenCode와 가짜 upstream으로 `codeye start`의 키 파일 경로 전체(시작, probe, 검토 단계 수락, 키 거부 사유, 시험하지 않은 버전, 키 미노출)를 `python3 scripts/test_postgres.py --smokes-only --instance-model`이 확인한다(비용 없음). 예시와 부정 입력: `python3 scripts/validate_bundle.py`. 일반 CI는 유료 모델을 호출하지 않으며 scripted caller만 쓴다. scripted caller 결과는 플랫폼 검사의 근거이고 지침 품질의 근거가 아니다.
- 실모델 시험은 명시적으로 환경을 준 경우에만 실행한다. `CODEYE_TEST_OPENCODE_BIN`과 `CODEYE_TEST_REVIEW_RELAY`(필요하면 `CODEYE_TEST_REVIEW_MODEL`, `CODEYE_TEST_REVIEW_LEDGER`, `CODEYE_TEST_OPENCODE_MODEL`)를 주고 `go test -v -count=1 -run '^TestLiveVerifier$' ./internal/worker/review`처럼 하나씩 실행한다. 대상은 `TestLiveOpenCode`(키 파일은 `CODEYE_TEST_MODEL_CREDENTIAL`), `TestLiveInFlightCancel`, `TestLiveRelaySlowAnswer`(`internal/worker/opencode`)이다. `TestLiveRelaySlowAnswer`는 비용 없이 relay 뒤에 `scripts/fake_model_upstream.py --delay-seconds 320`을 두고 `CODEYE_TEST_MODEL_TIMEOUT=400s`로 OpenCode의 기본 300초 대기를 넘는 응답이 검토에 닿는지 본다. 검토 역할 전체를 실모델로 돌리는 경로는 회귀 파일럿(`scripts/regression_pilot.py --pilot`, [평가](EVALUATION.md))이다. 비용이 든다. 시험 체계는 [시험](TESTING.md)에 있다.

## 한계

- overview는 문서 계약이나 도구 진단에 관련된 줄과 모듈의 파일 전체 또는 선언 단위를 발췌한다. 후속 검토는 아직 전송하지 않은 줄을 다루며 호출·요청·slot 상한이 남은 줄을 결정한다.
- 모델은 도구를 쓰지 않는다. 요청에 없는 파일을 직접 열거나 검색하지 못하므로 한 요청의 단위 밖에 있는 호출 관계는 verify 확장과 slice로만 보인다.
- 선언 경계 판별은 Go 외 언어에서 구문 분석이 아니다. 매크로·전처리·비정형 들여쓰기에서는 경계가 덜 정확할 수 있다. C/C++ 전처리 분기는 첫 분기의 깊이를 따르므로, 분기마다 중괄호 균형이 다르고 대안 관계도 아닌 코드는 경계를 잃을 수 있다. JavaScript 정규식 리터럴은 앞 문자로 짐작하므로 `)` 뒤의 정규식(`if (x) /re/.test(s)`)은 나눗셈으로 읽는다.
- 보고서 검증기는 schema 0.7 조사 기록이 HTTP 코드와 테스트를 함께 읽었는지(`workflow_reading`) 보고서 본문만으로 알 수 없다. 0.6 기록은 그 읽기가 있을 때만 쓰였으므로 decoder 이름이 증거였지만, 0.7은 모든 역할이 쓴다. 그래서 문서 대조의 관련 흐름은 0.7 조사 산출물이 수락되었고 세 인용(호출 코드, 변경 코드, 테스트)이 같은 범위의 Go 근거일 때 받는다. 보고서 생성기는 기록의 `workflow_reading`이 있을 때만 관련 흐름을 만들고 문서 기록과 대조한다([보고서 연결](#보고서-연결)).
- 보고서의 표시용 발췌는 인용의 첫 50줄·1,800바이트까지다. 80줄까지의 인용은 근거 범위 전체가 기록에 남지만 화면에는 앞부분만 보인다([보고서](REPORT.md)).
- 큰 요청 예산의 실제 모델 품질·지연 시간·비용은 측정하지 않았다. 제한시간 600초와 기본 예산은 추정이며 실제 호출을 보고 다시 정한다(A58).
- 동적 디스패치와 실제 빌드·런타임 구성이 결정하는 호출은 제공된 발췌와 실행 기록으로 판단한다. 정적으로 연결한 지원 범위는 [파일 사이의 호출 근거](#파일-사이의-호출-근거)에 있다.
- 실행·재현 주장 거부와 민감값 패턴은 정규식이다. 다른 표현을 모두 잡지 못한다.
- 미완료가 사라진다는 보장은 없다. 끝내 검증되지 않은 후보는 `unreviewed`로 격리하고 task는 실패한다.
- 범위 없는 긴 발췌를 반대 근거로 인용한 verify 판정은 복구 뒤 그 후보가 인용한 범위로 정리된다(`citation_range_from_candidate`). 그 범위가 반박하는 줄을 담는다는 보장은 없다. 판정과 인용은 그대로 보이고 한계 코드가 정리했다는 사실을 밝힌다. 그 범위가 없으면 발췌 전체(`citation_range_unspecified`)라 위치가 덜 정확하다.
- 분류는 코드 단위다. 한 코드가 여러 원인을 묶으면(예: `text_invalid`는 서술 한도와 민감값 패턴) 같은 처리를 받는다. 형식 정리의 실제 모델 응답 빈도와 정리한 항목의 품질은 측정하지 않았다.
- 형식 오류로 항목을 모두 빼면 environment·interpret는 항목이 하나 이상이어야 하므로 응답을 거부하고 그 역할이 실패한다. 두 역할은 필수가 아니어서 AI 검토 상태는 바뀌지 않지만, 해석 가설은 검증으로 이어지지 않는다.
- 역할 계약 문자열의 인용 예시(`ev_5f0c2a9e1b7d4c3a8e6f2b10:120-134`)는 요청에 없는 ID다. 모델이 예시를 그대로 옮기면 무결성 오류(`evidence_id_unknown`)다.
- `roleRules`는 "근거·관찰 ID"를 인용하라고 하고 verify 계약은 "근거 ID"만 말한다. 이 어긋남은 구조(관찰 ID 처리 규칙)로 막았고, 문구 정리는 다음 지침 개정에서 독립 작성자가 판단한다.
- 모델의 자신감과 서술은 측정된 정확도가 아니다. 품질은 [평가](EVALUATION.md)의 판정과 지표로만 말한다.
