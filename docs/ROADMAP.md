# 로드맵

다음에 할 일과 순서, 각 작업의 완료 조건을 정한다. 끝난 작업은 이 문서에서 지우고 변경 기록에 적는다. 아래는 소유자가 승인한 계획이며 완료된 작업이 아니다. 범위와 착수는 소유자가 정한다. 이미 끝난 작업의 이력은 [변경 기록](../CHANGELOG.md), 지금 제공하는 기능은 [요구사항](REQUIREMENTS.md)의 현재 제공 범위에 있다.

## 진행 원칙

- 작업마다 구현·검증·CI 통과·병합까지 끝낸 뒤 다음 작업을 시작한다. 구현 설명만 있고 실제 시험 결과가 없으면 완료로 처리하지 않는다.
- 코드 시험 결과와 제품 분석 정확도 평가는 별도 결과로 보고한다. 경고 수나 모델 호출 수의 증가를 품질 향상으로 발표하지 않는다([평가](EVALUATION.md)).
- 한 머신에서 별도 노드 신원 둘로 한 시험은 여러 물리 머신·NFS·network partition 보증을 대신하지 않는다. 개발에 쓰지 않은 OS(Windows 11, RHEL 8.10)의 시험은 미실행으로 명시한다.
- '언어별 지원'은 탐색·기본·정밀·실행 검증 수준을 나누어 표시한다. 공통 탐색만 된 언어를 정밀 지원이라고 하지 않는다.
- 기존 CI 통합과 의존성 CVE 검사를 어떤 작업에도 끼워 넣지 않는다. 제품 범위 변경은 소유자 결정이 필요하다.
- API·schema를 바꾸는 PR은 호환 가능한 응답·예시·검증 스크립트·migration 필요 여부를 함께 검토한다([시험](TESTING.md), [결정 기록](DECISIONS.md)의 변경 절차).
- 지침 개정은 검토 지침(`prompts/review`) 하나에 하고 기본 회귀 집합(`fixtures/regression/`)으로 검증한다. 보류 평가 자료를 읽지 않는 규칙은 [평가](EVALUATION.md)를 따른다.

## 순서

지금의 우선순위는 쉽게 쓸 수 있는 것과 분석 품질이다. 소유자가 자기 머신에서 자기 프로젝트와 GitHub.com 저장소를 실제로 분석해 볼 수 있게 만드는 일이 먼저이고, 보안 강화와 분산 운영은 그다음이다. 사용을 막는 관문 대신 한계를 보고서에 기록하는 허용적인 기본값을 쓴다.

| 작업 | 선행 |
|---|---|
| GitHub 연결(App) | 없음 |
| GitHub App 설치 토큰으로 PR·댓글 검증 | GitHub 연결(App) |
| 다중 노드 검증 | 없음. GitHub 연결·PR·댓글 분석과 병행 |
| 폐쇄망 실기 확인 | 다중 노드 검증 |
| 운영 수용 | PR·댓글 분석, 폐쇄망 실기 확인 |

## 분석 품질 개선

소유자가 승인한 순서다(표의 위에서 아래로). 아직 끝난 작업이 아니며 앞 작업의 측정 결과를 보고 다음 작업의 범위를 정한다. 비교는 [프로젝트 규모 결함 집합](EVALUATION.md#프로젝트-규모-결함-집합)과 기존 회귀 집합으로 하고, 같은 모델·호출 상한의 전후 결과를 [평가 결과](EVALUATION-RESULTS.md)에 남긴다. 의존성 CVE 검사는 계속 범위 밖이다.

| 작업 | 선행 |
|---|---|
| 현재 빌드가 놓치는 결함의 발견(관점별 조사, 읽기 전용 소스 탐색, 진단 단서 추적) | 소유자가 정한 모델 예산(유료 회귀 실행)과 새 사례 집합 |
| 새 봉인 사례 집합 | 없음(모델 예산 불필요) |
| 쓰지 않는 코드 단서의 추적 정밀도와 `inconclusive` 답(검토 지침) | 소유자가 정한 모델 예산(유료 회귀 실행) |
| 새 플랫폼 경로의 실모델 관찰 | 다음 유료 실행과 함께 |
| 남은 출력 오류의 항목별 처리, 보고서 검사 보강, 최소 요청 예산의 서술 한도, 분류 묶음의 부분 분류 | 없음 |
| 비밀정보 선별의 단위(파일 전체 제외) | 없음 |
| Opengrep 규칙의 기본 심각도 상한을 올릴 근거 | 실제 애플리케이션에서 잰 보고 전용 근거 |
| Java 전이 classpath, Meson·autotools compile DB | 없음 |
| PR 인라인 댓글과 diff의 모델 입력, 예산 relay를 거치는 병렬 호출 | 없음 |

### 현재 빌드가 놓치는 결함의 발견

봉인한 holdout 분할의 짝 측정은 라벨 결함의 발견이 나아졌다는 것을 사전 기준으로 구분하지 못했다. 현재 빌드가 처음 보는 라벨 결함을 찾지 못하는 사례가 남아 있고 오탐은 줄지 않았다([평가 결과](EVALUATION-RESULTS.md#봉인-보류-분할의-짝-측정품질-작업-전-빌드와-현재-main)). 요청을 반으로 줄여도 같은 결함을 찾지 못한 앞선 실험이 있으므로([요청 예산 실험](EVALUATION-RESULTS.md#요청-예산-실험)), 입력 크기가 아닌 조사 방식이 남은 후보다. 후보는 셋이고 각각 유료 회귀 실행과 새 사례에서의 측정이 필요하다. dev 분할은 일부가 조정에 쓰였고 holdout은 소진됐으므로 이 작업의 효과는 둘 어느 쪽에서도 입증할 수 없다.

후보:
- 관점을 나눈 조사: 같은 코드를 오류 처리·자원 수명·동시성·경계 같은 관점별로 따로 읽는다.
- 모델의 읽기 전용 소스 탐색: 파일 사이의 원인을 스냅샷 안에서 더 찾아볼 수 있게 한다. 탐색은 스냅샷 밖을 읽지 않는다.
- 도구 진단 단서의 더 정밀한 추적: 쓰지 않는 값이나 중복 같은 진단이 가리키는 원인을 따라간다.

완료 조건:
- 후보마다 같은 모델·호출 상한에서 탐색 호출·읽은 줄 수와 비용을 기록하고, 새 사례(아래 새 봉인 사례 집합)에서 현재 빌드와 비교한 라벨 결함 발견·오탐 변화를 블라인드 판정으로 보고한다.
- 시험을 문맥으로 쓰는 문서 대조·검증의 근거는 줄지 않아야 한다.
- 개정 작성자는 평가 결과와 보류·dev 자료를 읽지 않는다([평가](EVALUATION.md#보류-독립성)).

### 새 봉인 사례 집합

프로젝트 규모 holdout이 소진되어 처음 보는 사례가 남아 있지 않다. 위 작업과 앞으로의 개선을 독립적으로 판단하려면 새 사례로 새 봉인을 만들어야 한다.

완료 조건:
- 사례 선정 규칙(저장소와 결함 계열이 기존 분할과 겹치지 않음 등)을 사례를 하나라도 고르기 전에 문서로 적는다.
- 후보 사례에 제품을 실행해 보고 사례를 고르지 않는다.
- 사례를 만드는 사람은 검토 지침이나 기능의 작성자가 아니고 어떤 평가 결과도 읽지 않는다.
- 봉인 digest와 기준 빌드의 SHA를 [평가](EVALUATION.md#보류-집합과-봉인)의 표와 `scripts/bundle_checks/docs.py`에 기록한다.
- 사례 수는 짝 비교로 차이를 가릴 수 있는 크기여야 한다. 짝은 적어도 열두 개를 목표로 한다. 사전 기준은 이번 짝 측정의 규칙을 그대로 쓰지 않고 새 크기에 맞춰(예: 짝 부호 검정의 임계값) 정하고, 그 크기로 가릴 수 있는 차이의 크기를 적는다.
- 기준 문서를 첫 유료 호출 전에 해시해 잠그고, 사례를 먼저 정한 뒤 결과를 보고 바꾸지 않는다([유료 batch 절차](EVALUATION.md#유료-batch-절차)).
- 같은 실행에서 시험·예제 경로의 게시 발견 수와 해석 가설의 수·질, 도구 진단 분류의 남은 측정(라벨 위치를 가리키는 진단이 조치 항목에 남는지, 경로 규칙으로 낮춘 시험 코드 진단 가운데 실제 문제였던 수, 분류하지 않은 진단 수)을 본다. 보고서 읽기 과제로 독자가 조치할 항목을 찾는지 확인한다.

### 검토 지침의 후속

지침 2.10.0 측정에서 남은 두 가지 약점이다. 쓰지 않는 값·중복 코드 진단을 단서로 읽을 때 원인 분기와 발생 조건의 추적이 틀리는 경우가 있고, 검증이 스냅샷으로 답할 수 있는 질문에 `inconclusive`로 답하는 경우가 있다. 측정 기록은 평가 결과에 있고 지침 작성자는 읽지 않는다.

완료 조건:
- 쓰지 않는 코드 단서를 따라가는 정밀도(어느 분기·어느 입력이 값을 쓰지 않는지)와, 스냅샷의 소스로 답할 수 있는 질문에 `inconclusive`로 답하는 빈도를 줄이는 지침 개정을 검토 지침(`prompts/review`) 하나에 한다.
- 합성 회귀 집합을 실모델로 한 번 실행해 기존 역할의 회귀가 없는지 확인하고, 두 약점이 줄었는지 측정한다. 이 일은 소유자가 정한 모델 예산이 있어야 하고, 개정 작성자는 평가 결과와 보류·dev 자료를 읽지 않는다([평가](EVALUATION.md#보류-독립성)).
- 합성 회귀 집합에는 도구 진단이 없어 분류가 회귀 시험을 받지 않는다. 도구 진단이 있는 합성 사례를 더할지 정한다.

### 새 플랫폼 경로의 실모델 관찰

후보를 검증에 보내지 않는 경로, 판단 불가 답의 복구, 묶음의 부분 위치 답은 실모델이 한 번도 일으키지 않았고 가짜 upstream으로만 확인했다.

완료 조건:
- 가짜 upstream의 형식·무결성 오류 주입 시험을 유지하고, 새 실모델 실행의 거부 코드와 제약을 기록해 세 경로가 실제로 나타나는지 본다. 나타나면 복구가 의도대로 동작했는지 기록에서 확인한다.

### 남은 출력 오류 처리와 보고서 검사

모델 출력의 형식 오류는 항목별로 처리하지만([출력 오류 분류](REVIEW.md#출력-오류-분류)) 처리하지 못한 곳이 남아 있다.

완료 조건:
- interpret와 environment는 모든 항목이 빠지면 여전히 단계 전체가 실패한다. 항목이 모두 빠졌을 때의 처리를 정하고 시험한다.
- 계약 후속 단계는 거부 사유를 하나의 코드로만 남긴다. 거부 조건마다 고유 코드를 두고 복구 요청이 그 코드를 쓰게 한다.
- 약해진 워크플로 읽기(`workflow_reading`) 보고서 검사를 새 입력 구성에서도 구조로 확인하도록 다시 세운다.
- 최소 요청 예산에서 서술(발생 조건·영향 등)의 한도가 어떻게 적용되는지 확인하고 시험으로 고정한다.
- 도구 진단 분류에서 실제 문제와 무해한 진단이 한 묶음에 섞이면 묶음 전체가 `harmless`로 분류될 수 있다(위치별 부분 분류가 있으나 모델이 쓰지 않았다). 묶음의 진단이 서로 다를 때 부분 분류로 이끄는 방법(플랫폼 검사 또는 분류 지침)을 정하고 새 사례에서 측정한다. 다른 묶음에서 문제로 분류된 위치를 `harmless` 묶음이 포함하면 플랫폼이 알아채는지 확인한다.

### Opengrep 심각도 상한의 근거

실제 애플리케이션 27개에서 Opengrep 진단 10건 중 실제 흐름이 없어 기본 심각도 상한을 낮춰 두었다([측정](ANALYZERS.md#opengrep-규칙-측정)).

완료 조건:
- 상한을 올리려면 실제 애플리케이션에서 잰 보고 전용 근거를 먼저 기록한다. 근거가 없으면 상한을 올리지 않는다.

### 빌드 문맥과 추가 분석 입력

Java의 전이 의존성을 포함한 classpath 해석, Meson·autotools `configure`·`bear`로 감싼 make의 compile DB를 더한다. CMake 프로젝트의 compile DB 생성, 허가받은 Rust build script의 시스템 C 도구 경로, dependency-cruiser 외부 대상 해석은 [compile DB 생성](ANALYZERS.md#compile-db-생성)·[Rust 환경](ANALYZERS.md#rust-환경)에, SARIF 입력 어댑터(팩 안의 도구 출력만)와 파일 안 taint 규칙은 [Opengrep 패턴·taint 팩](ANALYZERS.md#opengrep-패턴taint-팩)에 반영했다. taint 규칙의 측정과 남은 공백(파일 사이 흐름, 매크로 뒤의 호출, 검증 분기, 애플리케이션에서 찾은 실제 결함 0건)은 [측정](ANALYZERS.md#opengrep-규칙-측정)에 있다.

완료 조건:
- 해당 언어 사례의 tools 조건 위치 지표와 분석기 공백 task 변화를 기록한다.

### PR 인라인 댓글과 relay의 병렬 호출

PR 분석에서 변경 줄에 인라인 댓글을 달고 diff를 모델 입력에 넣는다. 검토 쌍은 정해진 병렬도로 함께 실행한다([호출 상한과 승인](REVIEW.md#호출-상한과-승인)). 예산 relay는 요청을 하나씩 처리하므로 relay를 쓰는 노드와 유료 평가 실행은 아직 직렬이다.

완료 조건:
- 실제 GitHub.com PR에서 인라인 댓글 게시와 재시도·중복 방지를 확인한다.
- relay가 요청을 함께 처리할 때 예산 장부의 상한과 사례별 귀속을 지키는지 시험한다.

### 비밀정보 선별의 단위

비밀 스캐너가 파일의 몇 줄만 표시해도 그 소스 파일 전체를 검토에서 뺀다. 이때 범위 장부는 그 파일을 검토한 줄 0으로 보인다.

완료 조건:
- 표시된 줄과 그 주변만 모델 입력에서 빼고 나머지 줄은 검토 대상으로 남기는 단위를 정하고 시험한다. 뺀 줄 범위는 장부에 비밀정보 제외로 보인다. 비밀값·일부·hash는 어디에도 남기지 않는다.

## 여러 사용자·GitHub 연동·분산 운영

수동·예약 분석과 저장소 웹훅은 설치에 지정한 플랫폼 GitHub 계정을 사용한다. 아래 두 작업은 조직 단위 GitHub App으로 연결하는 경로다. 현재 PR 고정과 댓글 outbox를 함께 사용한다. [GitHub 연결](GITHUB.md)

### GitHub 연결

실제 GitHub.com App으로 연결한다. 웹 사용자는 이메일·비밀번호로 로그인한다. 이벤트는 webhook 수신과, 외부에서 들어올 주소가 없는 호스트를 위한 polling 방식 둘로 받는다. GHES는 같은 계약을 따르지만 시험하지 않은 상태로 둔다. 계약은 [GitHub 연결](GITHUB.md)에 있다.

완료 조건:
- 연결 가이드와 최소 권한(내용 읽기, PR 읽기, 결과 댓글 쓰기). Checks/Actions 권한을 요구하지 않는다. 플랫폼이 Git 권한을 자동으로 바꾸지 않는다.
- 연결 상태 `repository_readable`·`branch_resolvable`·`webhook_verified`·`pr_readable`·`comment_writable`·`report_url_reachable`을 각각 진단한다. webhook이 없어도 읽기가 되면 수동·예약 분석이 동작한다(TC-27).
- App 설치 ID와 대상 저장소·프로젝트 권한을 검증하고 저장소 웹훅의 서명 검사와 영속 큐를 재사용한다. 실제 App에서 전달과 재전송을 검증한다.
- polling(제안, 아직 명세 없음): webhook과 같은 dedupe와 작업 의도 저장을 거치고, 놓친 이벤트를 무제한 따라잡지 않는다. 주기·조회 범위·rate limit 처리는 이 작업에서 명세한다.
- App private key와 게시 credential은 관리 서버만 갖는다. 노드에는 저장소·기간이 제한된 읽기 credential만 주고 checkout 뒤 제거한다. 다른 호스트 인증으로 fallback하지 않는다.

개발 머신에서 검증할 수 없는 것(GHES)은 [아래 목록](#실제-환경에서만-검증할-수-있는-것)에 있다.

### PR·댓글 분석

플랫폼 계정의 PR 이벤트와 멘션 처리, 원본 저장소·작성자 확인, 중복 전달 처리와 결과 댓글은 [저장소 웹훅](GITHUB.md#저장소-웹훅)을 따른다. 남은 검증은 실제 GitHub.com·GHES 인스턴스에서 배달 지연과 권한 철회를 확인하는 일이다. GitHub App 설치 토큰을 추가할 때도 같은 프로젝트 귀속과 실행 중복 방지 규칙을 사용한다.

### 다중 노드 검증

한 호스트의 노드 신원 여럿으로 배정·대기·노드 사망·분할·drain·에이전트 갱신과 `recovery_required` 정리 확인을 구현·시험했다([실행](EXECUTION.md#여러-노드에서-확인한-것), TC-250~254). 남은 것:

- 노드마다 다른 NFS 접근 권한·경로 차이의 처리.
- 노드별 Git 자격증명·CA 구성에 더해 실행 단위 자격증명 전달과 노드 간 스냅샷 이동이 필요한지 결정(A16의 후속 항목).
- 언어·도구 단위 배정이 필요한지의 결정(지금은 도구가 배정 기준이 아니다, A51).

나머지는 [실제 환경에서만 검증할 수 있는 것](#실제-환경에서만-검증할-수-있는-것)이다.

### 폐쇄망 실기 확인

배포팩·오프라인 모드·사내 CA는 구현했다([운영](OPERATIONS.md#폐쇄망-배포팩), [변경 기록](../CHANGELOG.md)). 개발 머신에서는 사설 CA·로컬 미러·network namespace로만 확인했다. 남은 것은 실제 환경이 있어야 하는 일이다.

완료 조건:
- 내부 미러와 회사 CA가 있는 RHEL 8.10에서 묶음을 풀고 `codeye up --offline`으로 여섯 언어군의 프로젝트를 분석한다. 실행 파일은 정적이지만 PostgreSQL·분석 도구·OpenCode의 glibc·시스템 라이브러리 호환은 그 머신에서 확인한다.
- 실제 폐쇄망에서 방화벽 기록으로 CODEYE·OpenCode·도구가 설정 밖으로 접속하지 않음을 확인한다(TC-30).
- 사내 레지스트리 설정이 없는 cargo의 미러 경로와 CA(`CARGO_HTTP_CAINFO`) 확인. 사내 서명 체계에 맞춘 묶음 서명.

개발 머신에서 검증할 수 없는 것은 [아래 목록](#실제-환경에서만-검증할-수-있는-것)에 있다.

### 운영 수용

여러 사용자에게 공개하기 전 마지막 작업이다.

한 호스트의 장애 훈련(모델 endpoint 실패, 노드 offline, DB 중단, 도구 버전 변경·사라짐, max workers 축소, 저장 상한, 실행 중 백업·복원, 사용자·구성원·노드 권한 철회)과 정리 확인 명령, 보존 정리, systemd 사용자 unit을 마쳤다([운영](OPERATIONS.md#장애-대응-runbook), TC-246~255, A48~A50). 남은 완료 조건:
- 실제 데이터 규모에서 백업·복원 시험과 목표 시간 결정.
- GitHub App 권한 철회 훈련(GitHub 연결 뒤).
- NFS 지연 훈련.
- 품질 baseline과 제한 사항 문서. 측정하지 않은 정확도를 주장하지 않는다.

## 실제 환경에서만 검증할 수 있는 것

개발 머신(WSL2 호스트 하나)에서는 확인할 수 없는 것을 한곳에 모은다. 실제 환경이 생기면 시험하고, 실행하지 않았으면 미실행으로 남긴다. 대신 확인한 것은 그 보증을 대신하지 않는다.

| 항목 | 관련 작업 | 개발 머신에서 대신 확인한 것 |
|---|---|---|
| 여러 물리 노드(서로 다른 머신의 시계·디스크·프로세스 공간) | 다중 노드 검증 | 한 호스트의 노드 신원 8개(TC-250~254) |
| 실제 network partition(패킷 손실, 반쪽 연결, 한쪽만 끊김) | 다중 노드 검증 | 로컬 TCP 프록시 차단(TC-252) |
| 사내 NFS의 지연·ACL·잠금 및 장애 복구 | 다중 노드 검증, 운영 수용 | WSL2의 읽기 전용 NFSv4.1에서 플랫폼 UID로 읽어 보고서를 게시했다. [소스 확보 시험](TESTING.md#소스-확보) |
| RHEL 8.10(커널 4.18의 `pidfd` 부재 경로, PostgreSQL·분석 도구·OpenCode의 glibc·시스템 라이브러리 호환) | 폐쇄망 실기 확인 | 정적 실행 파일 기동, Red Hat UBI 8.10 사용자 공간에서 웹·보고서 게시 |
| 실제 폐쇄망, 내부 미러·회사 CA에서 `codeye up --offline`로 여섯 언어군 분석, 방화벽 기록(TC-30) | 폐쇄망 실기 확인 | 사설 CA·로컬 미러·network namespace(TC-240~245) |
| cargo의 사내 미러 경로와 CA(`CARGO_HTTP_CAINFO`), 사내 서명 체계에 맞춘 묶음 서명 | 폐쇄망 실기 확인 | 없음 |
| 회사 SSO 계정의 권한 철회 | 운영 수용 | 로컬 사용자·구성원·노드 token 철회(TC-255 D8) |
| GHES 인스턴스(버전·허용 API·PR·댓글 API 권한 차이) | GitHub 연결, PR·댓글 분석 | 가짜 GitHub API |
| 재부팅·로그아웃 뒤 사용자 unit 유지 | 운영 수용 | WSL2 사용자 systemd의 start·stop(TC-249) |
| 실제 데이터 규모의 백업·복원과 목표 시간 | 운영 수용 | 작은 데이터의 실행 중 백업·복원(TC-255 D7) |

## 분석 내용과 보고서의 다음 개선

여섯 언어군의 문서 대조에 확인한 파일 간 직접 호출과 구현 위치를 활용한다. `with-tests`에서는 코드가 인용한 기존 테스트의 줄과 실제 실행 결과를 대조한다. 다음 정밀도 개선은 공개 함수의 동적 호출, 프레임워크에서 주입한 구현, 선택하지 않은 빌드 조건처럼 근거가 끊긴 지점에 집중한다. [언어별 사용 범위](GUIDE.md#언어별-분석과-테스트) · [모델 검토](REVIEW.md#한계)

| 우선순위 | 개선할 부분 | 다음 판단에 쓸 근거 |
|---|---|---|
| 1 | 문서에서 고른 동작이 여러 파일에 걸칠 때, 누락된 결정 분기와 호출부·테스트를 추가로 찾는다. 특히 조회 실패, 복구, 데이터 저장처럼 사용자가 결과를 구별해야 하는 경로의 끝을 확인한다. | 서로 다른 프로젝트의 입력 양식 호환, 구매 가격 계산, 세션 재접속처럼 파일 하나로 답하기 어려운 과업에서 문서의 약속, 실제 조건문, 호출부 또는 테스트의 단언을 추적한다. 전달한 파일 수와 판단할 수 있었던 질문 수를 구분한다. |
| 2 | 처음 읽는 사람에게는 해당 버전에서 가능한 동작과 유지할 이유를, 유지보수자에게는 확인할 조건·영향·근거를 보여준다. | 프로젝트별 새 독자가 화면에서 대상과 핵심 동작을 찾고, 근거를 연 뒤 판단이 바뀌는 조건과 다음 확인 방법을 설명하는지 시험한다. 적절한 결론이 ‘변경할 필요 없음’인 사례도 포함한다. |
| 3 | 여러 모듈에 걸치는 권한 변경과 세션 재접속을 추적한다. 공유 해제 후 기존 보고서를 열 때의 권한 재검사, 터미널 재접속 시 살아 있는 셸과 입력 소유권을 결정하는 경로처럼 결과를 바꾸는 조건을 찾는다. | 서로 다른 두 계정의 공유 전후 열람 결과, 화면을 닫고 다시 연 뒤의 셸 상태와 입력 승인 여부를 비교한다. 보고서가 인용한 테스트와 평가자가 실제로 실행한 시험을 구별한다. |

긴 안내 문서에서 기존 API 발췌 뒤에 남은 예산을 첫 발췌와 API 절 사이의 본문에도 쓰면 실제로 답할 수 있는 빌드·런타임 질문이 늘어나는지 같은 모델·커밋·예산으로 확인한다. 번역된 계약은 원문의 정확한 문장 범위와 연결해 호출부나 단언이 없는 어휘 일치를 과대 평가하지 않는지 확인한다.

## 후속 선택 작업

필요할 때 별도 작업으로 만든다. 순서는 정하지 않았다.

- Container 실행기(ContainerExecutor). Native 실행을 대체하지 않는 선택 실행기다.
- 고비용 interfile 분석.
- 추가 OS(Windows의 `codeye up`·`start`·`stop` 포함).
- 인프라 용량 공급자(CapacityProvider): 클라우드 VM 생성·삭제는 초기 범위 밖이다.
- 문서에서 찾은 주요 사용 경로에 대한 E2E·부하 검증을 계획하고 필요한 테스트 서비스를 준비해 결과를 연결한다. 현재 `with-tests`는 프로젝트가 이미 선언한 npm E2E 스크립트 등을 실행한다.
- PDF 내보내기.

| 항목 | 내용 |
