# 요구사항과 범위

CODEYE가 무엇이고 무엇이 아닌지, 사용자 역할, 기능·비기능 요구사항과 분석 품질 원칙을 정한다. MUST는 필수다. SHOULD는 근거를 기록하고 조정할 수 있다. REQ·NFR ID는 구현 작업·시험·설계 변경에서 그대로 유지한다. 요구사항과 수용 시험의 연결은 [시험](TESTING.md), 결정 이력은 [결정 기록](DECISIONS.md), 남은 작업은 [로드맵](ROADMAP.md)에 있다.

## 제품 정의

CODEYE는 프로젝트에 맞는 분석 계획을 만들고, 독립 작업공간에서 정적 분석 도구와 LLM 검토를 수행하며, 개발자가 판단하고 수정할 수 있는 근거 중심 보고서를 제공한다. 핵심 가치는 경고 수가 아니라 분석의 깊이·유용성·설명의 정확성이다. 기존 CI 결과를 수집하는 대시보드가 아니다.

## 고정된 제품 방향

아래는 소유자가 확정한 요구다. 기술 편의 때문에 바꾸지 않는다.

| 범주 | 요구 |
|---|---|
| 우선 사용 | 개인 PC의 개인 프로젝트에서 먼저 쓰고 여러 사용자에게 공개한다. 사내 전용이 아니며 GitHub.com 저장소에도 쓴다 |
| 환경 | Windows 계열 개인 PC와 RHEL 8.10 폐쇄망을 우선 고려. 사내 패키지 미러·NFS·기존 툴체인 활용 |
| 배치 | 한 머신에서 시작하되 여러 머신에 에이전트를 등록해 확장 |
| 실행 | Native 기본. Docker·Podman은 선택. SSH 원격 작업 기능 없음. 운영자가 설치한 노드 에이전트가 API로 작업을 받음 |
| 등록 | 이메일·비밀번호로 직접 가입한다. 중복 주소는 DB에서 거절하며 메일 수신 확인은 요구하지 않는다. GitHub.com/GHES 저장소는 플랫폼 GitHub 계정에 읽기 권한을 주고 URL을 입력한다. 로컬/NFS는 서비스 Linux 계정이 읽을 수 있는 프로젝트 경로를 입력한다 |
| 맥락 | README·AGENTS·architecture·guide·docs와 환경 파일을 자동 탐색. 문서가 없어도 진행 |
| 추가 정보 | 사용자 설명·첨부·관심 영역은 선택. 필수 입력 부담을 늘리지 않음 |
| 소스 | 일반 실행은 확보 시 최신 브랜치 HEAD, PR은 대상 SHA, 로컬은 별도 복사본 |
| 트리거 | 수동, 시간대가 있는 예약, PR 이벤트, 권한이 있는 사용자의 댓글 명령 |
| 결과 | 프로젝트별 실행 단계 요약과 상세 상태, 완료 수·추정 진행 정도, 요약·영역별·개별 상세 보고서 |
| 확장 | 운영자가 최소·최대 워커, 병렬 수와 자원 예산을 설정. 자동 증감. 한 머신에서도 여러 워커, 취소, lease와 fencing |
| 모델 | 사내에서는 허용된 OpenCode 연결을 우선. 직접 LLM API는 허용된 환경의 옵션 |
| 언어 | C/C++, Python, JavaScript/TypeScript, Go, Rust |

런타임·컴파일러 버전은 환경에서 탐지하고 프로젝트 요구와 대조한다. 특정 최신 버전의 설치를 강제하지 않는다. 노드를 추가하면 각 실행 환경에서 도구·자원을 관측한다. 모든 분석기가 모든 OS·버전에서 작동한다고 가정하지 않는다. 다중 노드 확장을 위해 전체를 다시 써야 하는 전역 상태 구조를 만들지 않는다.

## 비목표

- 기존 CI/Coverity 연결, CI 결과 수집, CI 파일 생성, CI 결과에 따라 검사 생략.
- 초기 의존성 CVE 검사·패키지 업그레이드 권고. 의존성 선언은 환경 분석에 사용한다.
- 운영 인스턴스 DAST·부하 시험, 운영 DB 사용, 배포, 자동 수정 커밋.
- 모든 업무 요구사항 자동 복원, 모든 언어/OS/버전 지원, 무결함 인증.
- Native 환경에서 적대적 임의 코드를 안전하게 실행한다는 보안 샌드박스 보장.
- 초기 클라우드 VM 생성·삭제. 등록된 머신 안의 워커 증감과 별개다.

CODEYE 저장소 자체의 자동 테스트(GitHub Actions)는 위 CI 비목표와 별개다([결정 기록](DECISIONS.md)의 A13).

## 현재 제공 범위

지금 쓸 수 있는 것은 **한 Linux 머신에서 `codeye up`으로 띄우는 웹 서비스**다. 혼자 써도, 다른 머신의 여러 사용자를 초대해도 같은 서비스이며 프로젝트 열람·실행 권한은 로그인한 사용자에게, 소스 읽기 권한은 설치에 설정한 플랫폼 계정에 속한다(A54). 설치와 사용은 [사용 안내서](GUIDE.md)를 따른다.

| 영역 | 현재 제공 |
|---|---|
| 실행 형태 | 상태 디렉터리의 관리형 PostgreSQL(기본) 또는 운영자가 준비한 PostgreSQL, controller(loopback, 또는 다른 머신용 TLS·명시적 평문 HTTP)와 로컬 에이전트. `codeye up`·`open`·`start`·`stop`·`status`(Linux 전용), 한 머신의 여러 워커와 최소·최대 자동 증감, 취소, lease·fencing |
| 계정 | 이메일·비밀번호 회원가입과 로그인, 기존 사용자 이름·일회용 링크 로그인. 같은 소스를 등록해도 사용자마다 프로젝트·실행·보고서를 소유하고 접근은 프로젝트 ACL로 관리한다 |
| 입력 | 서비스 Linux 계정이 읽을 수 있는 서버·NFS 폴더, 승인된 HTTPS 호스트의 Git 저장소 브랜치와 GitHub.com/GHES pull request. 저장소 웹훅과 PR 댓글 멘션으로도 분석을 요청한다. 비공개 저장소는 설치에 지정한 플랫폼 GitHub 계정으로 읽는다. 설명 없이 등록하고 문서·환경·모듈을 자동 탐색 |
| 정적 분석 | Go(go vet·Staticcheck·gofmt), C/C++(cppcheck·clang-tidy), Python(ruff·mypy·pyright·bandit), JS/TS(ESLint·tsc), Rust(cargo check·clippy) 다섯 언어 팩과 구조·중복 지표(lizard·jscpd), 비밀정보 검사(gitleaks). Go 패키지의 내부 import와 C/C++ 진단에 연결된 위치를 코드 줄까지 확인할 수 있다. 도구는 운영자가 설치하고 경로를 지정한다 |
| 기존 테스트 | `with-tests`에서 Go·npm 스크립트·Python unittest·Cargo의 기존 테스트를 작업 사본의 Linux 전용 loopback에서 실행한다. 저장소 코드 실행 권한이 필요하다. 실행 결과와 미실행 사유, 확인된 Go 실패의 선언 위치를 보고한다. [실행](EXECUTION.md#기존-테스트-실행) |
| 모델 검토 | 검토 지침 하나(`prompts/review`), 승인된 OpenCode 연결. 모델 없이도 도구 결과 보고서가 나온다 |
| 보고서 | 종합에서 문서와 구현의 대조, 도구 실행과 진단, 구조·중복 지표, 비밀정보, 코드 검토와 분석 공백의 상세 근거로 이동한다. 웹에서 문서 대조와 발견을 검색하고 같은 리비전을 JSON·Markdown·HTML로 내보낸다. 내보내기는 코드 미포함이 기본이다. [보고서](REPORT.md#보고서-패널) |
| 진행 | 프로젝트별 단계 표시, 완료 수와 가중 진행률, SSE 재접속 |
| 예약·이력 | 시간대가 있는 예약, 이전 실행과의 비교(absent≠fixed), 사람의 판정(disposition) |
| 운영 | 저장 영역 상한, 같은 시점 DB·산출물 백업과 새 위치로 복원, `codeye doctor` |
| 평가 | 품질 평가 runner와 정답 차단 relay([평가](EVALUATION.md)) |

조직 단위 GitHub App, Windows의 서비스 시작·중지와 관리형 PostgreSQL, 별도 빌드 전용 단계, 모듈 중심 프로필(`focused`), 잔여 시간 추정은 후속 작업이다. 여러 물리 노드와 실제 폐쇄망은 검증이 남아 있다. [로드맵](ROADMAP.md)

API 권한·프로젝트 소유권·노드 식별·lease는 처음부터 여러 사용자를 전제로 한다. 한 머신의 검증 결과를 여러 물리 머신 배포의 검증이라고 표현하지 않는다.

## 품질 축

**이해:** 요구사항을 발명하지 않고 문서 사실·코드 사실·추론을 구분한다. 함수 간 계약, 오류·취소 경로, 상태 전이, 동시성, 자원 수명, 구조적 성능 위험을 검토한다.

**다각도 검사:** 문법·규칙, 타입·컴파일 의미, 경로·데이터 흐름, 구조·복잡도, 비밀정보, 선택적 빌드·기존 테스트를 구분한다. 한 도구의 경고를 모델이 바꾸어 쓰는 것만으로 심층 분석을 주장하지 않는다.

**전달:** 문제→발생 조건→근거→영향→개선 방향→확인 방법을 연결한다. 미분석 영역은 보고서 첫 화면에서 알 수 있어야 한다.

## 용어

| 용어 | 뜻 |
|---|---|
| 프로젝트 | 소스와 정책 |
| run | 한 번의 분석 요청 |
| attempt | 재시도를 구분하는 실행 실체 |
| snapshot | 입력 기준점 |
| task | 도구·LLM 작업 |
| 노드 | 머신 |
| 에이전트 | 노드의 상주 관리자 |
| 워커 | 한 번에 한 attempt를 맡는 프로세스 |
| finding | 여러 관찰과 근거를 묶은 논점. 실제 결함 확정과 동의어가 아니다 |

## 사용자 역할

| 역할 | 할 수 있는 일 |
|---|---|
| 운영자 | 노드·풀·모델·도구·공통 정책 관리 |
| 프로젝트 관리자 | 소스·멤버·예약·분석 설정 관리 |
| 실행자 | 분석·취소·보고서 검토 |
| 열람자 | 읽기만 |

사용자는 이메일·비밀번호로 가입해 자기 프로젝트와 분석 이력을 관리한다. 같은 URL이나 경로를 다른 사람이 등록하면 새 프로젝트와 실행이 생긴다. 등록한 사용자만 보는 것이 기본이고, 프로젝트에 구성원을 추가해 결과를 공유한다. Git 호스트, 모델 연결, 서비스 정책과 사용자 관리는 운영자가 담당한다.

## 기능 요구

| ID | 수준 | 요구 |
|---|---|---|
| REQ-001 | MUST | Git URL·브랜치 또는 로컬 경로로 등록. 설명 없이 분석 요청 가능 |
| REQ-002 | MUST | 요청자의 프로젝트 권한과 노드 실행 계정의 소스 접근 권한을 각각 검사 |
| REQ-003 | MUST | 소스 확보 시 SHA/manifest를 고정하고 원본의 후속 변경과 분리 |

| REQ-005 | MUST | 문서 없음·상충·불완전을 구분하고 가능한 범위에서 분석 계속 |
| REQ-006 | MUST | 계획에 검사 목적·대상·선행조건·예산·완료 기준 포함 |
| REQ-007 | MUST | 규칙·타입·흐름·구조 등 보완적인 분석기 어댑터 제공 |
| REQ-008 | MUST | 원시 진단·규칙·버전·위치·환경·로그 보존 |
| REQ-009 | MUST | 도구 결과 해석과 맥락 기반 독립 탐색을 구분 |
| REQ-010 | MUST | 후보의 호출 경로·방어 코드·반례·가정을 검토하거나 미완료 표시 |
| REQ-011 | MUST | 사실·추론·재현·사람 검토를 구분하고 증거 참조 검증 |
| REQ-012 | MUST | 요약·영역별·발견별 보고서 및 실패·미지원·제외 범위 제공 |
| REQ-013 | MUST | 통계와 상태를 구조화 데이터에서 산출. LLM 서술로 수치 변경 금지 |

| REQ-016 | MUST | 프로젝트 목록·실행 상세에 대표 실행의 단계와 상태를 시각적으로 표시. 종료 수·경과 시간·대기 사유·로그 제공 |
| REQ-017 | SHOULD | 진행률은 작업량 추정으로 표시. 충분한 이력 후 잔여 시간 범위 제공 |

## 분석 프로필

| 프로필 | 범위 |
|---|---|
| `deep-review` | 기본. 문서·환경 진단, 정적 검사, 주요 경로 검토와 후보 반증, 보고서를 제공한다. 경로를 선택하거나 전체 코드를 확장 검토할 수 있다. [검토 범위](REVIEW.md#모듈-단위-검토-분할) |
| `with-tests` | 기본 분석에 승인된 기존 테스트 실행을 더한다. 실행 권한과 환경, 결과 사유는 [기존 테스트 실행](EXECUTION.md#기존-테스트-실행)을 따른다. |
| `focused` | 특정 모듈·관심 영역·PR 중심으로 보고 영향받는 파일까지 읽는 설계 계약이다. 전용 워커는 후속 작업이다. |

프로필은 실행 권한을 높일 수 없다. 기본 분석에는 정적 검사와 독립 맥락 검토가 모두 필요하다. 필요한 도구나 환경이 없어도 수행할 수 있는 검사를 계속하고 그 범위를 보고한다.

## 해석

최신 커밋은 소스 확보 시 관찰한 HEAD다. 같은 run의 재시도는 확정 입력을 유지한다. 원본 미변경과 운영 자격증명 미사용을 보장하도록 설계하지만 동일 호스트·NFS의 자원 영향이 0이라고 표현하지 않는다. Native는 작업공간 분리와 프로세스 제어를 제공하며 OS 샌드박스와 같지 않다.

## 분석 품질 원칙

동작이 코드상 가능한지와 공개 계약 안에서 조치할 문제인지를 따로 판단한다. 원래 결함을 고친 수정본에서도 계약 밖 입력에 대한 별도 경고가 남을 수 있으며, 이런 경고가 조치 우선순위를 과장하지 않게 한다. 역할별 지침은 [모델 검토](REVIEW.md)에 있다.

### 좋은 분석

좋은 발견 사항은 실제 코드 위치, 발생 가능한 조건, 원인과 영향의 연결, 이미 있는 방어 코드의 검토, 구체적인 개선·검증 방향을 갖는다. 단순 스타일 취향이나 근거 없는 일반론으로 보고서를 채우지 않는다. 문제 수가 0이어도 무엇을 검토했고 무엇을 못 했는지 유용하게 설명할 수 있어야 한다.

세 가지 산출물을 별도로 만든다. 프로젝트 맥락 지도는 구조와 제약을 설명한다. 발견 사항은 문제 후보와 검증 수준을 담는다. 분석 범위 원장은 수행한 검사·검토와 공백을 설명한다. 이 세 가지를 섞어 하나의 점수로 압축하지 않는다.

### 깊이의 단계

| 수준 | 실제 수행 | 허용되는 표현 |
|---|---|---|
| D0 | 파일·설정 탐색 | 환경을 파악함 |
| D1 | 규칙/문법 검사 | 특정 규칙의 진단을 얻음 |
| D2 | 타입·컴파일 의미·정적 흐름 분석 | 해당 도구 범위의 의미/경로를 분석함 |
| D3 | 관련 호출부·상태·예외·소유권을 연결한 검토 | 특정 가설을 코드 경로로 지지/반박함 |
| D4 | 통제된 실행이나 테스트로 조건 재현 | 명시된 환경·입력에서 재현됨 |

D4가 항상 필수이거나 항상 더 넓은 보장을 뜻하지 않는다. 재현은 그 조건의 사실이며 다른 모든 조건을 입증하지 않는다. D3의 소스 근거만으로도 유용한 결과를 제공할 수 있다.

### 상호 보완적인 탐색

도구 중심 경로는 원시 진단의 발생 조건과 영향 범위를 확인한다. 맥락 중심 경로는 도구 결과에 앞서 주요 경계·실패 경로를 검토해 규칙 밖의 가설을 만든다. 초기 예산 예시는 맥락 파악 15%, 독립 탐색 25%, 진단 검토 25%, 반증 25%, 종합 10%다. 이는 실행 시간 보장이 아닌 LLM 작업 예산의 조정 가능한 출발점이다.

동시성·취소, 데이터 일관성, 인증/권한, 입력 경계, 자원 수명, 오류 전파, 성능 구조, API 계약, 유지보수 위험을 별도 관점으로 다룬다. 복잡도나 중복만으로 기능 결함을 확정하지 않는다. 보안 검토만 수행하고 종합 코드 품질 분석이라고 표현하지 않는다.

### 후보의 검토 순서

1. 해당 코드가 현재 snapshot에 있는지 확인한다.
2. 주장의 전제와 발생 조건을 적는다. 가능한 입력과 불가능한 입력을 구분한다.
3. 호출자·피호출자·생성자·종료 경로에서 계약과 소유권을 확인한다.
4. 상위 검증, 잠금, finally/defer/RAII, 재시도·취소 처리가 주장을 반박하는지 찾는다.
5. 언어·런타임·빌드 플래그에 따라 판단이 달라지는지 확인한다.
6. 근거가 충분하면 supported, 실제 통제 실행 근거가 있으면 reproduced, 반례가 있으면 refuted, 부족하면 inconclusive로 기록한다.

지원되는 주장을 다시 모델에게 동의받았다는 이유로 reproduced로 올리지 않는다. 반증 지침은 모델의 내부 사고 과정을 요구하는 것이 아니라 확인한 코드·조건·결과를 짧고 검증 가능하게 제출하도록 한다.

### 노이즈를 줄이되 결과를 숨기지 않기

같은 원인과 영향 경로의 진단은 하나의 finding에 observation을 여러 개 연결한다. 같은 규칙이나 같은 줄이라는 이유만으로 다른 발생 조건을 합치지 않는다. 기각·중복 원본도 감사 가능한 상태로 남긴다. 요약에는 고우선순위 항목을 제한하고 전체 결과는 필터로 제공한다.

사용자 dismissal은 자동 정답이 아니다. 이유·적용 범위·만료일을 저장하고 규칙이나 코드가 바뀌면 재검토한다. 여러 사용자 행동을 근거 없이 모델의 영구 규칙으로 자동 학습하지 않는다.

### 범위를 정직하게 표현하기

도구가 처리한 파일, 모델에 제공한 코드, 검토 task가 완료된 범위, 테스트 커버리지는 다른 지표다. 파일 목록 수집이나 모델 컨텍스트 제공만으로 해당 파일 전체를 검증했다고 계산하지 않는다. 부분 파싱, timeout, 해석되지 않은 import, 지원되지 않는 features는 범위 원장에 남긴다.

문서가 없는 프로젝트를 감점하지 않는다. '업무 규칙 확인 불가'와 '구현 오류'를 구분한다. 문서와 코드가 충돌하면 양쪽 위치를 제시하고 어느 쪽이 옳은지 확인되지 않았음을 표시한다.

### 보고서 출판 전 검사

- 모든 코드·문서 위치가 확정 입력 또는 생성 artifact로 연결되는가.
- 심각도에 영향과 발생 조건 설명이 있는가.
- 재현 주장에 실행 ID·명령·종료 상태·출력이 있는가.
- 요약 숫자가 데이터 모델에서 계산된 값과 일치하는가.
- 필수 검사 실패·예산 종료가 첫 화면에 드러나는가.
- 수정 방향이 다른 계약이나 호환성을 깨뜨릴 수 있음을 검토했는가.

지침·도구·모델 변경은 [평가](EVALUATION.md)에 따라 보류 데이터로 비교한다. 실측 없이 '더 정확해졌다'고 발표하지 않는다.
