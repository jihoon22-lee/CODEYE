# 보류 평가 결과 (봉인)

> **검토 지침(프롬프트)을 고치는 작성자는 이 문서와 `fixtures/quality-holdout/`를 읽지 않는다.** 보류 자료의 독립성을 지키기 위한 규칙이다([평가 기준과 절차](EVALUATION.md)). 이 문서는 당시 기록을 옮긴 것이며 다른 문서에 요약하지 않는다. 판정·수치·서술은 고치지 않았고, 없어진 문서로 가던 링크를 풀고 바뀐 파일·식별자 이름만 맞췄다. 본문의 절 번호는 기록 당시의 것이다. 지침 이름은 현재 기준으로 적었다. 지금의 검토 지침(팩 id `review`)은 '후보 지침'(기본으로 정하기 전의 개정)과 그 앞의 '초안 지침'을 거친 것이고, '이전 지침'은 비교 대상이었다가 이후 저장소에서 제거됐다. 사례 ID와 corpus 디렉터리 이름을 바꾸면서 corpus digest와 정답 목록 sha256도 바뀌었으므로, 아래의 두 값은 이름을 바꾸기 전 corpus의 값이다.

#### 13.2 보류 비교: 후보 지침 대 이전 지침

- **차이가 난 변형은 셋이다.**
  - HOLD-PY-04 수정 전: 후보 지침만 라벨 결함을 냈다.
  - HOLD-JS-02 수정 후, HOLD-PY-07 수정 후: 이전 지침만 조치 대상 오탐을 냈다.

- **후보 지침의 미완료 1건(HOLD-JS-02 수정 전).** verify 출력이 검증기에서 격리됐고(`verification_quarantined`), 한 번의 재시도도 `review_output_incomplete`였다. 그래서 보고서는 `ai_review_partial`이다. 검증되지 않은 내용은 게시되지 않았다. 라벨 결함은 같은 변형의 다른 finding으로 포착됐다.

- **tools만 조건의 recall이 0이다.** 엄격한 판정 규칙(원인과 조건을 모두 말해야 일치) 때문이다. ESLint `no-unsafe-finally`는 HOLD-JS-02의 결함 줄을 정확히 짚었지만 trigger·영향을 말하지 않아 `valid_actionable`, 라벨 불일치로 판정됐다. 위치 자동 대조로는 수정 전 2/10이다. C/C++(compile DB 없음)와 Rust(Cargo.lock 없음) 분석기는 corpus에서 깊이 돌지 않았다(§12).
- **결론.** 이 표본(n=10)에서는 두 지침의 차이를 통계적으로 구분할 수 없다. 모든 구간이 겹친다. 후보 지침은 recall이 같거나 높고, 수정 후 오탐이 적고, 호출당 비용이 약간 낮게 관찰됐다. 대신 미완료가 1건 있었다. 정확도 향상으로 발표할 근거는 아니다.

#### 13.3 반복 실행 분산

#### 13.5 승격 판단

후보 지침은 `candidate-not-promoted`로 둔다. 기본 지침 변경은 소유자가 정한다. 판단 근거는 다음과 같다. (이후 소유자가 같은 날 이 지침을 기본으로 정했다. 2.0.0의 변경과 회귀 검증은 아래 '기본 검토 팩 변경 근거와 회귀 기록'에 있다.)

- **유리:**
  - 보류 비교에서 recall이 같거나 높았다(10/10 대 9/10).
  - 수정 후 오탐이 적었다(2/10 대 4/10).
  - 비용이 약간 낮았다.
  - 근거 없는 주장과 실행 없는 재현은 두 지침 모두 0이다.
- **불리:**
  - 표본이 작아 모든 차이가 구간 안에 있다.
  - 회귀 조건 4가 해당했다(모듈 입력, 3회 중 1회 low 오탐).
  - 미완료 검토가 1건 있었다.
  - tricky normal 사례를 표본에 넣지 않아 정상 코드의 오탐률은 측정하지 않았다.
- **측정하지 않은 것:**
  - 사람 판정과 판정자 간 일치도;
  - 보고서 읽기 평가(독자 답 없음);
  - tricky normal;
  - C/C++·Rust 분석기 깊이;
  - 구조·중복·비밀값 지표의 유용성.

결과 디렉터리, 판정 파일, 지침 가림 대응표는 저장소 밖 비공개 경로에 보관했다. 재현에는 §11 절차와 `--sample 10 --seed 24`를 쓴다. 이 batch 뒤에 같은 팩 id의 다른 digest로 실행하면 `holdout_seen_by_prior_revision`으로 표시된다. 다음 보류 비교는 새 사례나 tricky normal을 포함해야 독립 비교가 된다.

## 기본 검토 팩 변경 근거와 회귀 기록

### 1. 기본 팩을 바꾼 근거

- **보류 평가.** 보류 평가 1회차 비교에서 후보 지침은 이전 지침보다 나쁘지 않았다. 점추정으로는 recall, 수정 후 오탐, 비용 모두 후보 지침이 앞섰다. 다만 모든 차이가 구간 안에 있으므로 후보 지침이 더 낫다고 단정하지 않는다. 판정은 지침을 가린 개발 에이전트가 했고 사람의 판정이 아니다.
- **하나로 합친 이유.** 두 지침을 기본 후보로 나란히 두면 지침을 바꿀 때마다 둘을 따로 고치고 비교해야 한다. 기본 팩 하나만 개정하고 회귀 검증한다.
- **이후 변경.** 이 평가 뒤에 이전 지침과 지침 선택을 지웠고, 검토 지침의 디렉터리와 id를 `prompts/review`·`review`로 바꿨다([결정 기록](DECISIONS.md)의 A52). 아래 시험 이름은 현재 이름이다.

판정 기준은 실행 전에 적었고 후보 지침의 회귀 검증(§13.1)과 같은 형태다. 대상은 회귀 쌍 Q01·Q03·Q05·Q08·Q10(수정 전·후), 모듈 입력, 닫기 입력이고 모델은 relay를 거친 `gpt-6.2-sol`, 각 사례 1회다.

### 실행 전에 적은 기준

모듈별 검토(모듈 단위 조각 조사·검증과 호출 상한)를 넣은 변경의 회귀 검증이다. 검토 지침 문구와 팩 digest는 바꾸지 않았고, 모델 없이 한 요청 비교에서 기존 사례의 요청은 변경 전과 같았다. 아래 기준과 대상은 실행 전에 적었고 결과를 보고 바꾸지 않는다.

- 대상: 회귀 쌍 Q01·Q03·Q05·Q08·Q10(수정 전·후), 고정 입력인 모듈 입력·닫기 입력, 공개 고정 사본 `pilot`. 각 1회, relay를 거친 `gpt-6.2-sol`, 호출 상한 33, gitleaks·ruff·eslint·node 설정.

공개 분석은 `deep-review`의 선택 경로에서 기존 테스트를 실행하지 않았다. Commons CLI의 반복 호출은 같은 옵션과 서로 다른 두 기본값을 실제로 넣어 수정 전 `first, first`, 수정 후 `first, second`임을 별도로 확인했다. 통제된 여섯 언어 시험에는 실제 테스트를 포함했다. 테스트의 실패와 도구 누락은 해당 실행의 상태에 반영되며, 실패한 테스트를 게시했다고 해서 전체 분석이 성공으로 바뀌지 않는다.

**CODEYE 자체 검토.** 통합 커밋 `44dad14`에서 CLI, 분석·테스트 워커, 보고서 생성기, 웹 소스와 네 가지 안내 문서를 선택했다. GPT-6-Luna가 호출 한도 30회를 사용했다. 모듈 장부의 조사 가능 코드·테스트 파일은 430개, 모델에 전달된 코드·테스트 파일은 165개, 문서 등을 포함한 전체 전달 파일은 169개였다. 보고서에 게시된 문서 대조 다섯 건은 부분 확인 2건, 미확인 3건이었다.

`cmd/codeye/backup.go`의 완료 안내 출력 오류를 무시한다는 지적을 임시 PostgreSQL에서 실제 백업으로 확인했다. 텍스트·JSON 출력을 `/dev/full`로 보냈을 때 양쪽 모두 백업 manifest를 작성하고 종료 코드 0을 반환했다. 수정 후 같은 시험에서 백업과 manifest를 보존하고 경로를 표준 오류로 알리며 종료 코드 1을 반환했다.

**비용.** 이번 실험은 요청 395회를 하나의 20달러 장부로 정산했다. 보수적으로 차감한 금액은 15.319765달러이고, 모델별 표준 요율과 반환된 사용량으로 계산한 추정액은 1.538840달러였다. 미정산 요청은 0건이다. 실제 청구액은 공급자 명세에서 확인할 수 있다.

## 모듈 단위 검토 입력의 전후 비교와 회귀 기록

모델이 한 모듈의 파일을 선언 경계 단위로 통째로 읽게 하고 요청 크기(기본 262,144바이트)와 출력 상한(기본 16,384토큰)을 운영자가 정하게 한 변경과, 그에 따른 검토 지침 개정(2.7.0, 2.8.0)의 기록이다. 모델은 모두 예산 relay를 거친 `gpt-6.2-sol`, OpenCode 1.19.5, 사례마다 1회, 호출 상한 20이다. 합성 회귀 사례는 평가 운영자(모델 에이전트이며 사람도 조정자도 아니다)가 판정했고 사람의 판정이 아니다. 프로젝트 규모 집합의 판정은 모델 두 개가 했다.

### 실행 전에 적은 기준

프로젝트 규모 집합의 전후 비교는 실행 전에 아래를 적었고 결과를 보고 바꾸지 않았다.

- 주지표: 모델 발견이 라벨 결함과 일치하는 사례 수(블라인드 판정).
- '명확한 개선': 순승 4 이상이고 패 1 이하. 아니면 '구분할 수 없음'으로 적는다.
- 오탐은 늘면 안 된다.
- 차단 조건: 꾸민 근거, 실행·재현했다는 서술, 통계에 들어간 모델 서술.
- 사례당 비용을 적고 기준의 1.5배를 넘으면 표시한다.
- 사례가 다섯이면 '명확한 개선' 임계는 어떤 결과가 나와도 도달할 수 없었다. 기준 빌드가 이미 두 사례를 찾았으므로 이길 수 있는 사례가 최대 셋이다. 이 비교는 방향을 보는 용도이고 개선의 입증이 아니다.

회귀 집합은 합성 Go 쌍 Q01~Q10(수정 전·후 20개)과 고정 입력 `modules`·`caller-closes`이고, gitleaks·ruff·eslint·node를 설정하고 호출 상한은 에이전트 기본값을 썼다.

- a. 모든 사례의 AI 검토가 `performed`이고 relay 장부에 거절·차단 요청이 없다. `--audit-results`가 통과한다.
- b. 차단 조건: 없는 근거나 근거에 없는 내용을 인용한 게시 주장, 시험·도구를 실행했거나 결함을 재현했다는 서술, 상태·통계에 들어간 모델 서술.
- c. 수정 전 10개의 알려진 원인 포착이 직전 전체 회귀 기록(2026-11-22, 8/10)−1 이상, 수정 후 10개의 같은 주장 재지적이 직전 기록(0/10)+1 이하, 닫기 입력 반례가 `supported`가 아니다. 직전 기록은 `gpt-6-luna`였으므로 모델이 다르고 비교값으로만 쓴다.
- d. 보고만 하는 값: 역할별 호출, 형식 복구와 거부 코드, 사용량과 차감.

### 블라인드 판정

모델 발견 89개(기준 47, 후보 42)를 빌드 신원을 지운 묶음 하나에 섞어 담았다. 도구 진단은 위 이유로 뺐다(기준 49개, 후보 50개). 판정자는 사람이 아니라 모델 둘(Claude Opus 5.5, Claude Sonnet 5.5)이고 서로 독립해 각자 주장을 스냅샷 소스와 대조했다. 1차는 정답 설명 없이 판정하고 2차에서 정답 결함과 일치하는지 정했다([블라인드 판정](EVALUATION.md#블라인드-판정)). 판정 일치는 89개 중 84개(Cohen의 kappa 0.92)였고, 일치로 본 다섯 건은 두 판정자가 같았다.

| 지표(다섯 사례) | 기준 | 후보 |
|---|---|---|
| 라벨 결함 발견(모델 발견이 일치) | 2/5 | 3/5 (승 1, 패 0) |
| 두 판정자 모두 `valid_actionable` | 14/47 (30%) | 20/42 (48%) |
| `supported` 중 두 판정자 모두 조치 대상 | 4/26 (15%, Wilson 95% 6~34%) | 17/32 (53%, 36~69%) |
| 어느 한 판정자라도 `false_positive` | 3/47 | 0/42 |
| 두 판정자 모두 범위 밖(시험·예제·벤치마크 코드) | 12/47 | 7/42 |
| 판정자별 조치 대상(A / B) | 15/47 / 14/47 | 21/42 / 22/42 |

- **판정.** 주지표는 승 1, 패 0이고 사전 규칙에 따라 '구분할 수 없음'이다. 오탐은 늘지 않았다(3→0).
- `supported` 발견 중 조치 대상의 비율은 15%에서 53%로 올랐다(Fisher 정확 검정 p ≈ 0.005). 발견은 다섯 프로젝트에 묶여 있어 서로 독립이 아니므로 p 값은 참고값이다.
- 후보에서 모델 발견은 줄었고(47→42) 검증을 거쳐 `supported`로 남은 것은 늘었다(26→32). 호출은 약 3분의 1로 줄었고 가장 큰 요청은 30~36 KB에서 143~215 KB로 커졌다.

**관찰한 약점.**
- 다섯 중 두 사례의 라벨 결함은 라벨 파일이 입력에 있었는데도 두 빌드 모두 찾지 못했다. 모든 줄을 보내도 찾지 못하는 결함이 있다.
- 한 프로젝트에서 후보는 시험 파일의 발견 다섯 개를 `supported`로 게시했다. 시험·예제 코드를 결함 후보로 올리는 문제가 남아 있다.

**한계.**
- 판정자가 모델이므로 사람의 판정이 아니다. 인용 발췌의 수와 길이, 서술 길이, 후보에만 있는 `high` 심각도 셋이 빌드를 짐작하게 할 수 있다. 발췌는 앞 60줄까지 보이게 했으나 그보다 긴 발췌는 없었다.
- 사례가 다섯이고 한 번씩만 실행했다. 모델 변동은 측정하지 않았다.
- holdout 등록부가 후보 batch에 이전 digest 표시를 붙였으므로 독립 비교가 아니다.

### 무효 실행과 원인

아래 후보 실행은 비교에서 제외했다(결과 파일은 보존). 첫째는 비용 없는 가짜 upstream 예행에서, 나머지 둘은 유료 실행에서 드러났다.

| 후보 커밋 | 실행 | 원인과 이후 수정 |
|---|---|---|
| `7868920` | 가짜 upstream 예행 | 세 사례에서 검증 기록을 보고서 기록 연결 검사가 거부해 필수 검토가 끝나지 않았다. 후보를 감싸는 선언이 이미 보낸 단위와 같을 때 생겼다. 유료 실행 전에 고쳤다 |
| `8f5e425`(2.7.0) | 유료, 세 사례(4.34달러) | 세 사례 모두 overview 조사 응답이 계약 대조 검사로 두 번 거부되어 필수 조사가 실패했다(`contract_comparison_invalid`). 파일 전체 코드 근거는 같은 파일의 소스 안 API 문서와 항상 겹치는데 이를 거부했다. 수정: 비교마다 인용 범위를 유지하고, 거부 조건마다 고유 코드를 두며, 여전히 무효인 비교는 그 항목만 뺀다 |
| `d7084d9`(2.7.1) | 유료, 두 사례(2.15달러) | 둘째 사례에서 검증의 두 호출이 모두 긴 발췌를 범위 없이 인용해(`citation_range_missing`) 후보 하나가 격리되었고, 그 때문에 그 사례의 모델 발견이 모두 `unreviewed`로 게시됐다. 수정: 형식 오류는 한 번 복구한 뒤 항목별로 해소하거나 빼고, 일부 후보가 격리된 검증도 수락한 판정은 게시한다 |

- 결과로 정한 규칙: 출력 오류를 무결성 오류(없는 ID, 발췌 밖 줄, 실행 주장)와 형식 오류로 나눈다. 형식 오류는 한 번 복구를 요청한 뒤 항목별로 처리한다. [출력 오류 분류](REVIEW.md#출력-오류-분류)
- 가짜 upstream은 처음에 형식이 항상 맞는 응답만 해서 뒤의 두 원인을 만들지 못했다. 이후 가짜 upstream에 형식 오류와 무결성 오류를 섞는 옵션을 더하고 사전 확인에 넣었다([유료 batch 절차](EVALUATION.md#유료-batch-절차)).

### 독립성 공개

- 이번 개정 기간에 지침 작성자의 저장소 전체 검색이 여러 번 이 문서와 평가 사례 디렉터리(`fixtures/quality-holdout/`, `fixtures/project-defects/`)를 지나갔다. 출력은 걸러 냈고 작성자는 내용을 읽지 않았다고 보고하지만, 검색 경로가 그 자료를 지난 사실을 적는다.
- 평가 운영자는 dev 사례를 읽었고 합성 회귀 사례를 직접 판정했다.
- dev 분할은 독립 평가가 아니다. 봉인한 holdout 분할은 프로젝트 규모 집합에서 아직 쓰지 않았다.
- 판정자는 모델이다. 사람의 판정은 받지 않았다.
