> **검토 지침(프롬프트)을 고치는 작성자는 이 문서와 `fixtures/quality-holdout/`를 읽지 않는다.** 보류 자료의 독립성을 지키기 위한 규칙이다([평가 기준과 절차](EVALUATION.md)). 이 문서는 당시 기록을 옮긴 것이며 다른 문서에 요약하지 않는다. 판정·수치·서술은 고치지 않았고, 없어진 문서로 가던 링크를 풀고 바뀐 파일·식별자 이름만 맞췄다. 본문의 절 번호는 기록 당시의 것이다. 지침 이름은 현재 기준으로 적었다. 지금의 검토 지침(팩 id `review`)은 '후보 지침'(기본으로 정하기 전의 개정)과 그 앞의 '초안 지침'을 거친 것이고, '이전 지침'은 비교 대상이었다가 이후 저장소에서 제거됐다. 사례 ID와 corpus 디렉터리 이름을 바꾸면서 corpus digest와 정답 목록 sha256도 바뀌었으므로, 아래의 두 값은 이름을 바꾸기 전 corpus의 값이다.

#### 13.2 보류 비교: 후보 지침 대 이전 지침

- **차이가 난 변형은 셋이다.**
  - HOLD-PY-04 수정 전: 후보 지침만 라벨 결함을 냈다.

- **결론.** 이 표본(n=10)에서는 두 지침의 차이를 통계적으로 구분할 수 없다. 모든 구간이 겹친다. 후보 지침은 recall이 같거나 높고, 수정 후 오탐이 적고, 호출당 비용이 약간 낮게 관찰됐다. 대신 미완료가 1건 있었다. 정확도 향상으로 발표할 근거는 아니다.

#### 13.3 반복 실행 분산

#### 13.5 승격 판단

후보 지침은 `candidate-not-promoted`로 둔다. 기본 지침 변경은 소유자가 정한다. 판단 근거는 다음과 같다. (이후 소유자가 같은 날 이 지침을 기본으로 정했다. 2.0.0의 변경과 회귀 검증은 아래 '기본 검토 팩 변경 근거와 회귀 기록'에 있다.)

- **유리:**
  - 보류 비교에서 recall이 같거나 높았다(10/10 대 9/10).
  - 수정 후 오탐이 적었다(2/10 대 4/10).
  - 비용이 약간 낮았다.
  - 근거 없는 주장과 실행 없는 재현은 두 지침 모두 0이다.
- **불리:**
  - 표본이 작아 모든 차이가 구간 안에 있다.
  - 회귀 조건 4가 해당했다(모듈 입력, 3회 중 1회 low 오탐).
  - 미완료 검토가 1건 있었다.
  - tricky normal 사례를 표본에 넣지 않아 정상 코드의 오탐률은 측정하지 않았다.
- **측정하지 않은 것:**
  - 사람 판정과 판정자 간 일치도;
  - 보고서 읽기 평가(독자 답 없음);
  - tricky normal;
  - C/C++·Rust 분석기 깊이;
  - 구조·중복·비밀값 지표의 유용성.

결과 디렉터리, 판정 파일, 지침 가림 대응표는 저장소 밖 비공개 경로에 보관했다. 재현에는 §11 절차와 `--sample 10 --seed 24`를 쓴다. 이 batch 뒤에 같은 팩 id의 다른 digest로 실행하면 `holdout_seen_by_prior_revision`으로 표시된다. 다음 보류 비교는 새 사례나 tricky normal을 포함해야 독립 비교가 된다.

## 기본 검토 팩 변경 근거와 회귀 기록

### 1. 기본 팩을 바꾼 근거

- **보류 평가.** 보류 평가 1회차 비교에서 후보 지침은 이전 지침보다 나쁘지 않았다. 점추정으로는 recall, 수정 후 오탐, 비용 모두 후보 지침이 앞섰다. 다만 모든 차이가 구간 안에 있으므로 후보 지침이 더 낫다고 단정하지 않는다. 판정은 지침을 가린 개발 에이전트가 했고 사람의 판정이 아니다.
- **하나로 합친 이유.** 두 지침을 기본 후보로 나란히 두면 지침을 바꿀 때마다 둘을 따로 고치고 비교해야 한다. 기본 팩 하나만 개정하고 회귀 검증한다.
- **이후 변경.** 이 평가 뒤에 이전 지침과 지침 선택을 지웠고, 검토 지침의 디렉터리와 id를 `prompts/review`·`review`로 바꿨다([결정 기록](DECISIONS.md)의 A52). 아래 시험 이름은 현재 이름이다.

### 실행 전에 적은 기준

모듈별 검토(모듈 단위 조각 조사·검증과 호출 상한)를 넣은 변경의 회귀 검증이다. 검토 지침 문구와 팩 digest는 바꾸지 않았고, 모델 없이 한 요청 비교에서 기존 사례의 요청은 변경 전과 같았다. 아래 기준과 대상은 실행 전에 적었고 결과를 보고 바꾸지 않는다.

공개 분석은 `deep-review`의 선택 경로에서 기존 테스트를 실행하지 않았다. Commons CLI의 반복 호출은 같은 옵션과 서로 다른 두 기본값을 실제로 넣어 수정 전 `first, first`, 수정 후 `first, second`임을 별도로 확인했다. 통제된 여섯 언어 시험에는 실제 테스트를 포함했다. 테스트의 실패와 도구 누락은 해당 실행의 상태에 반영되며, 실패한 테스트를 게시했다고 해서 전체 분석이 성공으로 바뀌지 않는다.

**CODEYE 자체 검토.** 통합 커밋 `44dad14`에서 CLI, 분석·테스트 워커, 보고서 생성기, 웹 소스와 네 가지 안내 문서를 선택했다. GPT-6-Luna가 호출 한도 30회를 사용했다. 모듈 장부의 조사 가능 코드·테스트 파일은 430개, 모델에 전달된 코드·테스트 파일은 165개, 문서 등을 포함한 전체 전달 파일은 169개였다. 보고서에 게시된 문서 대조 다섯 건은 부분 확인 2건, 미확인 3건이었다.

`cmd/codeye/backup.go`의 완료 안내 출력 오류를 무시한다는 지적을 임시 PostgreSQL에서 실제 백업으로 확인했다. 텍스트·JSON 출력을 `/dev/full`로 보냈을 때 양쪽 모두 백업 manifest를 작성하고 종료 코드 0을 반환했다. 수정 후 같은 시험에서 백업과 manifest를 보존하고 경로를 표준 오류로 알리며 종료 코드 1을 반환했다.

**비용.** 이번 실험은 요청 395회를 하나의 20달러 장부로 정산했다. 보수적으로 차감한 금액은 15.319765달러이고, 모델별 표준 요율과 반환된 사용량으로 계산한 추정액은 1.538840달러였다. 미정산 요청은 0건이다. 실제 청구액은 공급자 명세에서 확인할 수 있다.

## 모듈 단위 검토 입력의 전후 비교와 회귀 기록

모델이 한 모듈의 파일을 선언 경계 단위로 통째로 읽게 하고 요청 크기(기본 262,144바이트)와 출력 상한(기본 16,384토큰)을 운영자가 정하게 한 변경과, 그에 따른 검토 지침 개정(2.7.0, 2.8.0)의 기록이다. 모델은 모두 예산 relay를 거친 `gpt-6.2-sol`, OpenCode 1.19.5, 사례마다 1회, 호출 상한 20이다. 합성 회귀 사례는 평가 운영자(모델 에이전트이며 사람도 조정자도 아니다)가 판정했고 사람의 판정이 아니다. 프로젝트 규모 집합의 판정은 모델 두 개가 했다.

### 실행 전에 적은 기준

프로젝트 규모 집합의 전후 비교는 실행 전에 아래를 적었고 결과를 보고 바꾸지 않았다.

- 주지표: 모델 발견이 라벨 결함과 일치하는 사례 수(블라인드 판정).
- '명확한 개선': 순승 4 이상이고 패 1 이하. 아니면 '구분할 수 없음'으로 적는다.
- 오탐은 늘면 안 된다.
- 차단 조건: 꾸민 근거, 실행·재현했다는 서술, 통계에 들어간 모델 서술.
- 사례당 비용을 적고 기준의 1.5배를 넘으면 표시한다.
- 사례가 다섯이면 '명확한 개선' 임계는 어떤 결과가 나와도 도달할 수 없었다. 기준 빌드가 이미 두 사례를 찾았으므로 이길 수 있는 사례가 최대 셋이다. 이 비교는 방향을 보는 용도이고 개선의 입증이 아니다.

회귀 집합은 합성 Go 쌍 Q01~Q10(수정 전·후 20개)과 고정 입력 `modules`·`caller-closes`이고, gitleaks·ruff·eslint·node를 설정하고 호출 상한은 에이전트 기본값을 썼다.

- a. 모든 사례의 AI 검토가 `performed`이고 relay 장부에 거절·차단 요청이 없다. `--audit-results`가 통과한다.
- b. 차단 조건: 없는 근거나 근거에 없는 내용을 인용한 게시 주장, 시험·도구를 실행했거나 결함을 재현했다는 서술, 상태·통계에 들어간 모델 서술.
- c. 수정 전 10개의 알려진 원인 포착이 직전 전체 회귀 기록(2026-11-22, 8/10)−1 이상, 수정 후 10개의 같은 주장 재지적이 직전 기록(0/10)+1 이하, 닫기 입력 반례가 `supported`가 아니다. 직전 기록은 `gpt-6-luna`였으므로 모델이 다르고 비교값으로만 쓴다.
- d. 보고만 하는 값: 역할별 호출, 형식 복구와 거부 코드, 사용량과 차감.

### 블라인드 판정

모델 발견 89개(기준 47, 후보 42)를 빌드 신원을 지운 묶음 하나에 섞어 담았다. 도구 진단은 위 이유로 뺐다(기준 49개, 후보 50개). 판정자는 사람이 아니라 모델 둘(Claude Opus 5.5, Claude Sonnet 5.5)이고 서로 독립해 각자 주장을 스냅샷 소스와 대조했다. 1차는 정답 설명 없이 판정하고 2차에서 정답 결함과 일치하는지 정했다([블라인드 판정](EVALUATION.md#블라인드-판정)). 판정 일치는 89개 중 84개(Cohen의 kappa 0.92)였고, 일치로 본 다섯 건은 두 판정자가 같았다.

| 지표(다섯 사례) | 기준 | 후보 |
|---|---|---|
| 라벨 결함 발견(모델 발견이 일치) | 2/5 | 3/5 (승 1, 패 0) |
| 두 판정자 모두 `valid_actionable` | 14/47 (30%) | 20/42 (48%) |
| `supported` 중 두 판정자 모두 조치 대상 | 4/26 (15%, Wilson 95% 6~34%) | 17/32 (53%, 36~69%) |
| 어느 한 판정자라도 `false_positive` | 3/47 | 0/42 |
| 두 판정자 모두 범위 밖(시험·예제·벤치마크 코드) | 12/47 | 7/42 |
| 판정자별 조치 대상(A / B) | 15/47 / 14/47 | 21/42 / 22/42 |

- **판정.** 주지표는 승 1, 패 0이고 사전 규칙에 따라 '구분할 수 없음'이다. 오탐은 늘지 않았다(3→0).
- `supported` 발견 중 조치 대상의 비율은 15%에서 53%로 올랐다(Fisher 정확 검정 p ≈ 0.005). 발견은 다섯 프로젝트에 묶여 있어 서로 독립이 아니므로 p 값은 참고값이다.
- 후보에서 모델 발견은 줄었고(47→42) 검증을 거쳐 `supported`로 남은 것은 늘었다(26→32). 호출은 약 3분의 1로 줄었고 가장 큰 요청은 30~36 KB에서 143~215 KB로 커졌다.

**관찰한 약점.**
- 다섯 중 두 사례의 라벨 결함은 라벨 파일이 입력에 있었는데도 두 빌드 모두 찾지 못했다. 모든 줄을 보내도 찾지 못하는 결함이 있다.
- 한 프로젝트에서 후보는 시험 파일의 발견 다섯 개를 `supported`로 게시했다. 시험·예제 코드를 결함 후보로 올리는 문제가 남아 있다.

**한계.**
- 판정자가 모델이므로 사람의 판정이 아니다. 인용 발췌의 수와 길이, 서술 길이, 후보에만 있는 `high` 심각도 셋이 빌드를 짐작하게 할 수 있다. 발췌는 앞 60줄까지 보이게 했으나 그보다 긴 발췌는 없었다.
- 사례가 다섯이고 한 번씩만 실행했다. 모델 변동은 측정하지 않았다.
- holdout 등록부가 후보 batch에 이전 digest 표시를 붙였으므로 독립 비교가 아니다.

## 도구 진단 분류의 측정과 회귀 기록

도구 진단을 묶어 모델이 문제·무해·불명으로 분류하고 문제로 본 묶음을 검증하는 변경(PR #81, 측정 커밋 `48311d6`, 지침 2.9.0, 기록 schema 0.8, 보고서 생성기 22)의 기록이다. 모델은 예산 relay를 거친 `gpt-6.2-sol`이다. OpenCode 1.19.6(시험한 버전 1.19.5·1.19.6 중 하나)을 썼다. 사례마다 1회, 호출 상한은 20이다. 합성 회귀 사례는 평가 운영자가 판정했다. 평가 운영자는 모델 에이전트이며 사람도 조정자도 아니다. 분류 묶음은 별도의 모델 판정자가 소스와 대조해 판정했고 그 집계는 [분류 묶음의 독립 판정](#분류-묶음의-독립-판정)에 있다.

### 실행 전에 적은 기준

- 큰 요청 사례: dev 분할에서 요청이 가장 큰 한 사례를 쓴다. 비용 없는 사전 확인 두 가지(일반 가짜 upstream, 항목 절반에 형식 오류를 섞은 가짜 upstream)에서 모두 다음을 확인한 뒤에만 유료로 실행한다. AI 검토 `performed`, 필수 검토 task 손실 없음, 검토 대상 줄 전부 전송.

- 이 측정의 관찰은 [로드맵](ROADMAP.md#분석-품질-개선)의 도구 진단 분류 항목(지침 보강, 더 많은 사례의 측정)과 결정 A62로 옮겼다. 지침 문구는 바꾸지 않았다. 이 측정이 낳은 변경은 모델이 보는 입력과 지침을 바꾸지 않는 결정적 규칙이다. 시험·예제·벤치마크·생성물·외부 코드 경로의 도구 진단은 기본 심각도를 낮추고 분류에서 배포 코드 뒤에 둔다([분석기](ANALYZERS.md#기본-심각도), [검토](REVIEW.md#도구-진단-분류), 결정 A62). 이 규칙이 분류 품질을 올리는지는 아직 측정하지 않았다. (이후의 측정은 [지침 2.10.0 기록](#지침-2100))

**한계.**

- 사례 하나, 실행 한 번이다. 비율은 일반화할 수 없다.
- 판정자가 모델이다. 판정자 자신의 오류를 배제하지 못했고 사람의 판정을 받지 않았다.
- 합성 회귀 집합에는 도구 진단이 없다. 그래서 분류 역할은 회귀 시험을 받지 않는다. 합성 회귀의 통과는 분류의 근거가 아니다.
- 경로별 기본 심각도와 분류 순서는 이 사례로 정했고 같은 사례로 확인하지 않았다. 새 규칙의 효과는 결정적 시험(합성 진단)으로만 확인했다.

## 요청 예산 실험과 배포 코드 검토 초점(지침 2.10.0)의 측정

한 예산에서 이어서 한 두 측정의 기록이다. 하나는 코드와 지침을 바꾸지 않고 요청 예산만 줄여 본 실험이고, 다른 하나는 검토 지침 2.10.0(PR #85, 측정 커밋 `1247a7d`, 보고서 생성기 24)의 프로젝트 규모 사례 측정과 회귀 기록이다. 모델은 예산 relay를 거친 `gpt-6.2-sol`, OpenCode는 1.19.6이다. 사례마다 1회 실행했고, 프로젝트 규모 사례의 호출 상한은 20이다. 분석기 플래그와 의존성 받기 끔은 이전 측정과 같다. 합성 회귀 사례는 평가 운영자가 판정했다. 평가 운영자는 모델 에이전트이며 사람도 조정자도 아니다. 모델 발견과 진단 분류의 판정은 모델 판정자가 했고 사람의 판정은 받지 않았다.

**아래 세 프로젝트 규모 dev 사례는 조정에 쓴 사례이고 독립 평가가 아니다.** 요청 예산 실험과 앞선 진단 분류 측정에서 얻은 집계 관찰을 일반화해 지침 작성자에게 전달했다(이 절 끝의 독립성 공개). 이 절의 개선은 조정에 쓴 사례 안의 관찰이고 처음 보는 프로젝트에서의 정확도를 뒷받침하지 않는다.

### 요청 예산 실험

모듈 단위 입력에서 검토 대상 줄을 모두 보냈는데도 라벨 결함을 앞선 두 빌드가 모두 찾지 못한 dev 사례 둘(사례 B·C. 아래 지침 2.10.0 측정의 같은 사례)의 기록이다. 가설은 이렇다. 150~215 KB 요청 하나에 실은 코드는 주의가 흐려지고, 같은 코드를 더 작은 요청에 나눠 실으면 더 자세히 읽는다. 코드와 지침은 바꾸지 않았고 운영자 설정 `--review-request-bytes`만 바꿨다. 제품과 runner는 커밋 `17b655e`다. 변경 전 변형을 사례마다 1회 실행했다.

**실행 전에 적은 선택 규칙.** 65,536과 131,072 중 두 사례 모두 검토 대상 줄을 하나도 빼지 않는 가장 작은 예산을 고른다. 호출 상한 20에서 성립하면 20을, 아니면 40을 쓴다. 두 사례의 `plan` 기대 차감이 4.50달러를 넘으면 다음으로 큰 예산을 시도하고, 그것도 넘으면 멈춘다. 둘 다 호출 상한 40에서도 줄을 빼면 유료 실행을 하지 않는다.

**비용 없는 사전 확인(가짜 upstream).** 요청 예산 세 가지(262,144·131,072·65,536바이트)와 호출 상한 두 가지(20·40)의 여섯 구성을 모델 없이 수집했다.

### 지침 2.10.0

배포 코드를 검토 대상으로 하는 개정이다. 내용은 다음과 같다.
- 요청에 경로 종류(`path_class`)를 구조 필드로 싣고, 플랫폼 규칙이 시험·예제·벤치마크 코드만 인용한 조사 후보를 검증에 보내지 않고 센다([결정 A63](DECISIONS.md)).
- 진단 분류의 `unclear` 답은 입력에 없는 것을 이름으로 적게 한다.
- 진단 분류가 한 묶음의 일부만 나눠 분류할 수 있다.
- 쓰지 않는 값과 중복 코드 진단은 단서로 읽는다.
- 경로 종류를 확실한 것만 센다(`paths.2`).

**실행 전에 적은 기준.** 유료 실행 전에 적었고 결과를 보고 바꾸지 않았다.

- 회귀 집합(합성 Go 쌍 Q01~Q10 수정 전·후와 고정 입력 `modules`·`caller-closes`):
  - a: 모든 사례의 AI 검토가 `performed`이고 relay 장부에 거절·차단 요청이 없다. `--audit-results`가 통과하고 파일럿 종료 코드가 0이다.
  - b: 차단 조건. 꾸민 근거 또는 근거에 없는 내용의 인용, 실행·재현했다는 서술, 상태·통계 안의 모델 서술.
  - c: 수정 전 알려진 원인 포착 9/10 이상, 수정 후 같은 주장 재지적 1/10 이하, 닫기 입력 반례가 `supported`가 아님.
  - d: 보고만 하는 값(호출, 거부 코드, 사용량·차감).
- 프로젝트 규모 사례(dev 세 사례, 변경 전 변형, 사례마다 1회, 호출 상한 20, 제품 기본 요청 예산)의 비회귀 조건. 앞선 두 빌드가 라벨 결함을 찾은 사례가 여전히 일치하는 모델 발견을 낸다. 모든 사례가 검토 대상 줄을 모두 보내고 AI 검토가 `performed`다.
- 기대하되 통과 조건으로 쓰지 않는 개선(보고만 한다).
  - 한 사례에서 시험·예제 코드에 관한 게시 모델 발견이 1개 이하(이전 5/10, 6/15).
  - 다른 한 사례에서 진단 분류가 `unclear`로 남기는 진단이 3개 이하(이전 19개 중 12).
  - 세 번 놓친 사례의 라벨 결함이 발견되는지.

**비용 없는 사전 확인(가짜 upstream).** 유료 실행 전에 다음을 확인했다.
- 일반 실행과 형식 오류를 섞은 실행 모두에서 세 사례의 AI 검토가 `performed`이고, 필수 검토 task를 잃지 않았고, 검토 대상 줄을 모두 보냈다.
- 회귀 사례 하나의 예행이 종료 코드 0이었다.
- 최종 커밋이 사전 실행을 한 커밋과 같은 요청을 보낸다는 요청 다중집합 비교.

앞선 후보 커밋에서 받은 가짜 upstream 실행 결과는 폐기했다. 독립 코드 검토가 워커 변경으로 이어졌기 때문이다. 그 커밋에는 유료 실행을 하지 않았다. 가짜 upstream 실행에서는 세 사례 모두 검증에 보내지 않은 후보와 판단 불가 복구 코드의 경로가 나타났다. 실모델은 그 경로를 쓰지 않았다(아래).

## 봉인 보류 분할의 짝 측정(품질 작업 전 빌드와 현재 main)

프로젝트 규모 결함 집합의 봉인한 `holdout` 분할(여섯 언어군, 9사례)을 두 빌드로 사례마다 한 번씩 실행한 짝 측정의 기록이다. 비교 대상은 품질 작업 전 빌드(커밋 `e7821c0`, 이하 기준)와 현재 main(커밋 `28e03c7`, 검토 지침 2.10.0, 보고서 생성기 25, 이하 현재)이다. 기준 문서는 2026-11-25에 첫 유료 호출 전에 썼고, 유료 실행과 판정은 2026-11-26에 했다. 두 빌드의 runner·말뭉치·스크립트는 모두 `28e03c7` checkout의 것을 썼고, `--build-root`로 제품만 바꿨다. 모델은 예산 relay를 거친 `gpt-6.2-sol`, OpenCode는 1.19.6이다. 호출 상한은 20이고, 요청·출력 예산은 각 빌드의 제품 기본값이다. 분석기 플래그는 두 빌드에서 같다. 의존성 받기는 두 빌드 모두 켰다(서비스 기본값이다. 앞선 측정은 runner 기본인 끔으로 실행했다). 패턴·taint 분석기(Opengrep)는 두 빌드 모두 설치하지 않았다. 사례마다 변경 전 변형을 빌드별로 1회 실행했다. 보류 봉인을 전후 비교에 쓴 것은 이번이 처음이자 유일하며, 다시 실행한 것은 없다.

평가 운영자는 모델 에이전트이고 사람도 조정자도 아니다. 평가 운영자는 보류 사례의 발견을 판정하지 않았고 라벨과 비교하지도 않았다. 판정은 두 독립 모델 판정자가 빌드 정체를 지운 묶음 하나에서 했다(아래 주 결과).

3. 예산 차단은 제품 실패가 아니다. relay 거절이나 예약 거절로 끊긴 짝은 두 빌드 모두 무효로 하고 짝 비교에서 뺀다. 제품의 파이프라인 관문 실패는 기준대로 그 빌드의 "찾지 못함"이다.

실행 규칙: 현재 빌드의 관문은 참고용이다. 같은 관문이 현재 빌드의 연속 두 실행에서 실패하면 멈추고 보고한다.

### 비용 없는 사전 확인

유료 호출 전에 가짜 upstream으로 두 빌드가 보류 9사례 모두에서 모델 검토를 수행하는지 확인했다. 기준 빌드는 현재의 답 형식을 거절하므로 기준 빌드용 가짜 upstream을 따로 썼다. 두 빌드 모두 9사례 전부에서 AI 검토를 수행했고, 현재 빌드는 형식 오류를 주입한 수집도 통과했다. 유료 사전 확인은 손대지 않은 dev 사례 하나로 했고, 보류 사례에 유료 호출을 하기 전에 네 관문(모델 검토 수행, 전체 조사 수락, 검토 대상 줄 전부 전송, 검증 판정 게시)을 통과했다.

**구조 지표(판정 아님).** 라벨 줄과 겹치는 모델 발견이 있는 사례는 기준 3/9, 현재 7/9다. 라벨 줄과 겹치는 도구 진단이 있는 사례는 두 빌드 모두 2/9다. 겹치는 모델 발견의 검증 상태는 기준 5개 중 supported 3·inconclusive 2(한 사례는 inconclusive만), 현재 9개 모두 supported다. 줄이 겹친다는 것은 같은 결함을 찾았다는 뜻이 아니다. 주 기준은 아래 판정으로만 정한다.

**보고서 검사.** 현재 빌드의 한 사례에서 보고서 검사 스크립트가 "미확정 후보 수 불일치"로 실패했다. 제품은 배포 코드가 아닌 경로의 해석 가설을 요약의 미확정 후보에서 빼는데(결정 A65), 검사 스크립트는 inconclusive 발견을 모두 셌다. 제품의 계산과 문서는 서로 맞고, 검사 스크립트가 이 규칙을 따라가지 않았다. 스크립트는 제품 규칙(빌더 버전별 규칙 포함)을 따르도록 고쳤다. 검사는 첫 실패에서 멈추므로, 평가 운영자가 메모리 안의 사본에서 그 수만 바로잡아 나머지 검사를 돌렸고 모두 통과했다. 이 실행에 기록된 근거 유효성 지표는 측정된 그대로(실패 0/1) 둔다. 고친 스크립트로 다시 채점하면 이 실행의 근거 유효성은 1/1이다. 기록된 0/1은 옛 규칙에서 나온 값이다. 이 사례의 발견은 판정 묶음에 그대로 들어 있다.

**차단 관찰.** 구조 지표의 "실행 없이 재현"은 두 빌드 모두 0이다. 판정 묶음에서 근거 발췌가 없는 발견과 빈 발췌는 없다. 실행·재현을 주장하는 서술은 몇 가지 표현의 정규식으로만 찾았고 찾지 못했다. 이 검사는 완전하지 않다. 상태·통계에 모델 문장이 들어갔는지는 따로 검사하지 않았다. 인용이 주장과 맞는지는 판정자가 본다.

### 주 결과(맹검 판정)

판정자는 모델 둘(Claude Opus 5.5, Claude Sonnet 5.5)이고 사람이 아니다. 두 빌드의 모델 발견 177개를 빌드 정체를 지우고 섞은 묶음 하나로 각자 판정했다. 발견 판정의 일치는 177개 중 159개(Cohen의 kappa 0.85)이다. 라벨 결함 일치 판정은 두 판정자가 같았으므로 불일치 목록은 비었다.

| 두 판정자가 모두 라벨 결함의 발견으로 본 사례 | 기준 | 현재 |
|---|---|---|
| 9사례 중 | 3 | 5 |

짝 결과는 이김 3, 짐 1, 둘 다 찾음 2, 둘 다 못 찾음 3이다. 이김 − 짐 = +2로 사전 기준(이김 − 짐 ≥ 4이고 짐 ≤ 1)에 못 미치고, 회귀(짐 > 이김)도 아니다. **사전 기준에 따른 결론은 구분 불가다.** 서로 다른 결과를 낸 4사례에 대한 양측 부호 검정은 p ≈ 0.63이다. 라벨 결함 발견이 개선됐다는 것은 이 측정에서 보이지 않았다.

판정은 `blind-merge`로 판정 파일에 합쳐 판정자마다 `score`로 다시 채점했다. 사례별 결과와 조치 가능 수는 위 표와 같다. `score`의 "알려진 결함 recall(판정)" 행은 판정된 일치가 하나도 없는 라벨을 분모에서 빼므로 기준 3/4, 현재 5/5로 찍힌다. 사전 기준의 주 지표는 아홉 사례 전부를 세어 3/9 대 5/9다.

현재 빌드에서 라벨 줄에 발견이 있던 7사례 중 둘은 판정에서 일치가 아니었다(원인 기제나 발생 조건이 달랐다). 진 사례 하나에서는 현재 빌드가 같은 함수의 다른 문제를 보고했다.

### 손대지 않은 dev 사례(현재 빌드만)

dev 분할의 Python·Rust 사례 4개를 현재 빌드로 실행했다. 어떤 빌드도 이 사례를 실행한 적이 없고 그 결과는 검토 지침 작성자에게 전달된 적이 없다. 다만 앞선 개정 기간에 지침 작성자의 검색이 사례 디렉터리를 지나갔다([독립성 공개](#모듈-단위-검토-입력의-전후-비교와-회귀-기록)). 사전 확인 하나와 보류 뒤의 선택 사례 셋이다. 기준 빌드는 실행하지 않았고, 판정자는 모델 하나(Claude Sonnet 5.5)다. 선택 사례 셋은 모두 시작 규칙을 만족했고, 넷 모두 네 관문을 통과했다. 사전 확인을 포함한 차감은 3.77달러다.

- 라벨 결함을 찾은 사례는 4/4다. 라벨 줄과 겹치는 도구 진단이 있는 사례는 0/4다.
- 모델 발견은 22개다. 판정은 조치 가능 8, 참고 11, 오탐 1, 중복 1, 범위 밖 1(소스 파일 안의 시험 보조 함수)이다.
- 기준 빌드와의 짝이 없고 사례가 넷이라 개선의 근거가 아니다. 현재 빌드가 처음 보는 사례에서 동작하는지를 보는 관찰이다. 판정 묶음은 보류 묶음과 따로 만들었다.

범위: 이 역할이 모델로 분류한 묶음은 106개이고, 이 역할이 분류하지 않은 진단이 96개 더 있다(지표 관찰이거나 해석 역할이 다룬 것).

### 결론

- 처음 보는 사례에서 제품이 보고하는 발견은 조치 가능한 비율이 더 높고(전체 18% → 36%, `supported` 중 16% → 41%) 시험·예제 코드를 다룬 발견이 훨씬 적다(29% → 3%). 호출은 적고(170 → 63) 검토 대상 줄을 모두 보내며(보내지 못한 줄 16,449 → 0) 장부 차감은 1.23배다.
- 라벨 결함 발견은 9사례 중 3에서 5로 늘었다. 이 표본으로는 우연과 구분되지 않는다(사전 기준 결론은 구분 불가). 라벨 결함의 발견이 나아졌다는 것은 보이지 못했다.
- 오탐은 줄지 않았다(어느 한 판정자 기준 7 → 7, 둘 모두 기준 3 → 3).
- 도구 진단이 라벨 결함의 줄을 가리킨 사례는 두 빌드 모두 9사례 중 2다. 이 지표로 정적 분석 쪽은 나아지지 않았다.
- 라벨 결함 아홉 중 넷을 현재 빌드가 찾지 못했다.

### 판정 묶음과 빌드 노출

묶음은 18단위(2빌드 × 9사례)이고 모델 발견만 담았다(모두 177개). 단위 순서와 발견 순서를 섞고 새 불투명 ID를 붙였다. 인용 발췌는 60줄에서 자른다. 다음 필드는 빌드를 드러낼 수 있다.

- 인용 발췌의 수와 길이: 기준은 발견당 약 1.6개, 중앙값 약 42줄. 현재는 발견당 약 5.6개, 중앙값 약 13줄.
- 주장의 수: 기준 발견당 약 2.3개, 현재 약 3.8개.
- 심각도와 검증 상태의 분포: 기준은 low·inconclusive가 많고, 현재는 medium·supported가 많다. refuted는 현재에만 있다.
- 분류: 시험 공백과 성능 분류는 기준에만 있다.
- 조건 목록의 "후보가 성립하지 않는 조건" 항목: 현재는 모든 발견에, 기준은 대부분에 있다.
- 위치의 수: 기준 발견당 약 1.6개, 현재 약 5.8개.
- 출처: 진단 분류에서 나온 발견은 현재에만 있다(내용으로 짐작될 수 있다).
- 단위당 발견 수와 서술 문체.

진단 분류 묶음은 현재 빌드에만 있고 판정 묶음과 같은 참조 ID를 쓰므로, 두 묶음을 함께 보는 판정자는 빌드를 알 수 있다. 진단 분류 묶음은 맹검 판정이 끝난 뒤에 따로 판정했다. 이 맹검은 약하다.

### 한계

- 판정자가 모델이고 사람의 판정과 판정자의 오류율을 배제하지 못했다. 맹검이 약하다(위 목록).
- 사례마다 빌드마다 한 번씩만 실행했다. 실행 사이의 변동은 측정하지 않았다.
- 보류 사례가 9개라 사전 기준으로 분명한 개선을 가리려면 큰 차이가 필요하고, 9짝으로는 작은 개선과 우연을 가를 수 없다.
- 발견이 9개 프로젝트에 묶여 있어 조치 가능 비율의 p 값은 참고용이다.
- 진단 분류의 판정은 모델 판정자 하나와 표본 확인이다.
- 측정 설정 한계: runner에 npm과 Python 패키지 관리자(`--tool npm=…`, `--tool python=…`)를 주지 않았다. 두 빌드와 손대지 않은 dev 실행 모두 같다. 그래서 JS와 Python의 `deps.*` 작업은 모두 `unsupported`(`package_manager_not_configured`)로 끝났고, 한 JS 실행에서는 tsc와 타입 인식 ESLint가 `dependency_unavailable`로 실패했으며, mypy와 pyright는 외부 패키지 없이 실행됐다. 서비스의 도구 찾기([도구 찾기](ANALYZERS.md#도구-찾기))는 node에 딸린 npm과 pip가 있는 `python3`을 찾았을 것이다. 따라서 이 언어들의 도구 쪽 수치(라벨 줄을 가리킨 도구 진단 포함)는 서비스 기본 설정이 분석할 수준보다 낮게 나왔고, 이는 두 빌드에 같게 적용된다.
- 이 봉인은 쓰였다. 이후의 독립 주장에는 새 사례와 새 봉인이 필요하다.

### 독립성 공개

- 평가 운영자는 보류 사례의 비용 없는 사전 확인 결과(호출 계획, 요청 크기, 줄 수)를 보았다. 사례 내용과 라벨은 판정 묶음에 넣지 않았고, 평가 운영자는 발견을 판정하지 않았다.
- `score`는 두 빌드의 비교를 독립 비교가 아니라고 표시한다(`independent comparison: False`). 보류 등록부가 같은 지침 묶음 digest로 보류 사례를 이미 실행한 배치를 `holdout_seen_by_prior_revision`으로 표시하기 때문이다. 이번 측정은 사례마다 배치를 따로 만들었으므로 빌드별 첫 배치 뒤의 배치가 모두 표시됐다. 앞선 비용 없는 단계에서도 같은 사례를 가짜 upstream으로 실행했다. 프로젝트 규모 보류 분할에 유료 모델 호출을 한 것은 이번이 처음이다.
- 이 측정의 정성적 관찰 셋(현재 빌드가 찾지 못하는 결함이 남아 있음, 오탐이 줄지 않음, 섞인 진단 분류 묶음이 통째로 무해로 분류될 수 있음)을 로드맵으로 옮겼다. 수치와 사례 내용은 옮기지 않았다.
- `fixtures/project-defects/`는 holdout 분할을 담고 있다. 앞선 개정 기간에 지침 작성자의 저장소 검색이 이 디렉터리를 지나갔고, 출력은 걸러졌으며 작성자는 내용을 읽지 않았다고 보고했다([앞선 공개](#모듈-단위-검토-입력의-전후-비교와-회귀-기록)). 이 사실은 이번 비교의 독립성을 낮추는 요인으로 남는다.
- 판정자는 모델 둘(Claude Opus 5.5, Claude Sonnet 5.5)이다. 진단 분류와 손대지 않은 dev 사례의 판정은 Claude Sonnet 5.5 하나가 했다. 사람의 판정은 받지 않았다.
