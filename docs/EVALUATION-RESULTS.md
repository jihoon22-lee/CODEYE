#### 13.5 승격 판단

review-r1은 `candidate-not-promoted`로 둔다. 기본 팩 변경은 소유자가 정한다(docs/37 §11). 판단 근거는 다음과 같다. (이후 소유자가 같은 날 review-r1을 기본 팩으로 정했다. 2.0.0의 변경과 회귀 검증은 docs/49에 있다.)

- **유리:**
  - 보류 비교에서 recall이 같거나 높았다(10/10 대 9/10).
  - 수정 후 오탐이 적었다(2/10 대 4/10).
  - 비용이 약간 낮았다.
  - 근거 없는 주장과 실행 없는 재현은 두 팩 모두 0이다.
- **불리:**
  - 표본이 작아 모든 차이가 구간 안에 있다.
  - R0 회귀 조건 4가 해당했다(W15 입력, 3회 중 1회 low 오탐).
  - 미완료 검토가 1건 있었다.
  - tricky normal 사례를 표본에 넣지 않아 정상 코드의 오탐률은 측정하지 않았다.
- **측정하지 않은 것:**
  - 사람 판정과 판정자 간 일치도;
  - 보고서 읽기 평가(독자 답 없음);
  - tricky normal;
  - C/C++·Rust 분석기 깊이;
  - W21 지표의 유용성.

결과 디렉터리, 판정 파일, 팩 가림 대응표는 저장소 밖 비공개 경로에 보관했다. 재현에는 §11 절차와 `--sample 10 --seed 24`를 쓴다. 이 batch 뒤에 같은 팩 id의 다른 digest로 실행하면 `holdout_seen_by_prior_revision`으로 표시된다. 다음 보류 비교는 새 사례나 tricky normal을 포함해야 독립 비교가 된다.

## 기본 검토 팩 변경 근거와 회귀 기록

### 1. 기본 팩을 바꾼 근거

- **보류 평가.** W24 1회차 보류 비교에서 r1 rc2는 v1보다 나쁘지 않았다. 점추정으로는 recall, 수정 후 오탐, 비용 모두 r1이 앞섰다. 다만 모든 차이가 구간 안에 있으므로 r1이 더 낫다고 단정하지 않는다. 판정은 팩을 가린 개발 에이전트가 했고 사람의 판정이 아니다.
- **하나로 합친 이유.** 두 팩을 기본 후보로 나란히 두면 지침을 바꿀 때마다 두 팩을 따로 고치고 비교해야 한다. 기본 팩 하나만 개정하고 회귀 검증한다.
- **v1을 지우지 않은 이유.** R0·W15·W24 기록은 v1의 팩 id·digest로 해석된다. `TestLegacyPackIsPinned`가 그 요청 바이트를 고정한다. v1 파일과 검증기(docs/34)는 바꾸지 않았다.
- **이름을 유지한 이유.** 디렉터리와 id는 `review-r1` 그대로다. 이름을 바꾸면 기존 기록의 팩 대조(`review_pack_mismatch`)와 운영자 설정이 깨진다.

### 5.2 R0 회귀(실모델)

판정 기준은 실행 전에 적었고 rc2 회귀(docs/46 §13.1)와 같은 형태다. 대상은 R0 쌍 Q01·Q03·Q05·Q08·Q10(수정 전·후), w15, w12-close이고 모델은 relay를 거친 `gpt-6.2-sol`, 각 사례 1회다.

2.0.0이 회귀했다고 보는 조건:
1. 차단 조건(허위 근거, 실행 없는 재현 단정, 모델 서술에서 온 상태·통계, 잘못된 근거를 받아들인 verify 출력)이 나타난다.
2. 수정 전 결함 포착이 Q01·Q03·Q05·Q08·Q10에서 rc2(5/5)보다 2개 이상 적다.
3. 같은 결함을 수정 후 변형 2개 이상에서 다시 지적한다(rc2 0/5).
4. w15와 w12-close의 실행 가능한(supported, info 아님) 오탐이 합쳐 2개 이상이다. rc2 첫 실행은 1개였고 w15 3회 중 1회였다. 1개면 알려진 한계로 보고하며 통과로 세지 않는다.

`review_output_incomplete`·`review_output_invalid`로 끝난 검토 task 수, 3번째 호출과 `evidence_id_dropped` 수, 비용은 판정 기준이 아니고 보고만 한다.

## 모듈별 검토 도입의 회귀 기록

### 실행 전에 적은 기준

모듈별 검토(모듈 단위 조각 조사·검증과 호출 상한)를 넣은 변경의 회귀 검증이다. 검토 지침 문구와 팩 digest는 바꾸지 않았고, 모델 없이 한 요청 비교에서 기존 사례의 요청은 변경 전과 같았다. 아래 기준과 대상은 실행 전에 적었고 결과를 보고 바꾸지 않는다.

- 대상: 회귀 쌍 Q01·Q03·Q05·Q08·Q10(수정 전·후), 고정 입력 `w15`·`w12-close`, 공개 고정 사본 `pilot`. 각 1회, relay를 거친 `gpt-6.2-sol`, 호출 상한 33, gitleaks·ruff·eslint·node 설정.
- 기준 A — 기존 사례의 회귀로 보는 조건(직전 회귀 기록과 같은 형태):
  1. 차단 조건(허위 근거, 실행 없는 재현 단정, 모델 서술에서 온 상태·통계, 잘못된 근거를 받아들인 verify 출력)이 나타난다.
  2. 수정 전 결함 포착이 직전 기록(5/5)보다 2개 이상 적다.
  3. 같은 결함을 수정 후 변형 2개 이상에서 다시 지적한다(직전 0/5).
  4. `w15`와 `w12-close`의 실행 가능한(supported, info 아님) 오탐이 합쳐 2개 이상이다. 1개면 알려진 한계로 보고하고 통과로 세지 않는다.
- 기준 B — 모듈별 검토의 조건(`check_coverage`, 유료 실행에는 예외 없음): 파일럿이 아닌 사례에 조각 task가 없고 팩 digest가 고정값이다. 파일럿이 `completed`이고 AI 검토가 `performed`다. 장부의 `calls_used`가 알려져 있고 상한 이하다. 예산 소진 조각에는 기록도 호출도 없다. overview와 조각이 같은 파일을 보내지 않는다. 모델에 보낸 파일 수가 overview만의 수보다 크다. `--audit-results`가 통과한다. relay 장부에 거절·차단 요청이 없다.
- 보고만 하는 값(판정 기준 아님): 허용된 조각 수, 모듈별 보낸 파일 수, 호출 수와 비용, 조각에서 나온 후보 수와 검증 상태. 조각이 찾은 후보의 옳고 그름은 이 실행으로 주장하지 않는다.
