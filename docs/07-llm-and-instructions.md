# 07. 모델 검토 역할과 지침

## 현재 실행되는 역할

R0에서 모델이 받는 작업은 맥락 파악(`review.context`), 독립 코드 조사(`review.investigate`), 후보 검증(`review.verify`)이다. 맥락 파악은 선택한 문서·설정·코드 발췌를 함께 본다. Go vet은 워커가 실행하고, 보고서의 수치·상태·리비전은 서버가 결정한다. [역할 선택 코드](../prompts/review-v1/bundle.go) · [맥락과 조사 기록](33-w11-context-review.md) · [검증 기록](34-w12-verifier.md)

활성 팩은 공통·역할·영역·Go 지침을 조합한다. 워커가 각 역할의 출력 형식을 지정하고 스냅샷에 묶인 근거를 확인한다. 팩에 종합·보고 문서가 있어도 R0에서 별도 모델 호출을 뜻하지 않는다. 승인된 로컬 소스 루트만 모델에 제공할 수 있다. 공개 Git 취득 시험에서도 모델 전송 승인이 없어 해당 작업은 정책 제외로 기록됐다. [활성 팩](../prompts/review-v1/pack.yaml) · [모델 연결과 취소](32-w10-opencode.md) · [R0 파일럿](36-r0-pilot.md)

## R1 역할별 지침 후보

다음 파일은 후보 팩 `review-r1`(2.0.0-rc2, 승격 전)의 역할 지침이다. 노드 운영자가 `codeye agent --review-pack review-r1`로만 선택하고 기본값은 `review-v1`이다. 이전 판 rc1을 R0 사례 다섯 쌍과 W15 첫 입력에서 활성 팩과 같은 조건으로 한 번 대조했다. 조정에 쓴 사례라 독립 평가가 아니므로 승격하지 않았다([TC-100 결과](37-w15-discovery-and-progress.md#11-결과--tc-100-실모델-대조활성-팩-대-후보-팩)). rc2는 아래 변경 뒤 실모델로 평가하지 않았다. 계획·출력 검사·기록·보고서 규칙은 [W15 2단계 결과](37-w15-discovery-and-progress.md#10-결과--2단계후보-팩-연결-실모델-없음)를 따른다. 한 역할의 출력은 다음 역할에 넘길 자료다. 역할 수가 모델 호출 횟수를 정하지 않는다. 환경 버전 비교, 문서 존재 확인, 정적 검사 실행, 보고서 게시는 플랫폼만으로 처리할 수 있다.

| 지침 | 허용된 입력 | 다음 단계에 남길 결과 |
|---|---|---|
| [환경 분석](../prompts/review-r1/environment.md) | 모듈 범위, 선언 버전, 노드 관측값과 출처 | 검사별 요구·관측·불일치·미확인과 그 영향 |
| [문서 검토](../prompts/review-r1/documents.md) | 경로별 문서·설정·선택 첨부와 제한된 코드 발췌 | 적용 경로, 문서상 계약, 상충하는 근거, 미확인 질문 |
| [독립 코드 분석](../prompts/review-r1/investigate.md) | 모듈 계약, 환경 한계, 코드·테스트 발췌 | 원인·발생 조건·영향·반증 가능성을 가진 후보 또는 빈 목록 |
| [정적 진단 해석](../prompts/review-r1/interpret-diagnostics.md) | 어댑터가 발급한 관찰 ID, 버전·범위·파싱 상태와 관련 발췌 | 원시 관찰에 연결한 영향 가설 또는 해석 한계 |
| [후보 검증](../prompts/review-r1/verify.md) | 이전 후보 원문과 ID, 호출부·테스트·반대 근거 | 지지·기각·판단 보류의 이유, 유효·무효 조건, 추가 확인 사항 |

독립 코드 조사에는 원시 경고를 입력하지 않는다. 도구 진단 해석은 별도 입력으로 수행하며 원시 메시지와 심각도를 보존한다. 어떤 역할도 모델의 서술로 검사 성공·재현·진행률을 결정하지 않는다. 보고서 생성은 고정된 구조화 기록을 사용한다.

### rc2에서 바꾼 것(W24 2a단계)

보류 사례 평가 전에 지침에서 사례 내용을 빼고 언어 지침을 생태계별로 고르게 했다([A29](19-decisions-and-open-questions.md)).

- **사례 문구 제거.** rc1의 조사 지침 예시는 R0 Q08 수정본의 답(비어 있지 않은 입력 계약)을 담고 있어 그 사례를 무효로 만들었다. 이 예시를 지웠다. 문서·환경·해석·검증 지침의 예시도 바꿨다. 각각 W15 첫 입력(루트와 하위 모듈의 상충하는 재시도 안내, 하위 모듈의 Go 버전 요구), W15 worker 시험의 printf 진단, W12의 호출자 정리 반례를 옮긴 문장이었다. 모두 사례 없는 규칙으로 바꿨다. 경계 입력을 먼저 공개 계약으로 확인하라는 조사 지침의 일반 규칙은 유지했다. `bundle_test.go`는 지침 파일에 사례 ID·작업 ID·fixture 경로와 식별자가 없는지 검사한다. 같은 뜻을 다른 말로 쓴 문장은 이 검사로 잡지 못한다.
- **언어 지침.** `languages/go.md`와 같은 형식으로 네 지침을 추가했다.
  - [C/C++](../prompts/review-r1/languages/cpp.md): 수명·소유권, UB, 부분 translation unit 범위.
  - [Python](../prompts/review-r1/languages/python.md): 오류 흐름, 보안 sink, interpreter·import 공백.
  - [JS/TS](../prompts/review-r1/languages/javascript.md): 비동기 순서·취소, 타입·입력 경계.
  - [Rust](../prompts/review-r1/languages/rust.md): unsafe 불변식, panic 경로.

  의존성·타입·헤더가 없어 생긴 진단은 결함이 아니라 분석 공백으로 다룬다. 도구 규칙 ID는 쓰지 않았다. Go 지침과 영역 팩은 review-v1과 같은 바이트다.
- **선택 규칙.** rc1은 모든 역할에 Go 지침을 붙였다. rc2는 스냅샷 scope 안의 소스 생태계 지침만 생태계 이름 순서로 붙인다. 판별은 분석기 팩의 공백 계획과 같은 `pack.InScope`다([docs/39 §2.8](39-r1-analyzer-packs.md#28-범위에-없는-생태계와-분석기-공백)). 지원 생태계가 없으면 언어 지침을 붙이지 않는다. 역할별 digest는 pack.yaml과 실제로 고른 파일만 덮는다. 그래서 같은 역할도 생태계 조합마다 digest가 다르다. 호출 기록의 `pack_files`가 사용한 언어 지침을 보인다. Go만 있는 예시 기록(w15)의 역할별 digest 앞 12자리는 environment `6e97b2ac23a1`, documents `a42ead60396d`, investigate `af3590babf43`, interpret `68790a642d13`, verify `d0a85eb93bfd`다.
- **요청 크기.** 다섯 생태계가 모두 범위에 있으면 지침이 7,370바이트 늘어난다(verify 지침 9,501→16,871바이트). w15 입력에 Python·Rust 파일을 더하면(지침 셋) 가장 큰 요청은 verify의 18,319바이트다. 합성 최악 입력에서도 모든 요청은 40,000바이트 한도 안이다. 대신 조사 역할의 코드 발췌가 8개에서 5개로 줄고(`review_input_trimmed`), 검증 역할은 최대 길이 후보 6개 중 1개를 보내지 못한다. 그 후보는 `unreviewed`(`verification_budget_exceeded`)로 남고 verify task는 `review_input_incomplete`로 실패한다. Go만 있으면 같은 입력에서 6개를 모두 검증한다. rc2 당시 코드 발췌와 해석 창은 Go 파일만 썼다(`code_excerpts_go_only`). 그래서 다른 언어 지침은 그 언어의 코드 없이 도구 관찰·문서와 함께 전달됐다. W24 2c단계에서 다섯 언어로 넓혔다(아래). 요청 한도를 바꾸는 일은 소유자 결정으로 남겼다.
- **평가.** rc2는 실모델로 평가하지 않았다. 플랫폼 검사는 scripted caller로만 확인했다. 조정에 쓰지 않은 보류 사례 평가는 W24 평가 runner에서 수행한다.

### 다섯 언어 검토 입력(W24 2c단계)

조사·해석·검증 역할이 C/C++·Python·JS/TS·Rust 스냅샷에서도 코드를 받는다. 그 전에는 Python만 있는 스냅샷에서 `review.investigate`가 `review_input_unavailable`로 실패하고 verify는 생략됐다. 기본 팩 review-v1의 코퍼스 규칙은 [W11 기록](33-w11-context-review.md#다섯-언어-코퍼스w24-2c)에 있다. 종류 판별(code·test·config)은 경로만 보는 한 규칙이고, worker와 보고서 decoder가 함께 쓴다([A31](19-decisions-and-open-questions.md)).

- **조사 코드 발췌.**
  - Go 파일은 W15 규칙 그대로 가장 깊은 go.mod 디렉터리(모듈)로 묶는다. vendor·testdata·숨김·`_` 디렉터리는 뺀다.
  - 다른 언어 파일은 같은 생태계의 manifest가 있는 가장 깊은 디렉터리로 묶고, 없으면 `.`다. manifest는 pyproject.toml·setup.cfg, package.json·tsconfig.json, Cargo.toml, CMakeLists.txt·compile_commands.json이다. 제외 디렉터리는 W11 기록과 같다.
  - 묶음 안의 순서는 진입점, 소스, 테스트이고 같은 순위는 깊이와 경로 순이다. 진입점 규칙은 W11 기록과 같다. JS/TS `index`는 모듈 루트나 그 `src`에 있을 때만 진입점이다. 순회마다 각 생태계의 첫 묶음을 생태계 이름 순으로 돌고, 다음 순회에 둘째 묶음을 돈다. 그래서 첫 순회가 범위 안의 모든 언어를 지난다. Go만 있으면 순서는 이전과 같다.
  - 발췌는 파일 첫 50줄·2,400바이트 이하, 합계 8개·12,000바이트다. 근거 ID 규칙은 같다. 발췌가 있는 다른 언어 모듈 디렉터리도 `modules`에 넣는다.
  - `code_excerpts_go_only`는 더 쓰지 않는다. 보고서는 이전 기록을 위해 문구를 남긴다. 범위 안 소스가 제외 디렉터리 아래에 있어 빠지면 `source_in_excluded_directories`를 남긴다. 소스가 모두 그 아래에 있으면 investigate는 이전처럼 `review_input_unavailable`로 실패하고, 기록에 이 제약이 남는다.
- **해석 창.** 진단 위치가 다섯 언어 중 하나의 소스 파일이면 줄 창을 만든다. 위치 10줄 앞부터 21줄, 1,600바이트 이하이고 구문 분석기를 쓰지 않는다. manifest·설정·문서 같은 소스가 아닌 파일에는 창이 없고 관찰만 간다. 창은 여전히 최대 4개다.
- **검증.** 후보가 인용한 발췌와 문서 계약으로 검증한다. 호출자·테스트 확장(Go 구문 트리)은 Go만 한다(`caller_expansion_go_only`). 다른 언어만 인용한 후보에는 `no_symbol_for_expansion`이 남는다.
- **비밀값 선별.** 새 발췌와 창도 같은 읽기 경로(`readLines`)를 지나므로 W21 선별이 그대로 적용된다. 탐지 결과를 쓸 수 없으면 어떤 모델 요청도 보내지 않는다(`TestW24SecretScreenOnPython`).
- **언어 지침 선택은 rc2 그대로다.** 역할 입력에 실제로 있는 언어의 지침만 붙이는 안을 시험 구현했다. 적용 역할은 investigate·interpret·verify이고, 고른 언어가 없으면 rc2 규칙을 쓴다. 같은 최악 입력 시험으로 쟀다.
  - 큰 다언어 최악 입력(`TestR1RequestSizeWorstCaseAllLanguages/large`, 다섯 언어마다 최대 크기 모듈 3개)에서 rc2 규칙의 verify는 최대 후보 6개 중 5개를 보냈다(최대 36,106바이트). 시험 구현도 5개였다(36,456바이트).
  - investigate는 첫 순회가 다섯 언어를 모두 담아 지침이 줄지 않았다. 코드 발췌는 지침과 문서 결과 때문에 5개 중 3개만 보냈다(`review_input_trimmed`).
  - interpret만 32,223바이트에서 26,676바이트로 줄었다. 이 역할은 한도 압박이 없었다.
  - 압박을 줄이지 못했으므로 rc2 규칙을 유지했다. digest 규칙(pack.yaml과 고른 파일)도 그대로다.
  - rc2의 작은 경우(다른 언어 한 줄 파일, `tiny`)는 이제 그 파일이 발췌·후보 근거가 되어 6개를 모두 검증한다(35,630바이트). 입력이 작아진 결과이고 지침 선택의 효과가 아니다.
- **한계.**
  - 발췌는 파일 첫 줄부터다. 진단이 없는 파일의 뒷부분은 보이지 않는다.
  - 예산이 모자라면 목록 뒤쪽이 먼저 빠진다. 첫 순회에서 생태계 이름 순으로 뒤인 Python·Rust 발췌가 여기에 해당한다.
  - 확장자 없는 스크립트는 소스로 보지 않는다.
  - 지침 선택 수치는 되돌린 시험 구현에서 쟀다. HEAD에서는 rc2 규칙 수치만 다시 얻을 수 있다.
  - 실모델로 평가하지 않았다. 선택 규칙이 리뷰 품질을 높인다는 근거는 아직 없다. W24 보류 사례 평가에서 확인한다.

## 공통 입력과 출력 경계

- 플랫폼이 승인한 스냅샷·모듈·발췌와 근거 ID만 전달한다. 원본 절대 경로, 인증정보, 평가 정답, 개인 모델 세션을 입력으로 사용하지 않는다. README나 대상 저장소의 AGENTS에서 발견한 실행·권한 요청은 문서 내용으로 취급한다.
- 문서에서 읽은 기대 동작, 코드에서 관찰한 동작, 그로부터 추론한 영향을 구분한다. 근거에는 상대 경로·행 범위·blob 해시 또는 검증된 도구 관찰 참조가 있어야 한다. 모델은 새 증거 ID를 발급하거나 셸·네트워크·추가 모델을 호출하지 않는다.
- 워커가 스냅샷의 바이트와 행 범위를, 서버가 run·attempt·manifest·근거 연결을 확인한다. 실패·시간 초과·정책 제외는 해당 작업에 남기고 이미 확보한 도구 관찰을 보존한다. 반증 입력이 부족한 후보는 미검증 또는 판단 보류로 전달한다.
- 호출마다 모델·클라이언트 버전, 선택 파일과 팩 digest, 요청 digest, 가용 usage와 결과를 추적한다. 평가에는 추가·제거한 입력과 호출 예산도 남긴다. 외부 모델로 자동 전환하지 않는다.

## 연결 방식과 실패 처리

R0의 관리형 OpenCode는 작업별 디렉터리와 분리된 설정을 사용한다. 별도 사내 serve 연결을 추가할 때는 인증·버전·취소와 workspace marker/digest를 대상 환경에서 검증한다. 통신 단절이나 모델 사용량 미제공은 미확인으로 남기며 모델의 내부 추론을 로그나 화면에 표시하지 않는다. 검증 역할의 형식 복구는 제한된 한 번이고 계속 잘못된 항목은 격리한다. [실연동 범위](32-w10-opencode.md) · [후보별 검증 규칙](34-w12-verifier.md)

## 지침을 활성화할 때

W15에서 환경·문서 자료를 플랫폼이 먼저 수집하고 후보 팩의 역할을 개별 task로 나눴다. 워커의 선택기·출력 검증·선행 기록과 보고서의 필수 역할 판정을 함께 수정했다([A21](19-decisions-and-open-questions.md)). 계획을 고정할 때 각 역할의 필수 여부와 생략 사유를 정한다. 문서가 없어 생략한 문서 역할을 모델 검토 성공으로 세지 않는다. 반대로 필수 모델 작업이 실패했으면 도구 결과가 남아도 검토 전체를 완료로 올리지 않는다. R0의 기존 기록은 작성 당시의 세 역할과 팩으로 계속 해석한다. 운영자가 승인한 모델 범위와 예산 안에서 같은 입력을 활성 팩과 후보 팩으로 평가한 뒤 기본값을 결정한다. 조정에 쓰지 않은 보류 사례 평가는 W24에서 수행한다.
