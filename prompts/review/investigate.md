# 독립 코드 분석 지침

검토의 대상은 배포되는 코드다. 후보는 배포 코드의 결함만 다룬다. 시험·예제·벤치마크·생성물·외부 코드(`path_class`가 있는 발췌)는 맥락이며 보조 근거다. 시험이 기대 동작을 보이거나 배포 코드의 결함을 드러내면 보조로 인용하되 후보의 위치와 주된 근거는 배포 코드의 줄이다. 시험이 덮지 않는 동작도 덮지 않는 배포 코드의 줄을 인용한다. 배포 코드의 줄을 인용하지 않은 후보는 검증되지 않는다.

진입점에서 결과까지 추적한다. 문서 계약은 적용 경로 안에서 조건과 기대 결과를 파악하는 데 쓴다. 입력이 공개 계약에 포함되는지 먼저 확인한다. 반환값, 오류·취소 시 정리, 소유권 이전, 동시성 경계에서 손상될 수 있는 속성을 찾는다.

코드 발췌는 대개 파일 전체나 선언 단위다. 함께 온 파일 사이의 호출 관계를 따라 읽는다. 후보마다 무엇이 잘못되는지, 실제 발생 가능한 조건, 인용한 줄이 실패를 만드는 과정, 사용자 영향, 수정이 지켜야 할 속성, 후보를 반박할 수 있는 근거나 남은 불확실성을 연결한다. 원인이 같은 후보는 합친다. 계약 밖 입력은 실제 호출 근거가 있을 때만 후보로 삼는다. 보안 관련 관찰은 영향과 방어 방법에 집중한다.

짝으로 설정한 변수나 분기(함께 대입한 변수, 대칭 분기, 사례표)는 각각 짝과 같은 자리에서 쓰이는지 확인하고, 하나만 다르면 결과가 갈리는 구체적 입력과 그 결과를 적는다.

단서(`leads`)는 판정이 아니다. 보낸 코드로 판단할 수 있으면 후보로 쓴다.

강점에는 구현이 지키는 불변조건이나 막는 실패, 적용 경로, 구현 코드 근거를 적는다. 테스트 코드는 보조 근거다. 지표, 진단 부재, 함수 이름만으로 강점을 쓰지 않는다.

전체 조사에서 계약마다 각각 판정한다. 이유에 진입점이나 함수, 결과를 결정하는 검증·분기, 관찰할 결과를 연결한다. 계약이 사용자 진입점의 동작을 약속하면 호출부가 해당 조건에서 구현으로 연결되고 그 결과가 사용자에게 어떻게 전달되는지 확인한다. 계약이 특정 함수의 반환값이나 분기만 약속하면 그 함수에서 판정한다.

- 일치(`match`)는 해당 범위의 조건에서 피할 수 없는 검증이나 결과를 구현이 보여 줄 때 쓴다. 이름이 같거나 관련 함수가 등장한 사실, 테스트 이름이나 주석만으로 동작을 확인하지 않는다.
- 불일치(`mismatch`)는 계약 범위의 입력에서 구현이 반대 결과를 낼 때 쓴다. 아직 묶여 있는 여러 조항에서 준수와 위반을 각각 확인했으면 부분 일치(`partial`)로 적고 두 결과의 조건과 근거를 밝힌다.
- 미확인(`unknown`)은 결정적 호출부·분기·결과를 확인하지 못했을 때 쓴다. 확인한 부분과 추가로 확인할 위치나 조건을 이유에 적는다. 설계의 목표나 한 함수의 동작만 확인한 상태에서 사용자 경로 전체가 구현됐다고 판정하지 않는다.

`scope.direct_calls`가 있으면 연결된 호출부와 구현의 발췌를 함께 읽는다. 호출 관계는 입력 검증이나 사용자에게 전달되는 결과를 별도로 입증하지 않는다. 테스트는 해당 입력에 어떤 결과를 단언하는지 읽어 보조 근거로 쓰고, 실행 결과를 기록하지 않는다.

사용자에게 의미 있는 미확인 계약에 대해 `navigation_candidates`에서 아직 읽지 않은 위치가 누락된 분기·호출·단언을 보여 줄 가능성이 있으면 `contract_probe`로 한 건을 고른다. 판정 이유에 그 위치나 식별자가 어떤 미확인 조건과 결과를 확인할 수 있는지 적는다. 관련 후보가 없거나 계약을 이미 판정했다면 후속 요청을 생략한다.

`scope.workflow_routes`가 있으면 연결된 계약의 실제 등록·처리 구현을 `scope.excerpts`에서 확인한다. 상태를 바꾸는 처리와 이후 조회가 함께 필요한 계약은 양쪽의 조건과 결과가 이어지는지 확인한다. 확인하지 못한 분기나 저장·조회 처리가 있으면 필요한 코드 근거를 특정해 대조를 미확인으로 남긴다. `test_evidence_id`가 있으면 해당 조건의 입력과 결과를 실제로 단언하는지 읽는다. 테스트 원문으로 실행 성공이나 구현 전체를 확정하지 않는다.
