# 공통 검토 영역 팩

적용할 영역과 scope는 계획이 정한다. 모든 영역을 모든 파일에 기계적으로 적용하지 않는다.

| 영역 | 확인할 질문 | 반례·과잉 주장 방지 |
|---|---|---|
| 정확성/경계 | 빈 값·최대 값·정렬·범위·형 변환·시간 경계가 계약에 맞는가 | 도메인 제약으로 불가능한 입력인지 확인 |
| 오류 전파 | 실패가 호출자에게 전달되는가, 부분 성공을 성공으로 반환하는가 | 의도된 best-effort와 실제 손실을 구분 |
| 취소/시간 제한 | 취소가 하위 작업까지 전파되는가, deadline 후에도 자원을 잡는가 | 협력 취소 계약과 외부 서비스 한계를 확인 |
| 자원 수명 | 획득→사용→이전→정리가 모든 경로에서 맞는가 | 상위 owner/RAII/defer/finally를 먼저 확인 |
| 동시성 | 공유 상태·원자성·잠금 순서·재진입·signal이 맞는가 | 실제 병렬 접근 가능성과 동기화 경계를 확인 |
| 데이터 일관성 | 트랜잭션·멱등성·재시도·중복 입력·partial write가 안전한가 | 저장소나 상위 계층의 보장을 읽기 |
| API/계약 | producer와 consumer의 스키마·오류·단위·null 처리 일치 | 버전 협상·호환 변환이 있는지 확인 |
| 소스 보안 | 입력에서 sink까지 검증·권한·경로·escaping이 이어지는가 | sanitize가 올바른 맥락에 적용되는지, 실제 노출 경로 확인 |
| 성능 구조 | 반복 호출·복잡도·잠금·메모리/버퍼 증가가 중요한 경로에 있는가 | workload 없이 실제 지연·처리량 수치를 만들지 않기 |
| 구조/유지보수 | 모듈 방향·중복 책임·순환·상태 소유권이 변경 위험을 만드는가 | 취향이나 복잡도 하나를 기능 결함으로 올리지 않기 |
| 테스트 공백 | 중요한 조건과 실패 경로를 검증하는 사례가 있는가 | 파일명 검색만으로 테스트 없음 확정 금지; 실행 여부 별도 |

각 검토는 assertion, conditions, evidence IDs, checked counterexamples, limitations로 제출한다. 포괄적 체크리스트 완료 표시보다 실제 확인한 경로와 범위가 중요하다.
